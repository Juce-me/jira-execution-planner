## Response compression

Verified on: 2026-10-26.

- **Response compression** (aliases: gzip, `Content-Encoding`, compressed static assets, `Vary: Accept-Encoding`): [`register_response_compression`](../backend/response_compression.py) installs one `after_request` handler and is called first in [`create_app`](../backend/app.py), so Flask's reverse-order handlers run it last, after Flask-CORS (`Vary: Origin`) and [`register_security_headers`](../backend/security/headers.py) (`Cache-Control`, CSP). It consumes the request's `Accept-Encoding` and the final response; it produces `Content-Encoding: gzip`, a matching `Content-Length`, a weak ETag, no `Accept-Ranges` and a merged `Vary: Accept-Encoding`. Rules: GET and HEAD (HEAD describes the same representation as GET), status 200, allowlisted type (`COMPRESSIBLE_TYPES`), at least `MIN_COMPRESS_BYTES`, gzip level `GZIP_LEVEL`, never a generator response (`is_streamed and not direct_passthrough`, so the Board NDJSON stream in [`eng_board_routes.py`](../backend/routes/eng_board_routes.py) and the Scenario draft SSE in [`scenario_draft_routes.py`](../backend/routes/scenario_draft_routes.py) pass through), never an encoded, `no-transform`, range or error response, never `/api/auth/*` or `*.map`. `send_file` responses (the static files served by `serve_frontend_dist` and `serve_dashboard` in [`jira_server.py`](../jira_server.py)) are read once; under `/frontend/dist/` the gzip bytes are memoized by path and original ETag (at most `MAX_MEMOIZED_ASSETS`, oldest evicted, one lock so concurrent cold requests compress once). Every GET or HEAD response of an allowlisted type and every GET or HEAD 200 or 304 under `/frontend/dist/` carries `Vary: Accept-Encoding`, and a 304 for a compressible file carries the validators of its 200 for the client (weak ETag for gzip clients). Production ingress behavior is not in the repository and is unverified. Contracts: [`test_response_compression.py`](../tests/test_response_compression.py), `test_real_board_stream_ignores_gzip` in [`test_eng_board_routes.py`](../tests/test_eng_board_routes.py).

## Bounded Jira batches and dependencies

Verified on: 2026-10-26.

- **Bounded Jira batches** (aliases: batch runner, helper slots, rate-limit cooldown): [`run_batches`](../backend/services/jira_batches.py) runs independent Jira batches and returns a `BatchOutcome` (`results` in batch order, `None` for a batch that did not finish; the single `failure`, chosen so that any error that is not a `JiraBatchIncomplete` (an auth error, for one) outranks incomplete batches and the lowest batch index decides among equals, so an auth error in any batch still surfaces as the 401; `deadline_exceeded`; `rate_limited`; `complete`; `raise_if_failed()`). At `max_concurrency <= 1` it runs inline on the caller's thread in order. Above 1 the caller only waits on a request-local `ThreadPoolExecutor`: one worker always starts, and up to `max_concurrency - 1` helpers start only when the process-wide `BoundedSemaphore(JIRA_BATCH_GLOBAL_SLOTS)` has a free slot without waiting and no `RATE_LIMIT_COOLDOWN_SECONDS` cooldown is active (requested at the start and after each finished batch). No batch is admitted after the deadline (a `time.monotonic()` value), a failure, a raising `cancel_check`, or a rate-limited failure, which also starts the process-wide cooldown. The caller returns at the deadline without waiting for a stuck worker; the pool is shut down with `wait=False, cancel_futures=True`, late results never reach the returned outcome, and each helper releases its slot when it exits. `JiraBatchIncomplete` carries `reason` (`http_status`, `continuation`, `deadline`, `rate_limited`, `cancelled`), `rate_limited` and `partial`. Limits: `JIRA_BATCH_CONCURRENCY` per run, `JIRA_BATCH_GLOBAL_SLOTS` helpers per process. It bounds worker threads, not Jira calls per second; the shared retry loop in [`jira_client.py`](../backend/jira_client.py) is unchanged. Consumed by `fetch_issues_by_keys` and by the Story-readiness compute (ENG Story Readiness above). Contract: [`test_jira_batches.py`](../tests/test_jira_batches.py).
- **Dependencies collection** (aliases: `/api/dependencies`, dependency map, incomplete dependencies): `get_dependencies` in [`eng_routes.py`](../backend/routes/eng_routes.py) sets a `_DEPENDENCIES_DEADLINE_SECONDS` deadline and calls `collect_dependencies` in [`jira_server.py`](../jira_server.py) strict at `JIRA_BATCH_CONCURRENCY`. `collect_dependencies` fetches the requested keys, then (round two, skipped when round one failed) the linked keys outside them, through `fetch_issues_by_keys` in [`jira_client.py`](../backend/jira_client.py): batches of `KEY_BATCH_SIZE` keys; strict mode follows `nextPageToken` until `isLast` (at most `MAX_PAGES_PER_BATCH` pages), raises `JiraBatchIncomplete` on a non-200 (`rate_limited` when the status or its `upstreamStatus` is 429), a malformed page or a missed deadline, and each call's timeout is `max(1, min(30, deadline - now))`. Above cap 1 every worker call carries the resolved auth context; at cap 1 the implicit request context is kept. A complete result is cached in `DEPENDENCIES_CACHE` and answered exactly as before; an incomplete one is answered `200` with `{dependencies: <partial map>, incomplete: true, reason}`, the same `Server-Timing`, and is never cached, so the next request retries. An auth error in any batch stays a 401. Non-strict mode (the default; `/api/issues/lookup`, the Scenario planner's `collect_dependencies(issue_keys)` and the Epic record fetches) is unchanged: serial, one page per batch, failed batches logged and skipped. Client: `fetchDependencies` in [`dashboard.jsx`](../frontend/src/dashboard.jsx) always applies the map it receives and owns one state cell, `dependencyIncomplete`: set when the answer carries `incomplete: true`, is not OK, or the request fails with a non-abort, non-authentication error; cleared when a fetch starts or completes cleanly and wherever a scope change clears or replaces the map (`resetSprintScopedState`, `clearEngGroupScopeData`, `applyGroupState`), so a new Sprint or Department never shows the previous scope's notice before its own request. As a second line of defense `dependenciesIncomplete` is also gated on a non-empty `dependencyKeySignature`; the effect that clears the map for an empty scope is byte-pinned by `test_epic_refresh_source_guards.js`, so the flag is not reset there. Its `ENG_TASK_LOAD_OUTCOME` return values (what [`loadPerformance.js`](../frontend/src/eng/loadPerformance.js) records) are unchanged, and a 401 stays the global sign-in lock, never a notice. [`EngView.jsx`](../frontend/src/eng/EngView.jsx) renders, after the Story readiness notice, a second use of the registered `story-readiness-notice` hook (`role="status"`, "Some dependencies could not be loaded.", and a `secondary compact` Retry that bumps `dependencyRefreshNonce`, the existing refetch trigger). The per-Epic refresh paths (`refreshEpicDependencies`, the freshness adapter in [`dashboardFreshnessAdapters.js`](../frontend/src/dashboardFreshnessAdapters.js)) are unchanged: they merge only the keys they receive and never set the notice. On an http or https page with `fetch` it resolves the base with `resolveBackendUrl(window)` ([`backendUrl.js`](../frontend/src/api/backendUrl.js)) and starts the two reads of `earlyBootstrapRequests` in [`earlyBootstrapContract.js`](../frontend/src/api/earlyBootstrapContract.js) (`/api/config?includeViewConfig=true` and `/api/groups-config`, each `init` equal to what `fetchAppConfig` and `fetchGroupsConfig` in [`configApi.js`](../frontend/src/api/configApi.js) pass to `fetch`), each with its own `AbortController`, `credentials: 'same-origin'` and `referrerPolicy: 'no-referrer'`, so a share-link query in the address bar never leaves the page as a `Referer`. It reads no query string and no storage and never throws. Ownership is shared through the `window` slot (`EARLY_BOOTSTRAP_SLOT`, created by `earlySlot`): one entry per key (`config`, `groups`), created by whichever side reaches the key first, `state: 'early'` (with `url`, `method`, `cache`, `startedAt`, `startedAtEpoch`, `settledAt`, `claimed`, `controller` and a `promise` that resolves to the `Response` for any HTTP status, or to `null` on a network error or abort) or `state: 'app'` (the app made its own request, so a script that arrives later skips the key). Each endpoint is therefore requested once in any arrival order; with the script blocked, failing or late the app requests both itself, as before. - **`apiFetch` adoption contract** (aliases: `performApiFetch`, `takeEarlyResponse`, early adoption): `performApiFetch` in [`http.js`](../frontend/src/api/http.js) first offers each read to `takeEarlyResponse` in [`earlyBootstrapRegistry.js`](../frontend/src/api/earlyBootstrapRegistry.js). A URL that is not one of the two early URLs returns `null` with no effect; an early URL with no entry is marked `state: 'app'`; an entry that is claimed or the app's returns `null`. Otherwise the entry is claimed (in the slot, so a second bundled copy of the registry, as in `auth-focus-refresh.js`, cannot adopt it too); an entry older than `EARLY_BOOTSTRAP_MAX_AGE_MS`, a non-GET call, a different URL or a different `cache` mode aborts the early request and returns `null`. An adopted read links the caller's `AbortSignal` to the early controller (already aborted: at once; later: while the headers or the body are pending; the listener goes once the request has finished), so `fetchBootstrapConfig`'s `CONFIG_BOOTSTRAP_TIMEOUT_MS` still ends a stalled early body with `ConfigBootstrapTimeoutError` (see Startup config timeout above). Every HTTP status is adopted, 401 and 5xx included: the unchanged 401 handling, body wait and lock checks run on the adopted response, and the global authentication lock is stamped with the early request's `startedAtEpoch`, the value `consumeAuthRecoverySuccess` in [`authRecoveryCoordinator.js`](../frontend/src/api/authRecoveryCoordinator.js) compares with a recovery success. Only `null` (network error, abort) falls back to one normal request, which rejects at once when the caller's signal is aborted. `trackedFetch` reads `earlyTimingOf(response)` and times an adopted response from the early start to its response headers (`settledAt`; the `Math.min` against the end time never binds, because that end time is read after `apiFetch` has awaited the body), so the `config_bootstrap` `api_result` does not absorb the wait for the dashboard entry; an adopted read that ends in an error keeps the app's own clock. `http.js` keeps exactly two native `fetch(` calls (`performApiFetch` and the streaming `apiFetchHeaders`, which never adopts). Contracts: as above.
