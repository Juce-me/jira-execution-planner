## Goal and decision

For a selected sprint named `2026Q4`, treat an Epic label of `2026Q4` or `2026Q4_candidate` (including `2026Q4_Candidate`) as satisfying the selected-sprint-label requirement. Compare whole labels after trimming and case folding; do not accept prefixes or other suffixes. The `_candidate` suffix is a literal label convention, not a new Jira Sprint value. This applies when the Epic's Jira Sprint field is empty as well as when it has a value.

Scope: ENG selected-sprint Epic discovery for active and future sprints. Future-sprint Catch Up uses the existing `Backlog` → `Missing Team` → `Missing Labels` → `Stories Required` order. Active-sprint Catch Up/Planning may discover a candidate-only Epic for Story readiness, but does not gain a Missing Labels category; its existing Stories Required/Waiting/Empty routing remains. The configured mapped Team label remains separately required. Story sprint membership, Team matching, Epic status exclusions, dismissal, and alert filtering keep their existing rules. Do not add a Jira write, configuration field, API endpoint, or separate search path.

## Current implementation and failure

- `epicHasSelectedSprintLabel` and `epicMatchesSelectedSprint` in `frontend/src/backlogAlertSprintUtils.mjs` recognize only the plain sprint-name label. `frontend/src/dashboard.jsx` uses them both to keep an explicitly unsprinted Epic out of Backlog and to decide whether it has a required label. A candidate-only Epic therefore fails the label check and can enter Backlog before Missing Labels is considered.
- The separate `fetch_backlog_epics_for_alert` result in `jira_server.py` omits `labels` entirely. `frontend/src/dashboard.jsx` combines these remote rows with scoped Epic rows before computing the Backlog key set. A remote unsprinted Epic can therefore enter Backlog even with the plain sprint label today. Include labels in that existing response so the shared client predicate can enforce the rule for both sources.
- `fetch_epics_for_empty_alert` in `jira_server.py` discovers Epic-only alert candidates through `add_sprint_label_alternative_to_jql`, whose JQL contains only the plain sprint label. A candidate-only, unsprinted Epic may never reach the client classifier.
- That fetch reads one page with `maxResults: 250` and returns `[]` when Jira search fails. A non-final page or a rejected candidate JQL clause can silently remove matching Epics, and the task route can cache the result as a successful empty alert response. The alert-purpose read needs complete, bounded discovery and must fail instead of publishing partial or failed Epic scope. Keep the ordinary first-screen task fetch on its existing lightweight path.
- `_story_readiness_compute` in `backend/routes/eng_routes.py` also discovers Epics using the Jira Sprint field or the plain label. A candidate-only, unsprinted Epic with a mapped Team label can be absent from the complete readiness snapshot, so removing its Missing Labels warning without widening this query would hide a needed Story requirement.
- The `Missing Labels` subtitle/row note in `frontend/src/eng/EngAlertsPanel.jsx` and the ENG workflow/alert guides describe only the plain label.

Jira Cloud advanced JQL label search is [case insensitive](https://jira.atlassian.com/browse/JRACLOUD-24907); local verification must still compare the returned Epic labels as whole values after case folding. The planned JQL uses the plain and one canonical lowercase `_candidate` value, then tests the requested capitalized form against Jira in the target environment if available.

## Expected behavior

| Epic for selected `2026Q4` | Expected future-planning result |
| --- | --- |
| Empty Jira Sprint, `2026Q4_candidate`, mapped Team label, usable Jira Team | In selected-sprint scope; not Backlog or Missing Labels. If no actionable selected-sprint Story covers the Team, it reaches Stories Required. |
| Empty Jira Sprint, `2026Q4_Candidate`, mapped Team label, usable Jira Team | Same result, regardless of the suffix's case. |
| Empty Jira Sprint, plain `2026Q4`, mapped Team label | Existing behavior is preserved. |
| Empty Jira Sprint, candidate label but missing mapped Team label | Missing Labels, not Backlog; the candidate label only satisfies the sprint-label half. |
| Selected Jira Sprint value but neither accepted sprint label | Missing Labels; a Jira Sprint value alone does not satisfy the required label. |
| Empty Jira Sprint with `2026Q4_candidate_extra`, `2026Q5_candidate`, or no matching label | Existing Backlog behavior. |
| Matching candidate label with missing/unknown Jira Team, but otherwise admitted by the Department's Team-label scope | Existing Missing Team precedence. |
| Both accepted labels on one Epic | One Epic in the first applicable alert, with no duplicate Story requirement. |

For an active sprint, a candidate-only unsprinted Epic can enter the existing complete Story-readiness scan and produce the usual requirement/ghost when its mapped Team has no actionable selected-sprint Story. The candidate label does not create an active-sprint Missing Labels alert. If the selected sprint name is missing, neither label form matches. `2026Q4_candidate` is never interpreted as a sprint name for Story selection or capacity. “Classified exactly once” means the stable result after the alert Epic and readiness responses for the current scope have settled; the existing progressive loading may temporarily show a readiness result before an earlier alert source finishes.
