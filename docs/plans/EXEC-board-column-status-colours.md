# Board Column Status Colours Implementation Plan

> **For agentic workers:** Use `superpowers:executing-plans` (or `superpowers:subagent-driven-development`) to implement this plan task by task. Follow repository publication rules; this plan does not authorize commit, push, or PR creation.

**Status:** Proposed, 2026-10-06; decisions confirmed 2026-10-07 (text colour and filter-bar treatment settled the same day); revised after a three-reviewer validation (backend/storage, pill surfaces, settings/process) and again on 2026-10-07 after a six-reviewer validation (backend/ownership, Settings state machine, pill surfaces and CSS, budgets/docs/process, test feasibility, document consistency), whose findings are applied below; the operator settled the open questions the same day (Decision 1 wording, Decisions 9 and 10). Plan only; no production code written. Tracking issue: #244 ("Inherit colors from board for jira status pills"); the branch is `feature/244-board-column-status-colours` (renamed on 2026-10-07 from `feature/board-column-status-colours`, which had no upstream).

**Goal:** Add a per-Department checkbox in **Settings → Departments → Boards**. When it is on, every ENG Jira status pill whose status is held by one of that Department's Board columns is filled with that column's colour with the same white text the built-in palette pills use. Statuses no column holds keep today's colours. Off by default.

**Architecture:** One boolean, `board.inheritColumnColours`, stored inside the existing shared Department `board` object (same owner, route, validator and save path as the columns). One pure resolver turns `(columns, statusName)` into a colour or `null`; the existing Board filter-option resolver is refactored onto it so the filter popover and the pills share one status-to-colour rule (Board *placement* is a separate rule, Decision 3). A small `StatusColourProvider` (context) is mounted once at the dashboard root and is switched on only for the ENG view with the flag on. The shared `StatusPill` gains an opt-in `status` prop that reads the context and applies an inline `background` and `color`; every in-scope pill passes `status`. `StatusTransitionMenu` and `IssueCard` apply it themselves, so most call sites need no edit. The Settings composer does not use the provider: it passes the same style to its chips directly from its local draft (Decision 9). No new endpoint, request, schema or migration.

**Tech stack:** Python `unittest` (normalizer, routes), Node `node:test` (model, resolver, source guards), existing Playwright mocked dashboard fixtures.

## Decisions (confirmed by the operator 2026-10-07 unless marked)

1. **Scope is every Jira status pill, whatever the issue type.** A Jira status pill is the pill that shows a Jira issue's own status: Epics, Stories, Subtasks and any other issue type that shows one, when the status is held by a column. Tags that only look like pills are out of scope: the alert panel's `.alert-pill.status` is one fixed alert colour that also carries missing fields, assignees and "Postponed", so it is not a Jira status pill even where it shows an Epic's status name (operator 2026-10-07). Surfaces are listed in the inclusion table below.
2. **Match by status name only, never by issue type.** The column map is keyed by Jira status name, so any issue in `In Progress` takes the colour of the column holding `In Progress`. A status the Department did not put in a column (for example a Subtask-only `Analysis`) keeps its current colour until mapped.
3. **Unmapped means untouched.** This differs from Board *placement*, where an unlisted status lands in the first column (`resolveBoardColumnOwner`, `frontend/src/eng/engBoardColumns.js:151`; backend rule in `project_board`, `backend/services/eng_board.py`). The resolver never calls the placement rule.
4. **White text on a solid column-colour fill, exactly like today's pills (operator choice 2026-10-07, after seeing the numbers).** The operator compared three looks in [the approved visual](../../assets/mockups/board-column-status-colours.html) and chose its "Today (white on fill)" column: white text on a solid fill, as today's pills (the mockup's first column only names the colour). This **supersedes the earlier "clearly readable contrast" requirement**: white on the seven enum colours measures grey 3.36, violet 2.94, blue 3.65, teal 2.21, green 2.27, amber 2.20, red 3.27:1, all below WCAG AA's 4.5:1 (the same as today's built-in palette pills, which all set `color: white`, `frontend/src/styles/eng/epics.css:407-442`). The rejected alternatives were solid fill with `#141414` text (5.05 to 8.38:1) and the filter-bar soft tint with dark text (about 12 to 14:1). An inherited pill gets an inline `background` of the column colour and an inline `color: #ffffff`; the white is explicit because a status with no built-in palette class (for example `In Review`) has no text colour rule and would otherwise inherit dark text on a coloured fill. Hover, geometry, padding and radius stay exactly the existing `.task-status` / `button.status-pill` rules. If readability is revisited, the lever is the one `color` literal in `buildStatusStyle` plus the ratio list in this Decision, not the architecture.
5. **Stored as `board.inheritColumnColours`, written only when exactly `true`.** Absent means false. Anything that is not exactly `true` is treated as absent, on the backend and in the frontend helpers alike: a non-boolean value adds a normalizer **warning** (never an error) and the key is omitted, as an unknown colour does. This is the softest failure and deliberately the least work: a hand-edited bad value cannot discard groups or break a Department's strict Board, and Basic mode (being dropped soon) needs no special handling. Operator decision 2026-10-07 ("make as little as possible" for Basic mode).
6. **Out of scope:** dedicated Basic-mode work (it shares the same normalizer, which the pure normalizer tests cover and CI runs in its `JIRA_AUTH_MODE=basic` environment; it gets no Basic-specific cases), EPM, Statistics, per-column opt-out, any colour outside the existing enum, keyboard-only polish (park any finding in `docs/TODO.md` Deferred), the hard-coded Done/Killed card tint and left border on issue cards (`.task-item.status-done` in `frontend/src/styles/eng/issues.css`; a violet "Done" pill will sit on a green-tinted card until a separate decision), and the surfaces in the Excluded table below.
7. **The filter-bar Status popover is left as it is.** It already shows the Board column colour as a soft 28% tint with dark text, independent of any setting (`frontend/src/eng/engFilterOptionVisuals.js`, `filter-bar.css`; pinned by `tests/test_task_filter_menu_compaction_source_guards.js` and `docs/plans/EXEC-eng-filter-option-visuals.md`). The operator said "tint in the filters is ok" (2026-10-07), so that surface keeps its tint in both checkbox states. Every other pill is a solid fill, and the filter popover is the one intentional exception. Its resolver is still shared (see file map) so there is one status-to-colour rule.
8. **No extra permission gate.** The checkbox has exactly the columns' rights: Department board layouts are `authenticated_read` / `user_write` (`backend/security/CONFIGURATION_OWNERSHIP.md:12`), editable by every authenticated user; `userCanEditSettings` gates only the administrator sections.
9. **Composer chips preview the draft with a direct `style`, no nested provider (operator 2026-10-07).** The Settings composer computes `buildStatusStyle(resolveStatusColumnColour(columns, status))` from its local columns and flag and passes it as `style` to its chips, without `status`, so the root provider never touches composer chips and the preview needs no provider semantics of its own.
10. **One implementation commit (operator 2026-10-07).** Source, tests, rebuilt `frontend/dist`, budget manifest and docs land in a single commit, made only when the operator asks for it (this plan authorizes no commit, push or PR). Tasks 2 to 5 and 7 therefore leave `tests.test_codebase_structure_budgets` and the `run.sh` interface check red until Task 6 updates the manifest once, after the last source edit; no per-task commit is made.

## Evidence and boundaries (verified against `main` da17de89, 2026-10-06; re-verified by the 2026-10-07 six-reviewer validation, application code unchanged since)

- `backend/services/group_board.py` `normalize_group_board` runs on every group-config read and builds a new dict, so a key it does not copy is dropped. It already carries one scalar, `doneEpicRetentionDays`, with a presence check (`retention_present`). It is reached from `validate_groups_config` (which prefixes each board error and warning with `Group "X" …`, `backend/services/group_config.py` around `:136`), `_normalize_shared_payload`, `save_shared_groups`, the Basic-mode POST in `backend/routes/settings_routes.py`, and `load_effective_groups`, and directly from `normalize_board` (`backend/services/eng_board.py:131`, which ignores warnings and raises `board_config_invalid` on errors). No allowed-keys list exists for the group `board`; `WorkspaceGroupConfig.payload` is a plain JSON column, so there is no migration and `payload_version` stays 2.
- `frontend/src/settings/groupBoardModel.js` mirrors it: `toStoredBoard` (emits `id, name, statuses, colour, star, min, max` per column, then the retention), `normalizeStoredBoard`, `retentionDaysFromStoredBoard`, `fromStoredBoard` (returns only the composer column array, so the flag needs its own reader helper, as retention has: `inheritColumnColoursFromStoredBoard`, Task 2). `groupConfigUtils.js:188` runs `normalizeStoredBoard` on every config normalization. `BOARD_COLUMN_COLOURS` (the seven-colour enum) is defined here (`:16`); `engBoardColumns.js` and `engFilterOptionVisuals.js` import it from this module, and so will the new resolver. A non-enum colour is coerced to the default grey by `engBoardColumns.js:119` and `projectTrackStats.js:169` but dropped by the filter popover and by the new resolver; the backend validator replaces it with the default and warns, so only mocked fixtures (such as `#ffa940` in `eng_group_board_panel.spec.js`) can carry one.
- `GroupBoardSettings.jsx` keeps retention in `retentionDaysRef` with no UI, re-seeds from `board` only when it arrives from outside (`lastEmittedRef`), and resets on group switch by remount (`key={activeGroupDraft.id}` in `GroupBoardsTab.jsx`). Its own comment (about :142-145) warns about stale closures; `commit()` reads refs.
- Dirty state is a raw `JSON.stringify` comparison (`useTeamGroupSettings.js` `groupDraftSignature`; `groupsConfigConflict.js` `boardDraftIsDirty`). The server returns columns key-sorted (Flask `jsonify`), while `toStoredBoard` emits a different key order, so **any** board edit already leaves the draft dirty after reverting. This change does not alter that: an untouched board emits no flag key and so stays clean (Task 2), and a flag toggle follows the existing board-edit behaviour. The server returns keys alphabetically (`columns`, `doneEpicRetentionDays`, `inheritColumnColours`), which is why the flag is emitted last: it adds no ordering difference of its own.
- A Department with no board starts the composer with zero columns. `deleteColumn` has no last-column guard (`GroupBoardSettings.jsx:442-458`), so deleting the last column commits a present empty board, which `validatePresentGroupBoards` ("A board needs at least one column.") and the backend ("board must have at least 1 column") reject; a flag toggle on an empty composer would commit the same thing, so Task 5 disables the checkbox while there are no columns.
- Strict Board: `normalize_board` and `normalize_measurement_board` ignore unknown keys, so the normalized Board excludes the flag, which is correct and must stay that way (Task 1 asserts `normalize_board` and `snapshot.board` are flag-invariant). The cohort digest and `scope_version` are **not** flag-invariant: the Board route builds them from the raw stored group and the groups revision (`backend/routes/eng_board_routes.py:235-248`, `:391-400`), so they change on every shared-group save, flag or not, by design. A flag save bumps the groups revision, which is workspace-wide (one `workspace_group_configs` row per workspace, `backend/db/models.py`): in-flight Board loads of every Department may get `scope_changed`, the measurement signature changes (`backend/routes/dev_routes.py`, `_signature`), and the Story-readiness cache key embeds the revision (`backend/routes/eng_routes.py:224-247`), so its entries miss and an in-flight readiness request fails with `story_readiness_unavailable`. That is pre-existing behaviour for any shared-group save.
- Pill funnel: `getIssueStatusClassName` → shared `StatusPill`, which spreads `...props` onto both its `<span>` and its `<button>` (`StatusPill.jsx:26,33`), so a new `status` prop would reach the DOM as an attribute unless it is destructured, and a caller `style` can only be merged if it is destructured too. Two marker spans (`StatusTransitionMenu.jsx:226`, `EngBoardView.jsx:1112`) and `EpmRollupTree.jsx:53` are raw `task-status` spans outside `StatusPill`. No `!important` rule in `frontend/src/styles` can beat an inline `background` or `color`, and the palette classes set only `background` and `color` (no border, gradient or image, `epics.css:400-448`); `button.status-pill:hover` only sets `transform`, `filter` and `box-shadow`.
- `App()` renders the provider, so a hook cannot be called inside `renderEpicBlock` or `renderPlanningReviewFieldEditor`; those render functions run above (or in `EngView`, beside) the provider. Putting the hook inside `StatusPill` avoids the problem because the element is mounted below the provider. The app root is one `<div className="container">` (`dashboard.jsx` around :8858) with no ENG-only wrapper; EngView, EngBoardView, EpmView and the Settings modal are siblings inside it. Status menus render through `createPortal` (`IssueFieldOptionMenu.jsx:237`, `EngBoardView.jsx:1089`), which keeps React context, and the app mounts one root (`dashboard.jsx:10848`).
- Ancestor opacity (`.task-item.status-killed` 0.6, `.status-incomplete` 0.8, `.is-dimmed`) and `button:disabled { opacity: .5 }` change how a pill looks on dimmed cards. Inherited pills receive the same dimming as built-in ones; the tests assert computed `background-color` and `color`, never composited appearance.
- The existing settings checkbox is `div.group-preference-row` > `label.group-visible-control` > checkbox + `span`, with an optional `span.group-visible-helper` (`TeamGroupsSettings.jsx:319-348`; `frontend/src/styles/settings/group-editor.css:2-26`). `.group-visible-control` is `inline-flex; white-space: nowrap; min-height: 44px` and keeps the global `label` look (uppercase mono); `.group-visible-helper` is `display: block; white-space: normal`. A bare `label` placed after the composer's inline `.group-modal-meta` span would flow into that text, so the row needs the `.group-preference-row` wrapper. `.board-columns-toolbar` is `justify-content: space-between; flex-wrap: nowrap`, holding Reset and the optional scroll controls.
- **Four coupled size gates.** `tests/test_codebase_structure_budgets.py` holds (a) `LEGACY_ENTRYPOINT_LINE_BUDGETS["frontend/src/dashboard.jsx"]` (10855; the file is 10851, so 4 lines of slack), and (b) `test_extraction_owner_checkpoint`, which reads `scripts/extraction_lint/owner_budgets.json` and requires, for every registered owner and for `dashboard`, `lineCount == actual` (exact) and `lineCeiling >= actual`, plus exact aggregates `settings`, `uniqueOwners` and `appPlusOwners` (32762; the manifest's `transfer.netPhysicalLOC.nextAppPlusOwners` repeats it, but no checker reads that field). Both run in the full Python suite. Two more run only in `scripts/extraction_lint/run.sh` (local; no workflow or test calls it): (c) `check_hook_interfaces.mjs`, which freezes each registered module's sorted `exports` (`exports changed` on any new export, `:449`) and the reviewed input inventory (`GroupBoardSettings`: `board.doneEpicRetentionDays`, `expandedInputCeiling` 17, `sourceDigest` = sha256 of the **whole** file, `:368`), and (d) the eslint `--max-warnings` ratchet, 106 (`run.sh:8`), which the pinned eslint meets with exactly 106 warnings at HEAD, so there is zero headroom (one new unused import fails it). `--write-inventory` (`:430`) writes a whole new unreviewed manifest (`baseSha: REQUIRES_VERIFIED_BASE`) and is not a refresh command. ## Risks

- **Readability.** White text on the seven column colours is below WCAG AA (2.20 to 3.65:1), the same as today's built-in pills; the operator accepted this to keep the familiar look (Decision 4). Teal, green and amber are the weakest. A hard-coded Done card tint can also sit behind a differently coloured Done pill (Decision 6).
- **Recolouring is by status name across issue types** (Decision 2). The helper line next to the checkbox may need to say so.
- **Concurrent edits.** A flag save bumps the whole shared groups revision, so another user's unrelated Department edit can hit the existing 409 banner more often; the existing conflict contract applies. The revision is workspace-wide, so every flag save by any user also changes `scope_version` and the Board cohort digest for every Department (in-flight Board loads get `scope_changed`), the Story-readiness cache key (cache misses; an in-flight readiness request fails with `story_readiness_unavailable`) and the measurement signature. That is pre-existing for any shared-group save, but flag toggles are a new source of it.
- **Stale tab and backend/bundle skew** during deploy cannot be closed server-side (Task 7 note).
- **Concurrent edits to the same pill code (#241).** Re-read the four Board/menu files on the execution branch.
- **Operator-reviewed budget checkpoint.** Approved 2026-10-07 for `dashboard.jsx` and for the touched Settings owner files; the manifest must still be updated to the exact measured values in the same change.
- **A project learning is knowingly overridden for colour only.** "ENG epic-header layout rules must preserve the complete shared `.task-status` presentation" (`AGENTS.md` section 11) is overridden by Decision 4; the Epic header gets no header-specific path, it passes `status=` to the shared `StatusPill`.
- **Python version skew.** Local Python is newer than CI's 3.10 and 3.11; keep new backend lines 3.10-compatible.
