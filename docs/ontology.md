# Project Ontology

Coverage: verified entry points and relationships for Statistics (2026-09-10), ENG Board cross-sprint loading, selector availability, load authority, and operational measurement (2026-09-14), and workspace/catalog ownership and planned persistence contracts (2026-09-14). ## Workspace identity and shared catalogs

Verified on: 2026-09-14 against the merged selector baseline `d9da7bf`. Workspace meaning and sharing were confirmed on 2026-09-13; persistent Sprint and per-Sprint Team storage remains planned, with an implementation-ready contract and unexecuted acceptance tests.

- **Workspace** (domain aliases: Jira identity, Jira site, Jira domain): the Jira site shared by the entity within one configured application environment. All authenticated users resolved to that environment/site belong to the same catalog scope. The canonical implementation key is `RequestAuthContext.workspace_id`, not a user, OAuth connection, token version, or Department. [`Workspace`](../backend/db/models.py) has unique environment/cloud-ID and environment/site-URL indexes; [`stable_local_workspace_id`](../backend/auth/context.py) uses the environment plus cloud ID, falling back to normalized site URL. [`resolve_db_request_auth_context`](../backend/auth/db_context.py) connects authenticated identity to the persisted workspace. Reuse this resolution rather than inventing a new browser-supplied domain key. Different environments or Jira sites remain isolated. Evidence/tests: [`test_auth_context.py`](../tests/test_auth_context.py), [`test_auth_context_db.py`](../tests/test_auth_context_db.py), [`test_db_migrations.py`](../tests/test_db_migrations.py).
- **Workspace catalogs**: shared derived Jira metadata for that workspace. The Sprint catalog belongs to workspace + Jira source Board; per-Sprint Team membership belongs to workspace + Sprint, validated against the effective Board/project/query/Team-field scope; the global Team name directory belongs to the workspace. All users in the same workspace consume the same saved lists. Refreshing user's identity is authentication/audit context, not catalog ownership or a cache partition. A user signing out, reconnecting, or refreshing a token does not erase these shared catalogs. Relationships: consumes workspace Jira configuration and authenticated Jira reads; produces Sprint choices, Team availability, and Team labels. Contract and planned tests: [persistent catalog plan](plans/EXEC-persistent-sprint-team-catalogs.md); current name-directory ownership: [configuration ownership](../backend/security/CONFIGURATION_OWNERSHIP.md).
- **Effective catalog configuration and publication fence** (planned): the [implementation-ready catalog contract](plans/EXEC-persistent-sprint-team-catalogs.md#effective-configuration-and-common-fence) adds `resolve_effective_catalog_config` in `backend/services/workspace_catalog_config.py` (Create). It consumes saved Board/projects/Team field and environment-priority base JQL, preserving revision-zero exact-site fallback. A workspace advisory transaction fence must join current [`update_workspace_config_section`](../backend/services/workspace_dashboard_config.py), [`save_shared_capacity_config`](../backend/services/shared_capacity_config.py), explicit [`promote_legacy_shared_admin_config.main`](../scripts/promote_legacy_shared_admin_config.py), and planned catalog claim/publication. Relationships: configuration determines identity; fenced publication produces complete membership plus atomic directory names. PostgreSQL barrier/race tests are required; neither resolver nor catalog tables exist yet.
- **User authorization and preferences**: credentials authorize upstream requests; private preferences remain user-owned. Sharing these catalogs does not change the ownership of issue payload caches, personal connections, saved private views, or Department configuration. Complete refresh results replace the shared catalog under the plan's lease/completeness rules; this is shared metadata, not a per-reader reconstruction of Jira visibility.

## ENG Board cross-sprint loading

Verified on: 2026-09-12 against the local issue #190 follow-up implementation on `bugfix/board-progressive-loading`, from baseline `40bffe7`; the implementation is local and unpublished. Ownership is described as implementation responsibility, not an undocumented team assignment.

- **ENG Board** (UI aliases: Board, Kanban): Epic columns rendered by [`EngBoardView`](../frontend/src/eng/EngBoardView.jsx). Contract: [ENG workflows](features/eng-workflows.md#board-kanban). Ordinary Sprint mode consumes the already-loaded Catch Up snapshot through [`dashboard.jsx`](../frontend/src/dashboard.jsx); only cross-sprint Component/All work uses the strict owner. All ENG work waits for a non-empty Sprint catalog; a saved Sprint label is display-only until that catalog validates it. Once the shared selector is usable, cross-sprint selection is independent of load readiness. Loading still depends on server capability, accepted Department Board configuration, and persisted Jira authority from saved selected projects or a saved Jira source Board. Backend capture resolves and access-checks the saved authority. Tests: [`eng_group_board_view.spec.js`](../tests/ui/eng_group_board_view.spec.js), [`test_eng_board_routes.py`](../tests/test_eng_board_routes.py), [`test_eng_board_service.py`](../tests/test_eng_board_service.py).
- **Sprint catalog**: quarterly Sprint values returned by `GET /api/sprints` in [`settings_routes.py`](../backend/routes/settings_routes.py). Basic mode keeps the existing file cache; OAuth mode uses `SPRINTS_PROCESS_CACHE`, keyed by the authenticated Jira/Home cache partition and saved Jira Board, for 24 hours. Cache misses use [`fetch_sprints_from_jira`](../backend/services/sprints.py); empty or failed catalogs keep ENG data gated. Auth/config invalidation clears the process cache. Tests: [`test_oauth_stats_routes.py`](../tests/test_oauth_stats_routes.py), [`test_cache_partitioning.py`](../tests/test_cache_partitioning.py), [`eng_group_board_view.spec.js`](../tests/ui/eng_group_board_view.spec.js). Reviewed 2026-09-14 at `d9da7bf`; the [persistent catalog plan](plans/EXEC-persistent-sprint-team-catalogs.md) is implementation-ready with explicit server-produced browser identity, display-only restoration, validated empty replacement, generation suppression and bounded same-attempt completion reads. These are planned contracts, not implemented behavior. The current user-partitioned Sprint process cache remains the DB migration source; Basic file storage and allowed local/dev OAuth compatibility retain their own server behavior.
- **Team name directory and Sprint discovery** (verified 2026-09-14): `GET/POST /api/team-catalog` in [`settings_routes.py`](../backend/routes/settings_routes.py) delegates DB names to `load_workspace_team_catalog` / `save_workspace_team_catalog` in [`workspace_dashboard_config.py`](../backend/services/workspace_dashboard_config.py), backed by `WorkspaceTeamCatalog` in [`models.py`](../backend/db/models.py). Ownership: workspace-shared derived names per [configuration ownership](../backend/security/CONFIGURATION_OWNERSHIP.md). Current `get_teams` in [`eng_routes.py`](../backend/routes/eng_routes.py) discovers Teams from issues; `all=true` also unions global registry results and can fall back beyond the selected Sprint. Settings `loadTeamCatalog`, `fetchAllTeamsFromJira` and `resolveMissingTeamNames` in [`dashboard.jsx`](../frontend/src/dashboard.jsx) currently conflate names and availability. Tests: [`test_team_catalog_api.py`](../tests/test_team_catalog_api.py), [`test_oauth_stats_routes.py`](../tests/test_oauth_stats_routes.py). The [persistent catalog plan](plans/EXEC-persistent-sprint-team-catalogs.md) proposes separating these concepts; no per-Sprint membership table exists yet.
- **Component scope**: exact Department `missingInfoComponents` matched on Epic Components, across sprints. [`iter_strict_search_pages`](../backend/services/eng_board.py) validates each Jira page; [`iter_component_epic_batches`](../backend/services/eng_board.py) produces cumulative validated membership and a final marker consumed by [`_frame_stream`](../backend/routes/eng_board_routes.py). Candidate delivery is page-progressive but bounded/coalesced on the wire. Tests: [`test_eng_board_progressive_loading.py`](../tests/test_eng_board_progressive_loading.py), [`eng_board_progressive_loading.spec.js`](../tests/ui/eng_board_progressive_loading.spec.js).
- **All work scope**: union of Component Epics and eligible parents of Department-Team work. [`iter_team_epic_batches`](../backend/services/eng_board.py) preserves the 10,000-row scan bound, filters parent keys in batches, and applies the 1,000-Epic ceiling only to admitted membership; [`discover_team_epics`](../backend/services/eng_board.py) remains the collecting compatibility wrapper. Depends on captured projects, issue types, parent-owned status/retention and strict paging. Tests: [`test_eng_board_service.py`](../tests/test_eng_board_service.py), [`test_eng_board_progressive_loading.py`](../tests/test_eng_board_progressive_loading.py).
- **Strict Board stream**: OAuth-backed `GET /api/eng/board`, [`get_eng_board` / `_frame_stream`](../backend/routes/eng_board_routes.py). Produces protocol-v1 start/index/progress/column/terminal frames. Its route-local candidate policy allocates at most 8 MiB to optional cumulative candidate lines and keeps a 1 KiB terminal reserve inside the unchanged 32 MiB generation limit. [`EngBoardStreamWriter.prepare` / `write`](../backend/services/eng_board_stream.py) provide atomic validation, encoding and sequence admission; [`EngBoardRequestTransport`](../backend/services/eng_board_stream.py) and [`EngBoardChildScheduler`](../backend/services/eng_board_stream.py) retain request-local deadlines and two-child-worker ownership. Tests: [`test_eng_board_routes.py`](../tests/test_eng_board_routes.py), [`test_eng_board_stream.py`](../tests/test_eng_board_stream.py), [`test_eng_board_progressive_loading.py`](../tests/test_eng_board_progressive_loading.py).
- **Board data owner and authority**: [`createEngBoardDataOwner` / `engBoardDataReducer`](../frontend/src/eng/useEngBoardData.js) consume validated frames from [`consumeEngBoardResponse`](../frontend/src/api/engBoardApi.js), preserve generation/scope partitions and cache only completed snapshots. [`useStrictEngBoardPresentation`](../frontend/src/eng/useStrictEngBoardIntegration.js) consumes [`buildStrictEngBoardViewModel`](../frontend/src/eng/engBoardViewModel.js); child authority controls facets and Work items export. Tests: [`test_eng_board_data.js`](../tests/test_eng_board_data.js), [`test_eng_board_stream.js`](../tests/test_eng_board_stream.js), [`test_strict_eng_board_integration.js`](../tests/test_strict_eng_board_integration.js).
- **Board load measurement**: [`createBoardLoadMeasurement`](../frontend/src/eng/loadPerformance.js) is created by the strict owner and consumes optional frame/terminal observations without blocking synchronous reduction. [`load_performance.py`](../backend/services/load_performance.py) validates, persists, and filters Component and All work observations with a null Sprint; these operational records remain outside GA4. Retired or superseded measurements cannot publish late samples. Existing `firstFocusedContentMs` still follows a completed focused column; the joined synthetic campaign measures first visible `.ecard` paint separately in [`eng_board_progressive_loading.spec.js`](../tests/ui/eng_board_progressive_loading.spec.js). Tests: [`test_load_performance.py`](../tests/test_load_performance.py), [`test_load_performance.js`](../tests/test_load_performance.js), [`load_performance.spec.js`](../tests/ui/load_performance.spec.js), [`test_eng_board_data.js`](../tests/test_eng_board_data.js); privacy contract: [analytics](README_ANALYTICS.md). Current evidence is synthetic and test-based; authenticated live first-Epic timing, proxy buffering and the reported production failure's exact bound remain unknown.

## ENG shared Sprint selector and Board load authority

Verified on: 2026-09-14 against `renderSprintControl`, the readiness resolvers, both data owners, backend capture, and the acceptance matrix.

- **Shared Sprint selector** (UI label: Sprint): `renderSprintControl` in [`dashboard.jsx`](../frontend/src/dashboard.jsx) consumes the ordinary `selectedSprint`/`sprintName` identity, validated Sprint catalog, and transient `boardStrictScope`. It is shared by Catch Up, Planning, Board, Statistics and Scenario. Native option buttons inside a listbox support pointer and keyboard commitment; the ordinary identity remains persisted while Component/All work is transient. `boardScopeRequested` records selected intent, while `selectedScopeReadiness` decides whether Board shows loading/setup/error or may activate the strict owner. Relationships: ordinary Board consumes the Catch Up snapshot; an explicit Project Track Statistics Sprint commitment synchronizes its start/end source range and forces exactly one current source-only POST even when the matching range/per-Sprint cache is warm. Reselecting the current ordinary Sprint repairs a divergent range once; an already matching reselect is a no-op. Task-backed Statistics retains the task owner; Scenario compute stays explicit; cross-sprint scopes consume the strict owner only when ready. Tests: [`eng_group_board_view.spec.js`](../tests/ui/eng_group_board_view.spec.js). Completed plan and residual live gaps: [selector availability](plans/DONE-eng-board-scope-selector-availability.md). The [implementation-ready catalog amendment](plans/EXEC-persistent-sprint-team-catalogs.md#browser-authority-and-refresh-completion) will change only catalog validation/completion inputs through `dashboardRuntime.js` and `dashboard.jsx`; it preserves this selected-intent/load-authority split. Acceptance must rerun all five modes and readiness cases with fresh/stale/pending/failed/empty/changed-Board/delayed/auth-locked DB responses, including zero ordinary fallback under blocked Component/All work intent.
- **Board scope load authority**: `loadConfig` and `loadGroupsConfig` in [`dashboard.jsx`](../frontend/src/dashboard.jsx) produce independently generation-guarded accepted configuration states. A Board-affecting Settings save invalidates the applicable config/group read generations and holds a transaction fence from the first mutation through the designated post-save config acceptance, so pre-save and in-save reads cannot restore stale authority; successful authoritative group-save responses retain their existing acceptance role. `acceptedStrictBoardRevision` combines accepted workspace authority with Department revision/content for strict-owner invalidation. Readiness requires capability, a current accepted read, saved Jira projects or source Board, Department columns, and scope membership; unsaved Settings drafts cannot grant or revoke it. `strictBoardOwnerActive` alone activates `useStrictEngBoardOwner`; requested-but-blocked scopes suppress ordinary fallback. Final enforcement remains `_resolve_projects` / `_capture_shape` in [`eng_board_routes.py`](../backend/routes/eng_board_routes.py). Department Board columns are not Jira source-Board authority. Live saved-authority provenance and positive authenticated cross-sprint loading remain unverified; no backend-defect or widened-authority claim is made.
