# Planning capacity prefill across work configurations

> **Status:** Planned; implementation and live-cause confirmation outstanding. Independent of the unfinished historical capacity-editing plan. This contract supersedes that plan's removed read-status panel and Retry-button requirements, including its prop inventory.

## Outcome and current accuracy

The 2027Q1 Team capacity editor should offer the uniquely identified earlier Sprint's raw Jira capacity even when that Sprint belongs to the Legacy work configuration. This plan has not been executed. The localhost example shows a blank Distribution editor and a 2026Q4 display capacity of 27; the displayed value may include a Product/Tech share, so it does not establish the raw prefill value. Do not claim a live cause or raw value until measured.

## Evidence and diagnosis

- `frontend/src/dashboard.jsx` passes `sprintCatalogState.availableSprints` to `PlanningTeamCapacityCards`; `frontend/src/dashboardRuntime.js` replaces that list with the current configuration's accepted catalog. `backend/routes/settings_routes.py` applies `in_range_sprints` to configuration-scoped reads, including completion. A 2027-only DELIVERY catalog cannot contain 2026Q4 from Legacy. `previousPlanningCapacitySprint` cannot select a row it never receives. This is a code-proven failure mode, not yet proof of the specific localhost request path.
- The existing `tests/ui/planning_assignee_capacity.spec.js` prefill fixture supplies both quarters in one catalog and stubs Jira capacity independently of JQL. The new utility test proves the normalized request string only. Neither establishes cross-configuration or real Jira search behavior.
- `previousPlanningCapacityValue` rejects duplicate normalized names only among displayed cards. The backend normalizes ticket names before returning them, losing prefix provenance; two configured Teams with the same normalized name cannot safely be distinguished by preferring a raw prefix.
- Before implementing, reproduce with sanitized, transient observations: record whether opening the editor starts a prior-capacity GET, its source quarter, HTTP outcome, count of exact candidate issues, and whether the current stored value is own or inherited. Compare the loaded current and sibling catalog membership/authority. Never persist raw payloads, Team names, Sprint ids, Jira keys, credentials, or live screenshots. If the observation disproves the catalog hypothesis, update this plan and target the observed cause rather than claiming it was confirmed.

## Contract

1. On explicit editor open, preserve an own `user` or `jira` stored value; do not replace it with a previous Sprint. For an absent or inherited value, resolve earlier quarter candidates across the current and relevant earlier work configurations, including Legacy when 2027 DELIVERY is selected. Jira-editor blank/zero prefill keeps its existing expected-capacity conflict baseline. This is a read-only suggestion: opening, canceling, or resolving it never writes Jira or application data.
2. Reuse the existing configuration-stamped `fetchSprints` catalog read and its validation/completion lifecycle. On edit, acquire validated rows for each earlier configuration that can contain an earlier quarter; retain the current configuration's validated rows. There are at most the configured Legacy and DELIVERY sources. Do not initiate a force refresh or add startup requests. Honor existing cache identity, browser context, catalog version, configuration revision, completion and authentication rules; a mere HTTP 200 or a partial/pending source is not authority. Do not change the selected Sprint, work context, or review namespace. The Settings `sprint-values` endpoint is not a substitute for full, identity-stamped Sprint rows: it coalesces names and lacks per-row start dates.
3. Combine validated rows only for this lookup, respecting each configuration's quarter range. Deduplicate the same physical Sprint id only if its name, state and date agree; conflicting identity or duplicate equally ranked quarter/date candidates fail closed. Preserve the existing ordering: exactly one earlier active Sprint wins; otherwise choose the nearest earlier quarter and latest start date; tied candidates fail closed. Never select the current or a later quarter. If a relevant catalog is unavailable, incomplete, stale or ambiguous, retain the existing stored draft, allow manual entry, and show a retryable previous-capacity message instead of treating unknown as no ticket. Abort or fence both catalog and capacity reads on cancel, unmount, editor replacement, configuration, Sprint or Team change; late responses must not overwrite typing.
4. Establish uniqueness against the active Department's complete saved Team membership plus any additional distinct Team identities admitted to its Planning scope, not only visible cards. The merge-only workspace name directory is a name resolver, not a membership list: it contains re-keyed Legacy/DELIVERY ids with identical names, so counting every directory entry would incorrectly suppress valid Teams. Resolve membership and names from existing authoritative sources and fail closed if they are incomplete or distinct admitted ids normalize alike; deduplicate repeated references to the same id. Do not infer equivalence from a name. If the source Team's identity across eras is unprovable, retain the draft and document the limitation; an identity-mapping policy needs a separate operator decision. Keep exact matching and reject multiple Jira issue candidates; preserve numeric zero and full raw precision until the existing editor formatting. The existing response strips original prefixes. Verify Jira phrase-search behavior for prefixed and unprefixed titles with a controlled read or authoritative endpoint evidence. If both forms cannot be found and distinguished safely, stop that search-contract change for a separately reviewed design specifying request bounds, identity/provenance, pagination and partial-failure semantics; report this acceptance criterion unverified and do not claim the plan complete. Do not silently choose between candidates.
5. Keep the existing refresh icon available only when capacity is enabled, including compact mode. Make stale/error recovery identifiable to a sighted touch user using visible copy that identifies the icon or a compact visible label. Preserve the existing Planning action/icon button kind, registered layout hook, foundation hover/focus tokens, loading accessible name and busy state. Guard duplicate activation from the first click through settlement, including same-turn activations. Update `docs/design-system.md`, `docs/README_ANALYTICS.md` and the feature documentation to describe the actual control and its no-new-event rationale; existing `jira_team_capacity` `api_result` covers the capacity read. Review any new catalog read for its existing telemetry contract without sending identifiers.
