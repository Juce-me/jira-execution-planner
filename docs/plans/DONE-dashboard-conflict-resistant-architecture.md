**Goal:** Stop unrelated branches from being forced to resolve conflicts, and make a feature edit local to its own module. Track A removes the shared files every PR must edit and that cannot be merged by hand. Track B reshapes `frontend/src/dashboard.jsx` so a feature PR no longer edits it in many places.

**Architecture:** Track A runs first because the measurements below put most conflict volume there: committed generated output (`frontend/dist`), exact line-count registries, and append-style docs. Replayed over the 35-merge window, A1 to A3 take conflicted sync merges from 25 to 15 (43%); about 11 (31%) is reachable only with ontology and GATE-stamp conventions that cannot be replayed. Plan docs, tests, the ontology and `docs/postmortem/README.md` keep conflicting and are named residuals, not claimed fixes. Track B is the dashboard decomposition, built on the handle pattern the repo already uses for Scenario and the mutation and scope hooks (one `use<Feature>()` hook returns one handle; `App()` stops destructuring and re-listing names; Stats becomes a handle in B1). A data-only slice descriptor handles the per-group persisted keys, and only after a spike proves it. `App()` stays the always-mounted host; no React context and no external store.

**Tech Stack:** Node 20 (`node --test`, esbuild 0.27), Python 3.10+ `unittest`, bash, git 2.43 or newer for the measurement script, Playwright (Chromium). No new dependency.

**Spec:** this document. [Evidence](#evidence) is the rationale. Supporting analyses were five independent read-only reports on 2026-10-26 (merge simulation, `App()` structure map, choke-point inventory, Track A specification, Track B design), two review reports on R1 and four on R2 (dist and startup; registries, docs and sync; the conflict evidence; Track B and render cost); scratch output is outside the repository and every figure used here is reproduced in this file.

## Global Constraints

- Behavior-preserving. No API request, response, route, storage or analytics change. Analytics allowlist reason: Track A is tooling, configuration and docs; Track B is a pure refactor with unchanged canonical events and typed params. The one behavior change is isolated in Task B0a, a separate bugfix PR before Track B that closes two latent save-trigger gaps (D-9c); every refactor PR after it preserves behavior.
- No new runtime dependency and no new GitHub Actions job. Do not add a CI job for `tests/ui` (recorded decision in `AGENTS.md` section 10).
- `AGENTS.md` section 10 applies to every task: dedicated branch from fetched `origin/main` with zero inherited commits, atomic commits, full unittest and full Chromium `tests/ui` run before push, explicit user confirmation, and the publication transaction (MRT025). This plan waives none of it. The zero-inherited-commits rule applies to each publication group, not to the local chain. At about 8 minutes per UI run, budget one per task commit group while executing locally and one per publication group before push.
- Commit and merge with the noreply identity through one-shot `-c user.name=... -c user.email=...` flags, never the clone's configured address, and never edit git config files. Verify with `git log -3 --format='%h %an <%ae>'` before any push.
- Do not hand-edit `frontend/dist/`. Until Task A1 lands, rebuild it with `npm run build` and commit it. After A1 it is untracked build output, and every command that reads it (unit tests that read dist, `tests/ui`, local server runs) is preceded by `npm run build` in the same checkout.
- Track B keeps hook call order and effect order unchanged except where a phase's Files record lists an explicit effect-edit allowance (B2's scope effect, B4's ui-prefs effect). Persisted per-group state stays in `App()`; moving it into a component that can unmount is forbidden (`applyGroupState` writes it on every group switch).
- Every Track B phase keeps: cold-load request set unchanged, reopening Statistics adds zero requests, chart hover does not re-render `App()`, sticky layering untouched (MRT009), no fetch unification (MRT010). These are proven only by tests that actually run: the render-count and hover specs in `tests/ui/codebase_structure_smoke.spec.js` skip unless `JEP_RUNTIME_PROBE=1` (the bundle for them is built only under that variable; re-locate the lines with `rg -n JEP_RUNTIME_PROBE`). Every Track B phase command sets `JEP_RUNTIME_PROBE=1` and checks with `--list` that the named specs are selected, not skipped. Other specs in that file (22 sites with `useCommittedDist: true`, including cold-load and reopen) read `frontend/dist/dashboard.js` from disk, so after A1 a phase command also builds first and the freshness check in A1 must pass; otherwise "reopen adds zero requests" can pass on an old bundle.
- Rule changes land only in `AGENTS.md` sections 10 and 11 (template updates overwrite everything else), in `docs/plans/AGENTS.md` and in `docs/ontology.md`, and only after the approval recorded in D-5.
- Docs are first-class deliverables: each task updates the docs named in its Files list in the same commit as the change. Before each commit, `git diff --name-status` is compared with the task's Files and any divergence is recorded in this plan (MRT016).
- Never commit secrets, absolute local paths, real emails or real Jira keys. No agent attribution in commits or PRs.

## Review Focus

Failure modes the tasks do not otherwise exercise, most likely first. Each has an owning test.

1. A fresh clone, an old worktree or a pulled branch has no or a stale `frontend/dist` after Task A1, and the server serves assets with a generic 404 (MRT007 is the same failure mode). Owner: A1 `frontend_build_missing` and `frontend_build_stale` unit tests, the preflight check and a startup warning in `python jira_server.py`; gunicorn relies on the preflight alone.
2. The container image and the release zip have `frontend/dist` but no `frontend/src` and no `package-lock.json`; a build check that stats sources crashes the entrypoint preflight (`set -eu`, only `PreflightError` is caught). Owner: A1 dist-only-layout unit tests plus a preflight run in that layout.
3. After A1 the UI tests and Track B's `useCommittedDist` specs read a build output that nothing keeps fresh, so a gate can pass on an old bundle. Owner: A1 freshness gate and the build-first commands.
4. An open branch that modified `frontend/dist` hits a modify/delete or rename conflict on its first sync past A1, the merge leaves untouched dist files deleted, and a branch without `.gitattributes` misses `merge=union` on the first sync past A3. Owner: A4 tests for each path.
5. `merge=union` silently keeps both versions of a bullet, a plan link or a table row edited on both sides. Owner: A3 `tests/test_agents_md_learnings.py` (bullets, plan links, analytics rows, conflict markers).
6. The sync script commits with the personal email (automatic path, the conflict path, or through exported `GIT_AUTHOR_*`), auto-commits an unreviewed rerere resolution, or takes the clean path when git aborted the merge. Owner: A4 author, env-override, abort and `--continue` tests and the no-autoupdate rule.
7. Derived budgets stop auto-ratcheting down, so an owner file can grow up to its headroom unnoticed, or a hook edit no longer reopens its review. Owner: A2 tests pin exact failing and passing line counts and a changed-hook-source digest control; the `dashboard.jsx` ceiling stays exact.
8. A group switch (A, then B, then A) restores different state after a slice extraction, including the lone `showAlertsPanel` toggle, or the saved-preferences object silently loses a key. Owner: B0b asserting spec, the frozen 62-key preference check and B4 golden tests; hook order by `check_move_conservation`.
9. A handle is missing a name a consumer destructures, or an unstable handle (or a handle passed into a derived hook) is used as a dependency and recomputes models every render, and lint cannot see it. Owner: handle contract tests in B1 to B3 and the B0b AST guard run over every file that receives a handle.
10. A gate that cannot fail: the App render counter counts only the `App()` body, so an effect that runs every render passes. Owner: B0b snapshot-effect execution counter and `Storage.setItem` spy.
