## Issue

#267: "inherit planning table view (and epic level custom values) from the current sprint to the future sprint. when during the planning a table was created in the active sprint, inherit it to the following future sprint. when table is modified in the future sprint, keep it as main for the current future sprint."

## Direction (operator, 2026-10-17 to 2026-10-19)

- Custom columns belong to the Department group and are available in every Sprint for that group; they are not Sprint-scoped.
- An Epic is a cross-Sprint entity, so a custom value belongs to the issue and is the same in every Sprint (one value per issue, per group).
- The view (column order and hidden columns) stays per Sprint, is shared across users of the group, and is preserved for earlier Sprints. A Sprint that has not saved a view inherits one; the first layout saved in it makes that Sprint's view its own. A user who opens a Sprint sees the view it inherits (the nearest earlier saved view, see View resolution), changes it, saves on top, and everyone sees the result.
- A small dismissible hint shows where an inherited view came from.
- Hide (this Sprint's view, separately for the Epic view and the Story view) and Archive (every Sprint) stay two separate verbs; Archive gets a clear warning.
- Column order is kept, including for columns added later.
- Stories are Sprint entities and Epics are cross-Sprint. A Story number column that sums is shown on Epic rows as the read-only sum of the Epic's Stories, marked with a superscript "S"; an Epic column is shown on every Story row as the parent Epic's value, read-only, marked with a superscript "E". Never the reverse. Both are automatic, visible by default, and by default the last column of the other view. The rollup exists only while the Story column's total ("Show total") is on (confirmed 2026-10-19).
- Existing per-Sprint tables should not leave two permanent column sources; every configured Department group gets its own copy of the saved data, rolled out in a quiesced cutover.
- Sprints are ordered by numeric Sprint id, because ids only increase and Sprint names can be anything, not only quarters. Duplicating a group does not copy its review columns. Re-creating a group with a deleted group's id reattaches the old data; this was reaffirmed on 2026-10-19 with the real trigger (ids are creation-slot slugs, see Current State).

## Goals

- Columns and values added for a Department group appear in every Sprint for that group, and a value entered in any Sprint is the issue's value everywhere in that group.
- A Sprint with no saved view shows the nearest earlier Sprint's saved view; the first layout saved in it gives it its own view; earlier Sprints' views never change because of a later Sprint.
- A column added anywhere keeps a sensible position in every saved view.
- A Story number column rolls up into the Epic rows and an Epic column is inherited by its Stories, both read-only and without storing anything.
- No extra Jira requests, no catalog read, and a small, stated, bounded database cost.

## Non-Goals

- Copying columns or values between groups; duplicating a group does not copy its columns. Purging a group's review data when the group is deleted.
- Matching renamed, cloned or moved Epics by anything other than the immutable Jira issue id.
- Per-user views or per-user columns; any change to Jira-owned fields.
- Rewriting existing per-Sprint review rows in the application; a reset, choose-source or delete-view action for views.
- Cross-Sprint Epic totals (they would need Stories outside the table's scope); a Story overriding an inherited Epic value; storing any derived value.

## Anti-Goals

- Saving a view in one Sprint must never change another Sprint's saved view or the view an earlier Sprint displays.
- A read must never create or modify rows; a PATCH without changes must not create a row or take a lock.
- Archive must never be reachable without a warning that it affects every Sprint for the group.
- Application code never copies or shares a column between groups; the one-time adoption copies legacy columns into each group as independent data, and a group re-created with a deleted group's id is the same group id.
- A draft built for one group must never be saved under another.
- A derived cell must never show a partial or stale value as if it were complete.

## Design

### What lives where

| Thing | Scope | Shared with | Stored in |
| --- | --- | --- | --- |
| Column definitions (label, type, aggregation, archived, default order, creation anchor) | Workspace + Department group | Every authenticated user | New group schema table |
| Cell values | Workspace + group + issue | Every authenticated user, subject to per-issue Jira authorization | New group cells table |
| Views (column `order`, `hidden`; per row kind) | Workspace + group + Sprint | Every authenticated user | New Sprint view table |
| Totals (`aggregation`) | Column property, so group-wide | Same as columns | Group schema table |
| Derived columns (Story sum on Epic rows, Epic value on Story rows) | Computed in the client from loaded cells | Not stored | Nothing |
| Hint dismissal | One browser | Nobody | Dashboard preference state |

Column ids are the lineage: a column keeps one immutable UUID, and a saved view refers to it by id. The group id is the storage key and is stable on rename.

### Storage

Three new tables, one Alembic revision after `20261001_0018_review_layouts.py` (verified head). Names are provisional until the `EXEC-*` plan; types follow the existing review models.

- **Group schema** (`workspace_group_review_schemas`): `id` Uuid primary key; `workspace_id` FK to `workspaces` with `ON DELETE CASCADE`; `group_id` `String(128)`; `schema_revision` (check `>= 0`); `columns` JSON; unique `(workspace_id, group_id)`.
- **Group cells** (`group_review_cells`): `id` Uuid primary key; `schema_id` FK to the group schema row with `ON DELETE CASCADE`; `issue_id`, `row_kind` (check `epic` or `story`), `column_id`, `value` (`String(500)`, nullable), `revision` (check `>= 1`); unique `(schema_id, issue_id, row_kind, column_id)`. The same cell shape as today, one value per issue.
- **Sprint view** (`group_sprint_review_views`): `id` Uuid primary key; `workspace_id` FK with `ON DELETE CASCADE`; `group_id` `String(128)`; `sprint_id` `String(128)`; `sprint_order` `String(128)` with `CHECK (length(sprint_order) = 128)` (the decimal id left-padded with zeros, so string order equals numeric order with no cast; one shared padding helper serves the route and the adoption script); `layouts` JSON; `view_revision` (check `>= 1`, so 0 always means "no row"); unique `(workspace_id, group_id, sprint_id)` and an index on `(workspace_id, group_id, sprint_order)`.

The existing `workspace_sprint_reviews` and `sprint_review_cells` stay in the database untouched and are no longer read by the application after cutover; they hold no user columns. Downgrade drops only the three new tables, and with them everything entered since cutover. The parity tests assert the foreign keys' `ON DELETE`, the checks, nullability and indexes, not only column names and unique constraints, and an offline PostgreSQL SQL render test (as in `tests/test_db_migrations.py`) asserts the `CREATE TABLE`, cascade, checks and index.

### View resolution (server only)

For group G and Sprint S, one lookup: `sprint_order <= :S ORDER BY sprint_order DESC LIMIT 1` over G's view rows. An equal match is S's own view (`inheritedFrom: null`); a lesser one is the nearest earlier view (`inheritedFrom: {sprintId, viewRevision}`); none means no view, and the response omits `layouts` keys so the table model's default arrangement applies. It never writes.

- Ties cannot occur: the numeric-id regex forbids leading zeros and `(workspace_id, group_id, sprint_id)` is unique.
- A saved view is a row with at least one row kind. A row kind absent from `layouts` is absent, never stored as `{order:[],hidden:[]}`, because the table reads `hidden ?? DEFAULT_REVIEW_HIDDEN_COLUMNS` and empty arrays would unhide Component, Project, Capacity and Project Track. Inheritance is whole-row: a Sprint whose own row holds only one row kind shows the default arrangement for the other kind, not an inherited one, so any layout save freezes both kinds.
- Sprint ids are not checked against the catalog, so a group is capped at a fixed number of view rows (the `EXEC-*` plan pins it; recommended 500) and a save beyond it returns `400 review_view_limit` with client copy "This group has reached its limit of saved Sprint views." The risk is accepted in writing: any authenticated user can fill the cap with arbitrary numeric ids, a junk row with a low id is inherited by every unsaved real Sprint, and there is no delete-view action, so the plan carries an operator purge runbook.

**Decision (accepted 2026-10-18, inferred from the operator's answer on numeric ordering; a one-function change if reversed): an unsaved Sprint shows the nearest earlier saved view, not the latest saved view overall.** The latest-saved rule would change an earlier Sprint's displayed view: with Sprint A active and unsaved, a layout saved in Sprint B would make A suddenly show B's view, contradicting "previous views are preserved".

**Decision (confirmed 2026-10-18): order Sprints by numeric Sprint id**, with no catalog read. Ids only increase and Sprint names are not limited to quarters, so the rule needs no naming convention. Known limits, recorded and not fixed: a Sprint created out of chronological order, or a Sprint renamed or reused out of order, can inherit a later Sprint's view; the catalog's one-entry-per-name winner can change a quarter's id (future to active) and orphan its saved view, as today; a Board switch interleaves ids; an orphaned or deleted source makes the hint fall back to "an earlier Sprint"; there is no reset, choose-source or delete-view, so correcting a wrong inheritance means rearranging and saving, which then freezes that Sprint's view; and the hint can be dismissed. The hint makes the source visible.

### Column order

- A saved view stores the full order of built-in and custom columns, as today.
- `add` carries an optional `after` inside its `column` object (added to the strict key list): `null` means append, `'summary'` means directly after the pinned columns (what the boundary "+" and `insertColumnId` already use), or an id. A valid id is a same-kind built-in id or a same-kind group column id, archived ones included, including a column added earlier in the same request; anything else is rejected and the stored string is bounded. A missing `after` (legacy or adopted columns) reads as `null`.
- The client never sends a derived column's id. A boundary "+" after a derived column sends the nearest preceding same-kind column id (built-in or custom), else `'summary'`; the corner and touch "+" send the id of the last same-kind native column, or `'summary'` when there is none, so a new column lands ahead of any derived columns in the creating Sprint exactly as it does elsewhere.
- Placement is computed by the client in `buildPlanningReviewColumns`, not stored. It runs on the unfiltered column list (as `layoutColumns` does) and filters for admission afterwards, so an anchor on an admission-gated built-in such as `project` or `teamsInScope` still resolves. Start from the view's saved `order` (empty for the default arrangement) plus any built-ins missing from it in their default sequence; fold the viewed row kind's own custom columns missing from that base, archived ones included so chains resolve, in creation order (the `order` field; the UI never emits `reorder`), each through `insertColumnId(base, id, after)`; an absent anchor lands at the end. Derived columns missing from the order are appended after that fold, in creation order. Hidden is unaffected, and a new column is visible unless the view lists it as hidden. A saved layout freezes derived ids into `order` at their current positions (`movableIds()` includes them), which stays consistent because new native columns anchor to a native id.
- Adding a column in the UI also saves a layout in the creating Sprint (existing behavior), so that Sprint gets its own view with the column at the chosen position. This matches the issue: a future Sprint that is edited becomes the main one. Other Sprints' saved views lack the column and place it by the fold. The group's default order among custom columns (`order`, `reorder`) is unchanged.
- **Decision (my call, confirm):** this is the author's reading of "keep the order of the columns".

### Story relations (derived columns)

Stories belong to Sprints and Epics span them, so the two kinds are related by two read-only display rules and nothing else. A derived column is computed in the client from cells that are already loaded; it adds no storage, no column kind, no endpoint and no read.

- **Up (Story to Epic).** A Story-kind number column with `aggregation: 'sum'` also appears in the Epic view. The coupling is deliberate (confirmed 2026-10-19): a column's total setting means it is summable, so turning "Show total" off removes the rollup in every Sprint's Epic view, and because number columns default to a sum, a rating-style Story column needs its total switched off. An Epic row shows the sum of that column over the Epic's Stories in the current scope (the Sprint and the current filters, the same `children` that feed "Sprint SP"). The cell is blank until every in-scope Story's cells are loaded and none is unavailable (Epic batches load before Story batches and `unavailableIssueIds` are dropped), and blank when no in-scope Story has a stored value, so adding a column does not flood Epic rows with 0; otherwise a blank Story value counts as 0. Story text columns and non-sum Story columns do not appear in the Epic view.
- **Down (Epic to Story).** Every Epic-kind column, number or text, also appears in the Story view. A Story row shows the parent Epic's value, found through `epicIssueId`, a new field set in `buildPlanningReviewRows` from the Epic group's issue id (Story rows carry only `epicKey` today). The table builds the other mode's rows from its `epicGroups` and `visibleTasks` props, so `dashboard.jsx` does not grow. The cell is blank until the Epic's cells are loaded and the Epic is not unavailable (the existing availability guard checks only a row's own id, and an automatic refresh keeps stale saved cells), and blank when the Epic has no issue id. It is repeated per Story and never summed.
- **Never reversed.** Nothing from the Epic is divided among Stories and no Story value is written into an Epic column. A derived cell is never editable and never written; `setCell` and the server already reject a cell whose column row kind differs from the cell's row kind.
- **Marker.** The header shows a superscript after the column name, beside the heading button and not inside it (a focusable marker cannot live in a button): "S" on a Story column in the Epic view, "E" on an Epic column in the Story view. It appears on review columns only; the built-in parent-derived columns in the Story view (Epic, Capacity, Project Track) stay unmarked. The accessible name "Story property" or "Epic property" is carried into the `th` label, the grip, the menu trigger, the popover name, the Show hidden list and the sort label. A hover, focus and tap readout says "Story property, summed from this Epic's Stories in this Sprint and the current filters" or "Epic property, inherited from the parent Epic". `EpicHeaderValueReadout` opens only when truncated and sets its `aria-label` to its value, so the plan adds an always-on mode or another in-app mechanism and lists the file; a native `title` is never used. The marker is a new element kind to register in `docs/design-system.md` and the ratchets, and it reuses the heading's typography. The popover subject "Shared review column" never labels a derived column.
- **Placement and visibility.** Derived columns are automatic and visible by default, and by default the last columns of the other view, in creation order; they do not use the `after` anchor. A saved view's `order` can place them anywhere, so `apply_layouts` allows the custom ids of both row kinds in either kind's layout. Hide is stored per row kind in the Sprint's view (`layouts[kind].hidden`), so hiding a derived column in the Epic view leaves the Story view unchanged and vice versa. A derived column's menu offers Move left, Move right and Hide (the tap path for reordering) and nothing else; subject, rename, total and archive belong to the source column in its own view. Archiving the source removes its derived column everywhere, and derived columns do not count toward the 30 active. Twin headers can occur when an Epic and a Story column share a label; the marker tells them apart.
- **Totals and sorting.** The Epic view's total for a rolled-up column is the sum of the Epic rows' values, which equals the in-scope Story total because the "No Epic" group row shows the sum of its own Stories (the totals function counts that synthetic row for rolled-up columns only), and it is blank while any contributing value is not loaded. An Epic-derived column has no total in the Story view and carries no aggregation, so an Epic value 5 inherited by four Stories never totals 20. Sorting uses the derived value, with empties last.
- **Edge cases.** A Story with no Epic shows blank for an Epic-derived column; an "awaiting creation" placeholder row shows blank; an Epic with no in-scope Stories shows blank, not 0; a derived cell shows the source cell's effective value, so an unsaved edit appears in both views; a derived text cell is bounded and ellipsized with a readout like other bounded text. A Story carried over to the next Sprint keeps its value (one value per issue) and counts in each Sprint's Epic sum where it is in scope.
- **Sprint semantics.** An Epic's sum differs between Sprints and with the filters, exactly as Sprint SP does; there is no cross-Sprint Epic total.
- **Code touched.** `buildPlanningReviewRows` adds `epicIssueId`; `buildPlanningReviewColumns` flags derived columns from both kinds' definitions, never as `custom: true`, and places them last, and every `column.custom` consumer (the menu, the header and cell classes, cell rendering, `reviewValue`, sort, totals) checks the derived flag first; `CustomCell` renders a read-only variant; the heading renders the marker; `PlanningReviewColumnMenu` limits a derived column to Move and Hide; `apply_layouts` allows custom ids of both kinds. Both row sets are already loaded and authorized, so statement counts and Jira authorization passes are unchanged.

### Read contract

- `GET /api/eng/sprints/<sprint_id>/review?groupId=<id>` accepts exactly one `groupId` and nothing else (a duplicate, whitespace-padded or extra argument is a 400) and returns `{schemaVersion, sprintId, groupId, schemaRevision, viewRevision, columns, layouts, inheritedFrom, capabilities}`. `schemaRevision` is the group's column revision; `viewRevision` is the Sprint's own view revision (0 when it has none). Reads do not consult the group catalog: an id with no rows returns the empty schema, and a deleted group's data still reads back by id, which is the reattach.
- `POST …/review/values/read` takes `groupId` in the body (a query string is rejected) and returns the cells of the group's active columns for the requested issues, whichever Sprint is in the path; archived columns' cells are excluded, because group-wide accumulation would otherwise inflate reads. `unavailableIssueIds` and the per-issue `authorize_issues` pass are unchanged, so access still comes from the signed-in user's Jira visibility.
- `groupId` is a string of 1 to 128 characters, equal to its stripped form, with no control characters; a missing or malformed value returns `400 invalid_review_request`. A group whose configured id is longer cannot use review columns (documented limit).

### Write contract

`PATCH …/review` accepts `groupId` (required), `baseSchemaRevision` (required, as today), `baseViewRevision` (optional, default 0, checked only with a layout action), `schemaChanges` and `cellChanges`; a query string is rejected.

- Error precedence: authentication and capability (401, `503 review_storage_unavailable`); structural validation of the whole request, including the content of `schemaChanges` (keys, types, id shapes, the `after` shape, and required `order` and `hidden` lists on layout actions), moved ahead of authorization so a malformed layout cannot spend the Jira budget; group membership, an exact case-sensitive match against the ids from `current_shared_groups_config` (`400 review_group_unknown`; a malformed group catalog stays `503 review_unavailable`); Jira authorization (403/503); then the transaction, where only column-dependent checks remain. An empty request (no `schemaChanges` and no `cellChanges`) returns the resolved schema, creates no row and takes no lock.
- Every writer, including layout-only saves and the adoption script, takes the group schema row first (insert-do-nothing, then `FOR UPDATE`). A request with a layout action then handles the Sprint's view row under that lock: select it; if absent, require `baseViewRevision == 0` and `INSERT` with `view_revision = 1`; if present, require equality and bump. There is no insert-do-nothing and no second lock, so no insert race exists and a second first-save returns `viewConflict`. The lock serializes saves for one group across Sprints and users and is short because Jira authorization runs before the transaction.
- Column actions apply sequentially first. `schema_revision` is checked against `baseSchemaRevision` and bumped (once) if and only if the request has at least one non-layout action; a layout-only request checks only `baseViewRevision` and leaves `schema_revision` alone, so layout saves never conflict with column drafts. Layout actions validate against the post-action columns, archived included, so the normal Add column plus layout save in one request succeeds, and the relaxed `apply_layouts` allows custom ids of both row kinds.
- The server stores exactly the layout actions in the request, merged over the Sprint's own row if one exists, and copies nothing from another Sprint.
- Cell-only and column-only requests never create or touch a view row. Cell changes validate against the group's columns (existence, archived, row kind, type) and keep today's per-cell `baseRevision` semantics, touching neither revision. Because values are per issue, two users editing the same Epic's value from different Sprints conflict like two users in one Sprint do today.
- A 409 always carries `schemaConflict`, `viewConflict` and `cellConflicts`, plus `columns` and `schemaRevision` as today; resolved layouts are not required on a 409, which has no consumer. A 200 always carries `columns`, `schemaRevision` and `cells`, and carries `layouts`, `viewRevision` and `inheritedFrom` (`null`) only when the request had a layout action, so a cell-only save needs no view resolution. `sprintReviewApi.js` forwards `viewConflict`, and the controller applies response fields only when present and treats either flag as "the shared table changed, draft preserved".
- **Decision (my call):** carry the group as a query argument on GET and a body key on POST and PATCH, on the existing routes, so policies, CSRF and `X-Requested-With` guards stay where they are.

### Client

- **Activation.** The hook is active only when a configured group has resolved (`activeGroup?.id` from the loaded groups, not the stored `activeGroupId`, and groups not loading). The scope identity is keyed on the group id, not on `active`, and `load` refuses an empty group. While inactive the table must not show "Review saving is unavailable in this deployment": that message is gated on `schemaLoaded`, not on capabilities alone. The literal `active:` expression pinned in `tests/test_share_view_source_guards.js` changes with it. A `400 review_group_unknown` shows "This Department group is no longer configured." and latches `groupUnknown` until the group or context changes, so row changes do not refetch in a loop. Table-local sort, open menu and add anchor reset on a group change.
- **Group changes.** The controller's scope identity includes the group; `setScope` resets drafts, `loadedIds` and the review state on a group change, and `deferredRead` gains `!groupChanged`. A draft is bound to the group it was loaded under, and `save()` sends that captured group. User-initiated changes (the header dropdown, and a Settings Save that changes the active group) go through `guardScopeChange` like a Sprint change (save, discard or stay) with the scope dialog saying "Sprint or group"; automatic or forced changes (group deleted, favorite re-resolution on load and Retry, share-link apply, which already cancels when dirty, first-run, auth resume, the hide-the-active-group effect) discard like a context change. `trackFilterChanged` moves inside the guarded callback so "Stay" reports nothing, and a source guard pins the list of `setActiveGroupId` writers.
- **Revisions.** `viewRevision` and `inheritedFrom` get the same saved/current handling as `layouts`: `saved*` held while dirty, `current*` updated by refresh, restored by `discard`, `reapply` and `loadCurrent`, set from a response only when the key is present, and cleared by `reset()`. The refresh conflict rule compares `schemaRevision` only when column actions are pending and `viewRevision` only when a layout action is pending, so cell-only drafts survive a revision change by someone else (today any dirty draft conflicts). A missing `viewRevision` or `inheritedFrom` reads as 0 and `null`. Drift of the inherited source under a dirty draft is not a conflict, because a first save sends full layouts.
- **First layout save.** While `viewRevision` is 0 and `inheritedFrom` is non-null, `save()` adds a `layout` action for every row kind the displayed view holds, from the current `savedLayouts`. It is injected inside `save()` and never stored in `schemaChanges`, so "Refresh and reapply" after a `viewConflict` cannot overwrite another user's just-saved layout for a kind this user never touched.
- **Hint.** When `inheritedFrom` is non-null and no layout action is pending in either kind, the table shows one line, "Layout inherited from <Sprint name>." (name from the client's Sprint list, falling back to "an earlier Sprint"), with a small dismiss `IconButton` in a wrapper row (the constraint is line height). It is placed after the error and recovery lines and hidden while they show, reuses `.planning-review-guidance` text styling, works by tap, and carries no second instructional sentence. The wrapper class and the dismiss control are registered in `docs/design-system.md` (the map has no dismiss kind; precedents are `task-remove alert-remove` and the `secondary compact` Dismiss, and the ratchet forbids new `-button`/`-chip` class names without an allowlist entry). The dock measurement effect depends on the hint's visibility, and a geometry test at 375px covers it. This replaces the earlier "no marker" decision at the operator's request.
- **Dismissal** is dashboard state inside the existing preferences object and its dependency list (precedent `teamsEffortExpanded`), passed to the table as props, so `saveUiPrefs` does not erase it. It is a bounded map (newest 50 entries kept) keyed by group and Sprint and holding the source Sprint id and the source's `viewRevision`, so the hint returns once if the source Sprint is re-saved (an addition the operator did not request). Two tabs overwrite each other's preferences, as today. **Decision (my call):** browser state rather than `user_group_preferences`, which would need a migration for a convenience.
- **Archive, Hide and copy.** The Archive confirmation names the group and every Sprint: "Archive "<label>"? It leaves this table in every Sprint for <group name> and cannot be restored here." The group name is passed from the dashboard through the table, its two header renders (real and docked) and the column menu, with a fallback of "this group". Hide stays a view-level action with no added hint text, because the column menu carries no usage text by project rule. **Decision (my call):** the Add popover note becomes "Shared with everyone in this Department group."; the "Save this Sprint review?" dialog title stays, because four specs find the dialog by that name; tests asserting the changed copy change with it.
- `frontend/src/api/sprintReviewApi.js` takes the group, applies `encodeURIComponent` to it on the GET and forwards `viewConflict`.
- Automatic refresh of a clean table can change values, columns or the inherited view when someone else saves; that already holds for other users' edits, and the hint makes an inherited view visible. Refresh stays held while dirty, saving, in conflict or pending.
- Shared links (#194): the review stays inactive under `shareViewHold` until the link's group and Sprint are applied, so no codec change is needed; a test asserts the link's `groupId` on the review GET.

### Existing per-Sprint tables

The shipped table stores columns, layouts and values per `(workspace, Sprint)` with no group. Showing them next to group columns would leave two permanent column sources.

**Decision (confirmed 2026-10-18): a one-time adoption script copies the saved data into every configured Department group, run in a quiesced cutover, and the legacy tables are then retired from reading.** The target is always empty at that moment, which keeps the script simple.

Script conventions follow `scripts/promote_legacy_shared_admin_config.py` (required `--workspace-id`, dry run by default, `--apply` requires `--expected-sha256`, `sha256:` prefix, exit code 2 on refusal), under an importable name such as `scripts/adopt_legacy_sprint_reviews.py` with a way to list workspaces that hold legacy rows. It reads groups through `current_shared_groups_config` with a context carrying only `workspace_id`, never the bound validator in `jira_server.py` (importing it loads the repo `.env`); a test asserts `'jira_server' not in sys.modules`. It validates ids with the route's rules and aborts with a count on a malformed or over-128-character group id or on a non-numeric legacy Sprint id (none can exist), reuses `apply_schema`, `apply_layouts` and `MAX_ACTIVE_COLUMNS`, and runs a physical-table preflight (every required table exists in the connected database).

- **Refusal, not no-op.** `--apply` refuses before any write if any group schema, cell or view row exists for the workspace, as the precedent refuses a second apply, so a repeated run, a run after use of the new tables, and a rollback-then-forward all refuse with zero writes. A group added later starts empty because nothing re-runs the script. All groups are written in one transaction. The digest covers the legacy columns, layouts and cell tuples and the sorted group ids, and is recomputed inside the apply transaction; on PostgreSQL the transaction also takes `LOCK TABLE … IN SHARE MODE` on both legacy tables.
- **Columns.** Legacy columns are processed in ascending numeric Sprint id, then list position. Columns with the same `(row kind, casefolded stripped label, type)` merge into one column that keeps the id and label of the earliest and the `aggregation` of the latest; cells and layouts of the others are remapped to that id. A row kind never merges across kinds. Archive intent follows the latest state: if the latest legacy column of a key is archived, the key is not adopted at all (counted in the report), and archived columns are never adopted. Each merged column is built as one `add` with its final aggregation, so the 120-action limit holds at most 60 net adds per request; beyond 30 active columns per row kind the script keeps the 30 with the highest Sprint id (ties by list position), does not adopt the rest and lists them by column id; it does not abort. Same-key duplicates within one Sprint merge, the later list position winning a cell tie. Ids are unique per group schema, so the same id appears in several groups' schemas.
- **Cells.** Each legacy cell moves onto its merged column per issue with `revision` 1; the highest Sprint id wins a conflict and a `NULL` clear counts as a value, so a later clear wins. The report counts the dropped conflicting values.
- **Views.** A view row is written only for a legacy layout that holds at least one row kind, with only the kinds present, column ids remapped and unadopted ids dropped, duplicates collapsed, and `view_revision` 1; the script enforces the view cap and reports skipped views. Because inheritance is whole-row, a Sprint whose legacy layout held one kind gets a view row with that kind only and no longer inherits; a legacy Sprint with empty layouts creates no row and still inherits. `schema_revision` of a new group schema row is 1.
- **Derived columns after adoption.** Every adopted Story number column with a sum appears as a visible, last rollup column in every group's Epic view, and every adopted Epic column appears in every group's Story view; the report counts them and the runbook says so.
- **Hygiene.** The report prints counts and column or Sprint ids only, never labels, values or issue ids; inserts are chunked for SQLite and PostgreSQL parameter limits; test fixtures are synthetic; legacy rows are never modified or deleted.

**Cutover runbook** (precedent: migration `20260827_0008`, writers quiesced after a backup): back up the database; set `RUN_DB_MIGRATIONS=false`; stop every replica, so nothing serves; run Alembic as a one-off job; run the script dry run and then `--apply` with its digest as a one-off job from the new image (the Dockerfile gains a `COPY` for the script); start the new app; open tabs must reload (an old bundle gets a 400 without `groupId`). The README deploy section carries this exception. Rollback before `--apply` is an app rollback only; after `--apply` it is a forward fix, because `alembic downgrade` drops the group data and entries made since; adopted columns are identifiable (their id equals the legacy id), adopted cells are not.

## Performance

No Jira request, no catalog read and no write on read. Statements per call (upper bounds the `EXEC-*` plan must measure and pin with SQLAlchemy's `before_cursor_execute` event):

| Call | Today | New |
| --- | --- | --- |
| GET schema | 1 (the review row) | 2 (group schema row, the `<=` view lookup) |
| Values read, per batch | 2 (row lookup, cells) | 2 (schema row, cells filtered to active columns) |

## Known limits and rollout risks

- Sprint id proxy and its recovery limits (View resolution); the unchecked-id view cap as an accepted insider risk with an operator purge runbook; the permanent per-group 240-column ceiling.
- A group re-created with a deleted group's id, including the default "New Group" slot, silently inherits the old group's columns, values and views (reattach, approved 2026-10-19); archiving the unwanted columns is the recovery.
- A column or layout change by anyone interrupts dirty column or layout drafts elsewhere in the group; cell-only drafts are not interrupted.
- At cutover, adopted columns surface as derived columns in every group's Epic and Story views, and "highest Sprint id wins" collapses per-Sprint value history (the report counts dropped values).
- Archive affects every Sprint for everyone and cannot be restored; any layout save freezes a Sprint's inheritance for both kinds.
