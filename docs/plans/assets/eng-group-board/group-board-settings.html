Group Board settings

Mockup. Every class here is an existing app class, copied from the real stylesheets — the one exception is noted below.

Inherited, not invented

The configuration reuses the app's own settings vocabulary rather than a new one:

  • .group-modal, .group-modal-tabs, .group-modal-validation, .group-modal-footer — the real settings shell. Not a popup of its own: this is the settings modal.
  • .component-selector + .component-selector-label for every block, the same pattern Teams, Components and the epic selectors already use.
  • .component-chip + .component-name + .remove-btn for each status — the same chip as everywhere else in settings, carrying a .status-pill.task-status inside.
  • .group-modal-meta for counts and helper text, .group-modal-warning for warnings, .group-projects-subsection for the stacked summary + action.
  • .selected-components-list for chip rows, secondary compact buttons, .group-danger-zone, details.group-advanced.

The one new thing is the side-by-side column arrangement (.board-columns). Nothing in the app lays configuration out in columns, so that layout has to be new — but every control inside it is an existing class. The preview is not new either: it reuses the board's own .col / .col-strip / .fill / .vert, so it cannot drift from what the board actually renders.

Where it lives

Settings → Departments → Boards, a third sub-tab beside Team groups and Group labels, with the same group list on the left so the group is always the scope. Team groups keeps a Board section whose only content is a summary and a Configure board button — so the group editor stays scannable.

Saved in the group payload on /api/groups-config, not the global admin-only /api/board-config. Save is the modal's footer Save, which persists every dirty section together; Group Board gets no save button of its own.

Two ways to put a status in a column

+ Add status under each column opens a list in place and assigns on click. Drag by the ⠿ grip does the same thing faster. The × on a chip, or dragging it onto Not in a column, sends it back to the leftover pool.

The earlier version had drag and nothing else — and the chips carried draggable with no grip, no grab cursor, and a drop target that only appeared once a drag was already under way. The one affordance was invisible until after you had guessed it existed, and keyboard users had no path at all.

The picker lists every status this column does not already hold — orphans first as not in a column, then the rest as from <column> — because assigning moves a status rather than copying it. Restricting it to orphans would leave the control dead in this configuration, where all twelve statuses are already mapped, and force a drag for the most common edit. Eleven rows would double a column's height, so the list scrolls inside itself.

Min / Max warn, they never block

They control nothing. A column whose epic count falls outside its range glows red here, in the preview, and on the board, and states the breach in words. It does not block Save — the work is already in that state in Jira.

An empty column is different: that is invalid config, since the column would render nothing, so it does block Save through the existing validation banner.

Open question

/api/groups-config is user_write, so as specified any signed-in user can rewrite these columns for everyone in the group. If editing should be admin-only it needs an explicit server guard, not a hidden button.
