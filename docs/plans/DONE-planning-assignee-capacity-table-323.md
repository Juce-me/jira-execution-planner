## Intent

The team lead plans the team's effort for a Sprint from one view: how much capacity each person has, how much work each carries, how much has been taken (checked) into the plan, and how much work still has no owner. Issue [#323](https://github.com/Juce-me/jira-execution-planner/issues/323). All numbers are Story Points. Anti-goal: a second source of truth where a Jira capacity ticket exists. Jira capacity stays the core number; the stored team number is a fallback and an inheritance source only, and nothing is ever written to Jira without the user saving it in the existing capacity editor. D7 supersedes `SUPPORT-planning-capacity-editing-design.md` lines 46-47 and the Global Constraints of `EXEC-planning-capacity-editing.md` ("Jira is the only source of capacity values"); both get a Current Accuracy note in Task 10.

## Behaviour

### Where it shows

Planning Table layout, exactly one team selected (`!isAllTeamsSelected && selectedTeamSet.size === 1`). Otherwise `PlanningTeamCapacityCards` is unchanged. The team capacity card keeps its Jira number, pencil editor, missing-ticket banner and Refresh capacity, and gains the planned-number editor and reconcile banner (see Planned team capacity). The table is a new in-flow strip (D1) holding the table and the removed strip; its expanded state is persisted under its own `localStorage` key `jep.planningAssigneeCapacityExpanded` (the UI-prefs object cannot hold it, see Implementation state).

### Columns

Assignee, Capacity, Selected effort, Total effort, Vacations, Notes. No Total/available column.

- **Capacity, Vacations, Notes:** typed in. Numbers are Story Points, 0 to 10 000, at most two decimals, JSON strings on the wire (`"10.25"`), blank means unset (counts as 0). Notes up to 500 characters, single line, control characters rejected. Vacations are informational (not subtracted from Capacity) and may exceed it; negative values are rejected. An invalid draft stays in its cell with an error and is not sent.
- **Selected effort:** Story Points of the checked Stories of the selected team per assignee, taken from `selectedTasksList` (the set the capacity bar's `selectedSP` and the team card use), so its total equals the bar's Selected for the team. It comes from the same list as the capacity bar's Selected: search, Team, Project and Project Track facets narrow it; the Priority and open-status facets do not (`selectionTasks = baseFilteredTasks`, `dashboard.jsx:4188-4193`). The model itself does not filter by team. No test yet compares the table's Selected total with the bar's Selected (DoD 3).
- **Total effort:** every non-Killed Story of the selected team in the Sprint, independent of filters and checkboxes: `projectPlanningOriginals(capacityTasks, planningOriginals)` filtered by `getTeamInfo(task).id === teamId` and `normalizeStatus(status) !== 'killed'` (pending status edits count as the existing filters count them). Includes Stories under excluded Epics. Null Story Points count as 0.
- **Unassigned:** `!task.fields.assignee?.accountId` (the loader returns an assignee object with null fields for unassigned work, so a truthiness test is wrong). It gets its own row, highlighted with the existing warning tone (a reused class), sorted first, shown only while unassigned Stories exist, not editable or removable.
- **Totals row:** sums of Capacity, Selected, Total and Vacations (four numeric columns), including the Unassigned row's effort. The over-capacity cue reuses the existing thresholds (over above 120% and under below 90%, `planningCapacityUtils.js`) comparing Selected with Capacity, only for rows with Capacity set; the Totals cue compares the displayed Selected total (including Unassigned) with the sum of Capacity, the same numbers the row shows (the revision 3 text compared without Unassigned and contradicted the displayed values).
- Sums and comparisons run in integer hundredths (no float drift); display is at most two decimals, trailing zeros trimmed. Rows sort by name then key and keep their position while one is being edited.

### Rows and inheritance

- Rows are merged by assignee key from: assignees with Stories in scope, rows of this Sprint's document, and inherited rows. One person is one row, always.
- Inheritance is whole-document: for an active or future Sprint with no document of its own, the read returns the nearest earlier document for this team (`sprint_order <`) as `inherited`, a single source. Its non-removed people appear and their Capacity cell shows gray (only that cell carries `planning-assignee-inherited`), with one hint line "Inherited from Sprint X" (the existing hint pattern). Vacations and Notes are not inherited. Planning is unavailable for closed Sprints (`setShowPlanning(false)`, `dashboard.jsx:2895`), so the strip never renders for one; `ignoreInherited`/`sprintClosed` are defensive inputs only, and `baseRowsOf`/`applyChangesToDocument` ignore them (a first save there would store inherited people).
- **First write materialises.** The first save in a Sprint without a document creates it in one locked transaction: the server copies the source's non-removed people and Capacity, then applies the change. The Sprint becomes the complete source for the next one, so a partial edit never drops people downstream, and an edit to Vacations or Notes of a gray row cannot blank its Capacity. The client sends no inherited values. A no-op commit (value equals what is shown) sends nothing, so tabbing across gray rows creates no document.
- **Names are stored.** Every row stores a `displayName` snapshot (and the account id, which Jira keeps for deactivated users). When a Story supplies the person's current name, a save refreshes the snapshot; a read never writes. A person with no Stories, including one later deactivated or removed from Jira, keeps appearing under the stored name as historic data, and is never dropped because Jira no longer lists them. A person with Stories shows the name from the Story.
- **Remove / Restore.** Remove is offered only for a person with no Stories in scope. A removed person moves to a one-line strip under the table, "Removed from this Sprint and later ones: name, name"; each name, underlined as an inline action, restores with one tap (the operator's "sad face" is the unhappy tone of this line; the `☹` glyph is replaced by plain text because it renders as a circled mark and is an emoji-font risk in Firefox and WebKit). Values are retained while removed. A person who has Stories is never removed. The strip is absent when nothing is removed.

### Saving

- Commits (Enter or blur; Escape cancels) go through one serial save queue per Sprint and team: one request in flight, commits within about 200 ms coalesced into one `changes[]`, no no-op requests. Last-write-wins makes a retry idempotent, so a lost response is handled by reloading and re-sending only differing fields.
- The CSRF token is reused across the queue.
- As implemented: a Team or Sprint change sends the old scope's pending commits at once and lets them finish in the background (`setScope` calls `flush(previous)`); it does not use the review's dirty prompt (`guardScopeChange`). Revision 4: a failed background save keeps its queue per scope (the last five scopes, page session) and the scope shows Not saved with Retry and the drafts on revisit. Late responses for another scope are dropped (scope key plus generation counter). Collapsing the strip (not the panel) commits any open edit first. A 401 keeps drafts and uses the existing terminal sign-in lock.
- Basic or non-database mode: the read returns `capabilities {canRead, canSave, reason}` and the table is read-only or hidden accordingly.
- States defined and tested: loading, empty (no Stories, no rows), read failure, saving, saved, failed. The status shows in the collapsed 28 px header too (a scoped exception to the rule that hides `.capacity-subtitle`). A rejected change gets a discard path and `displayName` is validated before sending, so one bad change cannot poison later batches. The inherited hint reads "Inherited from Sprint X. Editing any value saves this Sprint's own copy." A muted guidance line says when selected Stories are hidden by filters.

### Team capacity (not in Jira)

Fields: a nullable decimal `planned_capacity` and `planned_source` (`user`, `jira` or `inherited`) on the Sprint and Team document, with `planned_source` null exactly when `planned_capacity` is null. Whole-document inheritance carries them: a Sprint without its own document shows the nearest earlier document's number gray, and the first write materialises it with source `inherited`. `planned.source` is client-supplied and unverified, like `assigneeKey` (D4). The PATCH body's `planned` is `{value, source, onlyIfSource?}`; an empty PATCH means no `changes` and no `planned` (a planned-only PATCH persists and does not hit the early return in `_apply`).

**The "no ticket" predicate.** The fallback and the editor apply only when `capacityEnabled && !capacityLoading && !capacityReadError && !capacityDataStale && capacityState.scopeSignature === scope && capacityIssueCount !== null && target.state === 'missing' && !numeric.matched`. Not `ambiguous` (the numeric Jira value is kept there), not loading or failed (every team looks `missing` during those states, and `capacityTargetsByTeam` is empty after a failure), and not when no Capacity Project is configured (`capacityEnabled` is false, no capacity read and no bar). A matched ticket with a blank value (`hasCapacityValue: false`) shows the stored number as the fallback, the pencil still edits Jira, and the banner offers Write to ticket only.

**Where it enters the capacity maths (B1, decided 2026-10-30: design A).** The Jira value is read in one place (`buildCapacityReadState`, `planningCapacityUtils.js:64-102`, to `capacityState.capacityByTeam`, a `Record<normalizeCapacityKey(teamName), number>`, to `effectiveCapacityState` and `getTeamCapacity`/`getTeamNetCapacity` in `useEngCapacity.js:181-312`, to `capacityTotalsSummary`, `totalCapacityAdjusted`, `projectCapacity`, `selectedTeamEntries` and `rawCapacity`). `buildSelectedTeamEntries` feeds only the cards and `rawCapacity`; the amber bar reads `totalCapacityAdjusted`, so a fallback inside the entries fixes neither the amber bar nor the project split bar. The stored document lives below App (the provider is mounted inside `planningOverview`, `dashboard.jsx:5984`), so the value would travel child to App to `useEngCapacity` to `rawCapacity` to the provider, a cycle. Two designs: **A** `useEngCapacity` takes `plannedCapacityByTeam` (`Record<normalizedTeamKey, number>`, only for teams with no ticket and no Jira value), merged inside the `effectiveCapacityState` memo after the scope check, never touching `capacityTargetsByTeam`, `capacityIssueCount` or `mutationEnabled`; the framework-free controller is held above the provider and read in App through one `useSyncExternalStore` (not in `HOOK_CEILING_NAMES`, but an exception to the "no new hook in App" rule and to "no edit to `useEngCapacity.js`"; DoD 13 becomes "App re-renders only when the planned map changes"); it works only in Table layout with one team, which is where the whole feature lives. Consumers that must stay identical when a Jira value exists: `getTeamCapacity`, `getTeamNetCapacity`, `capacityTotalsSummary`, `capacitySummary`, `projectCapacity`, `selectedTeamEntries`, `rawCapacity` into `buildUnderbar`, `PlanningCapacityBar.jsx:14-57`, the card maths (`PlanningTeamCapacityCards.jsx:457-481`), `applyCapacitySaveResult`, the freshness owners; `futureSprintCapacityIssuesMissing` and `canEditCapacity` (`capacityMutationEnabled`) stay Jira-only. The fallback shape is a finite number under `normalizeCapacityKey(team.name)` in `capacityByTeam` only: the card then has `capacityTargetState: 'missing'`, `capacityIssueKey: ''`, `hasCapacityValue: true`, `rawCapacity: stored`.

**Editor.** The card editor gains `mode: 'jira' | 'planned'` and an identity `${mode}:${teamId}` (today it is keyed by `issueKey`: effect deps, `pencilRefs`, `restoreFocusIssueRef`, `invalidTargets`, the draft updater; `showPencil` requires `targetMatched`, so a missing-ticket card has no rail today). The queue gains a team-level `planned` slot carried by `asDocument`, the optimistic overlay and `recover` (today `applyChangesToDocument` sets `inherited: null` and drops the gray number while any commit is pending). The editor stays disabled until `state.document` exists, and the card shows saving or failed state because the strip may be collapsed. **Mirror and reconcile rules.**
- Mirroring Jira into the store updates an existing own document only; it never creates one, never runs when the Sprint has no own document, and does not run for a team whose ticket value is outside 0..10,000. Absent counts as "differs" only when an own document exists.
- It triggers on the `capacityLoading` true to false transition of the same scope (the only discriminator of a user-initiated read; `capacityReadRevision` also increments on automatic successes), with the assignee document loaded for the same (Sprint id, Team id). It goes through the same serial queue, is computed from the post-queue document, and is dropped if the queue is busy or non-empty. A failed mirror is dropped silently: it never sets `failed`, never raises Not saved and is never replayed. The mirror PATCH sends `planned.onlyIfSource: ['jira','inherited']`; the server applies it in the locked section only when the stored source is in the list and otherwise returns the current document, so a concurrent user edit is never overwritten. Use ticket value omits it.
- Equality is compared after rounding both sides half-up to hundredths.
- After a successful pencil save to Jira, a stored source `user` becomes `{ticket value, 'jira'}`, so the banner cannot contradict the user's own Jira save.
- The banner is section-level, above the card grid (the existing banner pattern, `PlanningTeamCapacityCards.jsx:411-442`; one team is selected so at most one banner), shown only when a matched ticket with a writable target exists, a stored number with source `user` exists and it differs from the ticket value; buttons Write to ticket (opens the existing editor prefilled; the user saves with the existing single Jira call site), Use ticket value (source `jira`) and Not now. Not now suppresses the banner per (Sprint, Team) until either value changes. "Read-only user" means `capabilities.canSave === false`: no banner, no mirror, no Use ticket value; `canEditCapacity === false` hides only Write to ticket. Copy that coexists with the future-Sprint "Jira issues have not been created" banner is specified in Task 8.
- The negative test names the Jira write symbols: `frontend/src/api/capacityApi.js::updateCapacity`, `backend/services/capacity.py::update_capacity_issue` and the `current_jira_request` PUT; a stored-number path calling any of them fails the test.

### Undo

Last slice. A client stack of full-row snapshots queued behind the save queue (an undo is an ordinary edit), cleared on scope change and on any save failure; Cmd/Ctrl+Z only when focus is in the table and no cell is mid-edit, ignoring key auto-repeat, plus a visible Undo control for touch. Undo of the first edit of an inherited row cannot restore "still inheriting": the row stays saved with the inherited values, and the hint says so.

## Data model

One table, `planning_team_sprint_capacity`: `id` Uuid, `workspace_id` FK CASCADE, `sprint_id`, `sprint_order` (128-digit padded, `CHECK length = 128`, as `GroupSprintReviewView`), `team_id`, `rows` JSON (`assigneeKey`, `displayName`, `capacity`, `vacations`, `notes`, `removed`), `planned_capacity` nullable decimal string and `planned_source` (`user`, `jira`, `inherited`) (revision 4), `revision` int >= 1, timestamps. Unique on (workspace_id, sprint_id, team_id); index (workspace_id, team_id, sprint_order) serves the nearest-earlier lookup. Keyed by workspace + Sprint + Team, not Department group (Jira capacity is per team and Sprint; no group-id reattachment hazard). No user columns.

Bounds: at most 100 rows per document, 2,000 documents per workspace, body 64 KiB, response 256 KiB, ids 128 characters, `displayName` 200 characters without control characters. `assigneeKey` is the Jira account id and is not Jira-verified; `teamId` is validated by shape and length only.

Alembic revision `20261029_0022`, `down_revision = '20261028_0021'` (precedent `20261020_0019_group_review_columns.py`); the planned columns default to a new `20261029_0023` revision (nullable `planned_capacity` and `planned_source`, `CHECK planned_source IN ('user','jira','inherited')` and `(planned_capacity IS NULL) = (planned_source IS NULL)`) because `runners/local/run.sh:429` and `scripts/docker-entrypoint.sh` run `alembic upgrade head` on start and preflight compares only revision ids (`repository.py:46-53`), so a database already stamped at the old `0022` would fail on a missing column. Task 1b records `alembic current` for the Docker and Homebrew databases; the revision is amended in place only if the record shows no database at `0022`. The three head-pin tests already say `20261029_0022` and move only on the `0023` path; the offline SQL slices and model-column parity in `tests/test_assignee_capacity_service.py` change either way, and a test asserts an older head fails `_migrations_at_head` against the new head. Tests that pin the current head must move to the new one: `tests/test_review_adoption_migration.py`, `tests/test_remove_user_api_token_migration.py`, `tests/test_sprint_review_postgresql.py`.

Concurrency mechanism: insert the document row with `ON CONFLICT DO NOTHING`, then `SELECT … FOR UPDATE` (as `_locked_schema`, `sprint_review.py:419`); `SET LOCAL lock_timeout` about 3 s mapped to 503; no Jira or network call inside the lock; an empty PATCH takes no lock. SQLite ignores `FOR UPDATE`, so a PostgreSQL race test (two first-writers of one new document) is part of the DoD and runs with `REQUIRE_POSTGRES_REVIEW_CONCURRENCY=1` and an approved `TEST_DATABASE_URL`.
