# Planning capacity prefill across work configurations

> **Status:** Planned; T0 diagnostic complete 2026-11-12 (see T0 outcome), T1-T5 ready to execute. Implementation branch: `bugfix/team-capacity-prefill-and-refresh-icon`. Independent of the unfinished historical capacity-editing plan. This contract supersedes that plan's removed read-status panel and Retry-button requirements, including its prop inventory. Reviewed 2026-11-12 by three independent read-only reviews (frontend flow, backend/identity, file map/process); their confirmed findings are folded in below.

## Outcome and current accuracy

The 2027Q1 Team capacity editor should offer the uniquely identified earlier Sprint's raw Jira capacity even when that Sprint belongs to the Legacy work configuration. This plan has not been executed. The localhost example shows a blank Distribution editor and a 2026Q4 display capacity of 27; the displayed value may include a Product/Tech share, so it does not establish the raw prefill value. Do not claim a live cause or raw value until T0 measures it.

## Evidence and diagnosis

Verified against current code on 2026-11-12:

- `frontend/src/dashboard.jsx:6182-6184` passes `sprints={availableSprints}` and `readPreviousCapacity` to `PlanningTeamCapacityCards`. `availableSprints` comes from `sprintCatalogState` (`dashboard.jsx:573`); `reduceSprintCatalog` (`frontend/src/dashboardRuntime.js`, ~236-262) replaces it only with the accepted, validated, context-matched catalog of the *current* configuration. `in_range_sprints` (`backend/services/workspace_catalog_cache.py:312`) filters configuration-scoped reads (`backend/routes/settings_routes.py:912,1072`, `work_structure_routes.py:271,434`). A 2027-only DELIVERY catalog cannot contain 2026Q4 from Legacy, and `previousPlanningCapacitySprint` (`planningCapacityUtils.js:671-685`) can only choose from the list it receives. This is a code-proven failure mode, not yet proof of the localhost request path.
- `dashboard.jsx:586` already calls `useSiblingQuarterStates`, which fires `requestSprints(BACKEND_URL, { context })` for every non-viewed configuration when the sibling set changes (`useSiblingQuarterStates.js:46-63`). `fetchSprints` accepts a context carrying id, revision and digest (`engApi.js:29-52`). Requesting a sibling catalog is therefore feasible, but that hook is **not** an authority source: it checks only `response.ok` and `siblingStatesFromBody` keeps only quarter-to-state (`useSiblingQuarterStates.js:17-25`); it does not check `cache.identity`, `browserContextId`, `validatedAt`, `catalogVersion` or completion. Those checks exist only for the current catalog in `reduceSprintCatalog`.
- The backend search is `summary ~ "\"Team info <sprint> - <cleaned>\""` (`backend/services/capacity.py:61-74`) built from the *normalized* name; the frontend sends only the normalized name (`useEngCapacity.js:35`). Normalization strips `[archived]`, `r&d `, `product -`, `tech -` (`capacity.py:44-53`, mirrored `planningCapacityUtils.js:5-13`). Results are re-normalized and the prefix is dropped (`capacity.py` ~363-383), entries are `{teamName, issueKey, capacity}`, and `capacities` is a dict keyed by normalized name where duplicates overwrite while `entries` keeps all. T0 measured (see T0 outcome); whether prefix-titled tickets are found remains unproven because the sampled titles were plain.
- `previousPlanningCapacityValue` (`planningCapacityUtils.js:688-696`) rejects duplicate normalized names only among displayed cards (`teamNames` from the visible `entries`, `PlanningTeamCapacityCards.jsx:556`). Two configured Teams with the same normalized name cannot safely be told apart by preferring a raw prefix.
- The existing `tests/ui/planning_assignee_capacity.spec.js` prefill fixture supplies both quarters in one catalog and stubs Jira capacity independently of JQL. Neither it nor the utility test establishes cross-configuration or real Jira search behavior.
- Current editor code: both openers compute `previousSprint` synchronously at open and set `prefilling: Boolean(previousSprint)` (`PlanningTeamCapacityCards.jsx:489-492, 524-526`); `cancelEditor` (`:562-568`) does not abort the in-flight controller and the only stale guard is `editorRef.current !== nextEditor`; `scopeSignature` is not compared in the response path. The Jira editor prefills when the ticket value is null **or 0** (`:489`); the planned editor prefills when `planned.source` is neither `user` nor `jira` (`:524-525`).

## T0 diagnostic (blocking gate, no product code)

Transient, sanitized observations only; never persist raw payloads, Team names, Sprint ids, Jira keys, credentials or live screenshots; the user signs in themselves; read-only. Record:

1. On editor open in 2027Q1 DELIVERY: whether a prior-capacity GET starts, its source quarter, HTTP outcome, count of exact candidate issues, whether the stored value is own or inherited.
2. Loaded current and sibling catalog membership/authority (which configuration holds the 2026Q4 row).
3. Search behavior via the existing `debug=1` response (`capacity.py` ~397-405: JQL, `issueCount`, `matched`): run with the normalized name against a prefixed and an unprefixed title and record which are found and whether they are distinguishable.

Decision table: (a) catalog hypothesis disproved -> update this plan to the observed cause before any implementation; (b) prefixed titles are not found by the normalized phrase -> backend search/provenance change needs a separately reviewed design (request bounds, provenance field, pagination and partial-failure semantics) and T3 is stopped; (c) both forms found and distinguishable -> proceed. Record the outcome in this plan's Outcome section and commit it before T1.

### T0 outcome (2026-11-12, localhost, sanitized counts only; no names, ids, keys or screenshots kept)

1. **Catalog hypothesis confirmed.** The Legacy configuration (`throughQuarter` 2026Q4) holds 12 own rows, 2026Q4 being its one active Sprint; the DELIVERY configuration (`fromQuarter` 2027Q1) holds only 4 rows, 2027Q1-Q4, all future. The 2027Q1 view therefore never receives 2026Q4. Both sibling catalog reads returned 200 with `cache` keys `identity`, `browserContextId`, `catalogVersion`, `validatedAt`, `state`, `refreshStatus`, `refreshFailed`, `failureCode`, `configurationRevision`, `rowIdentity` and no top-level pending flag; completion/pending must be read from `cache.state` and `cache.refreshStatus` (T2 defines the validator over these).
2. **Editor open sends no prior-capacity GET.** After opening a Team's 2027Q1 editor, the request log held the single 2027Q1 capacity read and no 2026Q4 read beyond the diagnostic's own 41 (one all-tickets read plus 40 sampled names). Caveat: own-versus-inherited stored value of that Team was not recorded.
3. **Search.** The all-tickets read for 2026Q4 returned 160 issues and 158 entries (2 issues did not parse as titles); the 20 titles the debug output exposes were all plain (no `[archived]`, `R&D`, `Product -`, `Tech -` prefix). Querying 40 sampled normalized names exactly as the app sends them: 40 found exactly one entry, 0 found none, 0 found several, 0 errors. A hand-typed name variant test returned 0 for every variant including the as-shown form, so it is discarded as inconclusive (the typed name did not match a ticket).

**Decision:** row (c) holds in its narrowed form. The normalized phrase search finds one ticket for every sampled name, so the existing request path is usable for cross-configuration prefill. Whether prefix-titled tickets are found is **unproven** (no prefixed title was in the observed sample); T3 therefore keeps the stop rule: a name with zero or several `entries` yields no prefill and the retryable message, and the acceptance item "prefix-titled tickets" is reported unverified unless a prefixed title is later observed.

**Stop rule.** If search provenance cannot be proven, cross-configuration prefill ships only where the normalized phrase search is proven to return a unique ticket; otherwise the editor keeps the draft blank and shows the retryable previous-capacity message. The acceptance item is then reported unverified and the plan is not marked complete.

## Contract

1. On explicit editor open, preserve an own `user` or `jira` stored value; never replace it with a previous Sprint. For an absent or inherited value, resolve earlier-quarter candidates across the current and relevant earlier configurations. Jira editor: a null or 0 ticket value means prefill is allowed and the ticket value remains the expected-capacity conflict baseline (add a test where the ticket is 0 and the earlier quarter has a value). Read-only suggestion: opening, canceling or resolving never writes Jira or application data. Exactly one earlier-Sprint capacity GET per editor open, for the one resolved Sprint.
2. Reuse the existing configuration-stamped `fetchSprints` read. Extract a **per-sibling validator** from `reduceSprintCatalog`'s acceptance rules (`cache.identity`, `browserContextId`, `catalogVersion`, `validatedAt`, configuration revision/digest, completion) and apply it to each sibling response; do not use `useSiblingQuarterStates` output as authority and do not feed these reads into `sprintCatalogState` (no `reduceSprintCatalog` events, no auth lock or generation bump). Decision to record in T2: reuse the mount-time sibling reads' network responses only if the validator can see the full rows, otherwise issue an on-open read; if on-open, "no new startup requests" holds, if mount reads are reused, say so. No force refresh. "Relevant earlier configuration" = a configuration other than the current one whose `fromQuarter`/`throughQuarter` range includes a quarter earlier than the current quarter; at most the configured sources; a configuration with no usable context (`buildConfigurationContext` returns null) is treated as unavailable; more than two configurations are handled by the same rule. A pending, partial, failed, stale-revision or foreign (workspace/Jira site) catalog is not authority; a validated, complete snapshot whose `cache.state` is `stale` only because its refresh time passed is authority (ruling 2026-11-12: rejecting it would make aged Legacy catalogs permanently unusable; a started refresh shows as `refreshStatus: pending` and is rejected). Fail-closed cost, accepted: if any earlier source is pending or unavailable, no prefill is offered, even for a quarter the current configuration alone could have answered. The Settings `sprint-values` endpoint is not a substitute (coalesced names, no start dates). Unknown to be verified in T2: whether the backend can return pending/partial for a non-selected configuration.
3. Combine validated rows only for this lookup, held in a new lookup-private prop (for example `previousCapacitySprints`), never replacing the existing `sprints` prop (`availableSprints` also feeds `PlanningAssigneeCapacity`, `dashboard.jsx:6141`, and the Sprint selector). Dedupe by `String(id)`; compare name, `state` and `startDate`; any mismatch fails closed. "Equally ranked" means same quarter and same `startDate`; all tied candidates (not only the first two, `planningCapacityUtils.js:682`) fail closed. Ordering: exactly one earlier active Sprint wins; otherwise the nearest earlier quarter, latest start date. Never select the current or a later quarter. Unavailable, incomplete, stale or ambiguous catalog: keep the stored draft, allow manual entry, show a retryable previous-capacity message (distinct states: catalog pending, unavailable, ambiguous, no ticket). Restructure the openers so the Sprint choice, catalog acquisition and capacity GET form one async chain under one `AbortController` and a per-open token checked after every await. Fences: abort on cancel, unmount, new open, and a change of `scopeSignature`, Sprint, Team or configuration revision. A late response applies only if the draft still equals its baseline; a typed draft always wins. `AuthenticationRequiredError` stays silent for catalog reads as it is for the capacity read (`:559`). Re-check the catalog's `cache.identity` and `browserContextId` against the current workspace and Jira site at response time.
4. **Team uniqueness.** Membership input: the active Department group's complete saved `teamIds` (`activeGroup.teamIds`, `dashboard.jsx` ~2505-2515, deduplicated by id; persisted owner `useTeamGroupSettings`); names via `teamNameLookup`/`resolveTeamName` (`dashboard.jsx` ~1226, ~2600; ids authoritative, names only a lookup, `teamSelectionUtils.mjs` `buildTeamOptionsForScope`). The workspace name directory `workspace_team_catalogs` is a name resolver, not membership (`backend/security/CONFIGURATION_OWNERSHIP.md:20,56`). T3 must establish, from code, whether any Planning-scope admission source exists beyond `teamIds`; if none, drop the "additionally admitted" clause from this contract. Change `previousPlanningCapacityValue` to take the complete `{id, name}` membership; fail closed on an unresolved name or an id with no name (raw-id fallback is not a name), and on distinct ids that normalize alike (outcome: no prefill, no message, draft retained; pinned test). Dedupe repeated references to the same id. Uniqueness uses `entries`, never `capacities` (duplicates overwrite there). Exact matching, reject multiple issue candidates, preserve numeric zero and full raw precision until existing editor formatting. Cross-era identity is unprovable; an identity-mapping policy needs a separate operator decision. Do not silently choose between candidates.
5. **Refresh control.** Keep the refresh icon only when capacity is enabled, including compact mode. Current state: `planning-panel-refresh` (`PlanningOverviewPanel.jsx:28`, `planning-review-table.css:144-145`) is **not registered** in `docs/design-system.md`; register it (element-kind row or hook entry, with a ratchet allowlist reason if `tests/test_design_system_ratchets.js` flags it) rather than "preserve". Stale/error recovery copy currently names an unlabeled icon (`dashboard.jsx:6142` "Capacity stale — use Refresh capacity to retry"). Chosen fix: keep the control an icon button of the existing `planning-action-button planning-icon-button` kind with the existing `RefreshGlyph`, and have the status line carry the visible retry affordance by showing the same glyph inline in the copy ("Capacity stale — retry with ⟳") — no new control, no new class; verify compact-mode wrapping (`planning-review-table.css:181-182`) and the existing assertions at `planning_capacity_editing.spec.js:1182,1371`, `planning_review_integration.spec.js:694`, `planning_assignee_capacity.spec.js:3694` stay valid. Keep props `capacityStatus`, `onRefreshCapacity`, `capacityLoading`, `refreshLabel`; add none unless needed. Keep loading accessible name and `aria-busy`. Duplicate-activation guard must be synchronous (a ref, not React state: the current `if (!capacityLoading)` at `PlanningOverviewPanel.jsx:30` lets same-turn clicks pass); it lives in `retryCapacity` (`useEngCapacity.js:237`) or the panel via a ref — choose in T4 and add the file to the task's list if it is the hook. No new analytics event: `jira_team_capacity` `api_result` (`capacityApi.js:48`) covers the capacity read; the prior-Sprint GET reuses it with no Sprint name in params; document the rationale in `docs/README_ANALYTICS.md` (existing row ~258 "Future-sprint Capacity empty-state refresh") and review any new catalog read under its existing telemetry contract without identifiers. Keep `t=Date.now()` and `cache: 'no-cache'` unchanged.
