## Gaps and hypotheses to validate

- **Successful auth versus attempted auth:** the shared timestamp is written before the POST completes (`authFocusRefresh.js`, lines 58–75). A second tab can dispatch its long-absence event during the throttle even if the first tab's auth attempt failed or has not completed. The timestamp proves an attempt, not successful session validation. The current two-tab browser test is sequential, not an atomic concurrent claim test (`auth_focus_refresh_counts.spec.js`, lines 344–390). Any stronger deduplication or auth-ordering guarantee needs its own test.
- **Dropped eligibility:** `handleVisibleReturn` clears absence before `refreshAuthOnFocus` checks `refreshInFlight`/connection ownership (`authFocusRefresh.js`, lines 52–55 and 94–97). The dashboard may also ignore the resulting event while loading or onboarding (`dashboard.jsx`, lines 5950–5957). There is no pending-refresh intent in these paths. Investigate whether a visible stale view remains stale after the blocking state ends.
- **8-hour/24-hour return:** if blur/hidden was recorded and the document survives, both durations exceed the same 12-minute threshold; there is no separate 8-hour or 24-hour branch. An elapsed duration alone does not prove the Jira connection is invalid. The refresh route resolves current request auth and token data (`auth_routes.py`, lines 440–464); DB token handling checks expiry and performs a locked refresh with re-read (`db_tokens.py`, lines 393–459; expiry comparison in `jira_auth.py`, lines 219–221). Test valid rotating-token refresh, revoked/disabled sessions, failed refresh, and browser-discard bootstrap separately.
- **Sleep and discarded documents:** absence timestamps exist only in the current module instance. No `pageshow`/`resume` listener exists here (`authFocusRefresh.js`, lines 108–123). Do not infer OS sleep coverage from fake-clock tests; verify retained-document wake, back/forward-cache restoration, and ordinary new-document bootstrap as distinct cases.

These are source-derived hypotheses and coverage gaps, not reproduced reports of user-visible failures.

## Primary-source constraints

- **Visibility and focus:** the HTML standard makes visibility a browser-determined state, including background tabs, minimized windows, and obscuring system UI; it is separate from input focus. [WHATWG Page visibility](https://html.spec.whatwg.org/multipage/interaction.html#page-visibility). Chrome documents visible-without-focus as passive and hidden as a separate state. [Chrome Page Lifecycle API](https://developer.chrome.com/docs/web-platform/page-lifecycle-api).
- **Timers and suspension:** timers have no exact scheduling guarantee; browsers can freeze pages, suspending timers and fetch callbacks, and discard pages without a discard event. A discarded document requires a fresh page load. A future periodic policy should evaluate elapsed successful-data age when execution resumes instead of counting timer ticks or replaying missed intervals. The final sentence is a design inference. [WHATWG Timers](https://html.spec.whatwg.org/multipage/timers-and-user-prompts.html#timers), [Chrome Page Lifecycle API](https://developer.chrome.com/docs/web-platform/page-lifecycle-api).
- **OAuth longevity:** Atlassian documents rotating refresh tokens with a default 90-day inactivity expiry and 10-minute reuse leeway; each use replaces the refresh token. These provider defaults do not establish this application's browser-session lifetime or guarantee refresh success. [Atlassian OAuth 2.0 (3LO) apps](https://developer.atlassian.com/cloud/jira/software/oauth-2-3lo-apps/).
- **Jira consistency:** enhanced JQL search is eventually consistent after writes. `reconcileIssues` gives consistency only for up to 50 specified issue IDs. Re-fetching every few minutes cannot promise an instantaneous complete view of all remote edits. Reconciliation is a possible targeted post-write mechanism, not a blanket polling fix. [Atlassian Search and Reconcile](https://developer.atlassian.com/cloud/jira/platform/search-and-reconcile/).
- **Jira cost and backoff:** OAuth apps face points-based quotas plus endpoint burst limits; writes also face per-issue limits. Handle `429` and `Retry-After`, use bounded exponential backoff with jitter, request necessary fields, paginate, and cache stable data. API-token traffic is governed differently. Refresh policy therefore needs measured per-generation Jira cost and request coalescing, rather than deriving a safe cadence from browser request counts alone. [Atlassian Rate limiting](https://developer.atlassian.com/cloud/jira/platform/rate-limiting/) (documentation updated 2026-10-08).

## Proposed guardrails for plan review

Preserve the existing terminal auth lock, scoped current-user auth, connection-recovery precedence, and separation between data refresh and document navigation. Specify hidden and passive-window semantics independently. Treat active editors, dirty Planning/Scenario/Settings state, and in-flight writes as explicit eligibility conditions. Keep one eligible refresh generation per scope, reject late old-scope results, preserve last usable data on recoverable failure, and make accepted-data age observable without claiming upstream strong consistency. Measure cost and bound retries before introducing additional automated work. [MRT010](../postmortem/MRT010-startup-api-load-fanout-and-overscoped-payloads.md) records the existing harm from startup fan-out and broad heavy-endpoint reuse.

## Verification performed

`fnm exec --using 20 node --test tests/test_auth_focus_refresh.js` passed on 2026-10-09: 18 tests, 18 passes, 0 failures. These tests build current source in memory and use synthetic clock/visibility/auth responses. Coverage includes the exact 12-minute boundary, hidden focus, in-flight event bursts, sequential cross-tab timestamp skipping, connection ownership, auth `401`, network failure followed by a later independent absence, and storage exceptions. They do not establish real OS-sleep behavior, exact data age, concurrent cross-tab exclusion, or preservation of every dirty editor.

The companion browser spec was read: [`auth_focus_refresh_counts.spec.js`](../../tests/ui/auth_focus_refresh_counts.spec.js), lines 186–509, counts document/script/auth POST requests and includes active-view refetch wiring. This bounded background research task did not run that spec, start the server, inspect credentials, or query live Jira data.

The main planning investigation subsequently ran that Chromium spec: 10/10 passed. It also ran 53 merge/controller/Team-selection unit cases and two current-source synthetic Catch Up probes. The first injected the real long-absence event after a remote Epic priority increase: the read Story moved 330.08 CSS pixels, scroll reset from 232px to 0, and the Story DOM node was replaced, with only one document request. The second held primary task responses, simulated document-hidden/window-blur state, then released them; the incoming Story summary applied while hidden and unfocused. These reproduce two failures on a synthetic surface, not a live Jira incident or real OS wake. Settled screenshots were inspected; no production screenshot/data was saved. Measurement details and limits are recorded in the [design outcome](SUPPORT-dashboard-data-freshness-design-251.md#outcome-of-this-planning-pass).
