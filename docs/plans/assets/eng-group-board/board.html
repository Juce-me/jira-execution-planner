Status follows the board, left to right — Done last

What changed and why

Mockup. Board epics are synthetic; the epic body is lorem-ipsum placeholder prose of the target length, to test how a long description behaves.

The story list is the app's story list

Built on .story-subtask-row from eng/subtasks.css. The rule: whatever is editable on a story in Catch Up is editable here, with the same classes and the same visual design — only placement may differ. So priority is button.task-priority-icon and status is button.status-pill.task-status, both real buttons opening the existing transition menus. Assignee and updated stay read-only.

Cells are table-aligned pri · name · status · assignee · updated. The priority control's fixed-width box matters: the glyphs differ in width, so a content-sized element would break the column's left edge. Measurement caught that, not the eye.

Sorting changes the order and nothing else — no group headers, no layout variant.

Consequence: adding the priority cell changes the shared row, so the ENG subtask panel must render that cell too or its grid misaligns. Subtasks have priority in Jira, so showing it there is the recommended route. Story points stay off the row — priority was asked for, story points weren't.

One focused column, centred

In progress is the default focus and sits in the middle of the screen. Every other column is a slim bar; clicking one brings it to the centre and releases the previous. The board never stacks, so the focus model is identical on a phone and a monitor.

Favourite (★) keeps one column open permanently — it can never fold, and its Fold control is withdrawn. Only one column can be starred; starring another releases the first. Star and focus are separate: when you focus a different column the starred one stays open beside it, and the focused one is still the centred one. In progress is starred by default.

The chrome is the app's, not a look-alike

Everything above the board is production: .container at its real 1040px (shared/shell.css:45), .view-filters, the sprint / group / teams pickers as .control-field + .control-label + .sprint-dropdown-toggle, search as input.search-input, and the mode switch as the real SegmentedControl — .segmented-control.eng-mode-control with .segmented-control-button.active.

An earlier revision of this page invented .shell at 1560px plus .seg, .field and .compact-inner. None existed in any stylesheet, and the mode switch is the one control two postmortems were already written about, so a look-alike here was the most likely thing to get copied back into the app. The invented shell also hid a bug: bleeding the compact header by -1.5rem pushed 10px of document overflow at 360px. Production bleeds nothing — the header sits inside the container.

The board is the only thing that bleeds past 1040px, measured against the viewport, so an open column is still 660px and the rails still run edge to edge. What changed with the real width is the chrome above it: the filter bar has less room, so it collapses a chip into +n more sooner. That is the design working, not a regression.

Sticky header and widths

Scroll down: the compact header carries the whole Catch Up control set — sprint, group, teams, mode and search — and its controls land on the same left edge as the unstuck row, so nothing shifts when it appears. It publishes its height to --compact-h, which the filter bar uses as its top, so the bar can never slide under it.

Controls and the filter bar stay at shell width and centred, exactly as Catch Up. Only the board is full-bleed, because it is a scroller.

The chosen panel keeps its width

Open columns share one fixed width, not a fit-two formula. Opening a second column no longer squeezes the one you are reading — the extra column runs off the frame instead, which is fine because the board scrolls. When something is off-frame, the edge shows how many columns are out there and clicking it brings the next one to the centre.

Horizontal scroll, measured

The board bleeds to the full viewport rather than the shell's 1560px cap, so a wide display actually buys you columns. Padding is computed per focus so the centre is reachable without over-scroll. Centring is exact — 0px off for every column at every width tested.

  • 2560px — no scroll at all; all seven columns fit.
  • 1920px — scroll only for To do, Analysis, Ready to start and Done.
  • 1440px — scroll for everything except the default focus.
  • 420px — scrolls, still one row, still centred.

Epic ordering and people

Cards sort by PRIORITY_AXIS index, so Blocker is at the top of every column and Trivial at the bottom. Story points stay. Assignee and Delivery Owner (customfield_11147, type user) are both labelled on the card: the field is set on 39% of epics and, where set, names someone other than the assignee 90% of the time — so it is not a duplicate, and the unset case reads Not set rather than vanishing.

Catch Up: same bar, different subject

Switch the mode control to Catch Up. The bar, the chips and the popover are the same component; only the facet set and the subject change. Board filters epics and has no status facet because status is the column. Catch Up filters stories and keeps status, because a list has no columns.

Today Catch Up's statusFilter is one select spanning status, priority and totals, so "In Progress and high priority" cannot be expressed. Splitting it into two orthogonal multi-selects makes it expressible — try Status = In Progress + Blocked with Priority = Blocker, Critical, Major.

The four Display toggles are subsumed, not ported: with Status a real multi-select, "hide done" is unticking Done. Four controls disappear rather than getting restyled.

Status options read in board-column order, so the facet follows the workflow. Statuses with no story in scope are absent, not shown at zero — three are missing here for that reason. An epic group with no matching story is hidden entirely, and the count is the real filtered result rather than a sum of facet counts.

Dragging a card moves the epic

Drag a card onto another column — open or folded — and the epic's status changes. It is a second trigger for the transition the app already performs, not a second mechanism: same options call, same write route, same StatusTransitionMenu, same optimistic patch and refresh.

A column is a set of statuses, so the drop has to resolve which one. One status transitions straight away; several open the menu scoped to that column — drop on Done here and you are offered Done, Killed, Incomplete and nothing else. Only transitions Jira actually offers are eligible, so the menu can never propose a move Jira would reject. Drag CORE-27499 onto Done to see the refusal: nothing moves, the card flags, and the reason is announced.

The card does not move on drop — it moves when the write succeeds. The source column is not a drop target and is never highlighted, because dropping an epic where it already is would be a no-op. Counts, story points, bar heights, the shared scale and Min/Max breach all re-derive afterwards.

Drag is never the only path. The status pill in the epic panel stays the click target and the keyboard route; a pointer-only status change would be an accessibility regression.

Min / Max warn, they never block

Thresholds are set per column in Group Board settings. They control nothing: no transition is prevented and no save is blocked. When a column's epic count falls outside its range the column glows red and its header states the breach — here In progress is 6 over max 20. A folded column glows too, so a breach is visible without opening it.

Deliberately not a limit: the work is already in that state in Jira, so refusing to show it would only hide the problem. The glow is the signal, and the count stays truthful.

Slimmer bars, louder labels

Bars went 58 → 36 px and the vertical label went 0.55 → 0.74 rem at weight 600. The bar hangs from the top by epic count; the full track equals the largest column, stated above the board.

Rotated labels read bottom-to-top. writing-mode: vertical-rl on its own runs top-to-bottom, so the label is rotated 180°. Top-to-bottom would only be right for stacked upright letters, which is a different treatment.

Long descriptions clamp

The synthetic placeholder body is about 2,600 characters with six headings and nested lists — roughly 40 lines unclamped, which would bury the story list. The placeholder above matches that shape. It renders as structured text, clamped to about 11 rem with a fade and Show full description. The panel caps at 92vh and scrolls internally, so the story list stays reachable at any description length.

This needs a data change: fetch_epic_details_bulk doesn't return description today, and Jira serves it as ADF, not HTML — so it needs adding to the payload plus an ADF-to-text render, or a lazy fetch when the panel opens.

Filters

Delivery track is multi-select with two options, both ticked: Committed and Flexible. Both ticked is the neutral state and admits everything, including the epics with no track at all — of 3000 sampled, 2258 have none, so a state that only admitted the two real values would hide three quarters of the board. That is why its heading total reads the full scope rather than 8 + 14: no option represents untracked work, so summing the options would under-report by 65 epics. Every facet heading shows what it admits. Priority and Projects stay multi-select with the last option locked.

A chip states the shorter truth. The first version listed everything ticked, which for Status meant eight names in a 565px chip, and the bar wrapped onto three rows — the thing this design replaces. Now: fewer excluded than included reads Status hidden Killed, otherwise Status only In Progress, capped at two names plus +n. The full list is in the chip's tooltip and in the popover.

The bar is one row and sized to its content. It never wraps and never grows taller: the chips lane clips and collapses trailing chips into one +n more that opens the popover. Measured at 1440 / 960 / 360: 42px, 42px, 80px. Below 720px the view controls may take a second row, never a third — and the bar deliberately does not scroll horizontally like the controls row above it, because an overflow container would clip the popover anchored inside it.

No status facet on the Board, because status is the column. Catch Up keeps its existing status filters unchanged — it is a list, not a board, so filtering by status is meaningful there.

The subject differs, and that matters more than the facet set. Board filters resolve against epics; Catch Up filters resolve against stories. Search is the only one whose subject doesn't change. So counts are not comparable between the two surfaces and no facet state should carry across when you switch modes. The popover says which it is.

Facet order puts Delivery track last — coarsest cut, most often left alone. And an option with zero items in scope is hidden, not shown at zero: Trivial is absent here because no epic in scope has it. That makes counts functional rather than cosmetic — a wrong count would hide a real filter.

Field provenance

This page is meant to define filtering and workflow, so every value below is either a real Jira field or a stated derivation. Nothing else is present.

  • Epic / story — key, summary, status.name, priority.name, assignee.displayName, updated (raw ISO 8601).
  • storyPoints — customfield_10004. track — customfield_35024, values Committed / Flexible / null.
  • deliveryOwner — customfield_11147 "Delivery Owner", type user, .displayName. Unambiguous: it is the only field with that name, unlike "R&D Owner" and "Rnd Owner", which have four duplicates each.
  • Updated display — formatSubtaskUpdatedDate (subtaskProgressUtils.js:26) renders YYYY-MM-DD. Not a relative day count.
  • Priority vocabulary — PRIORITY_AXIS verbatim: Blocker, Critical, Major, Minor, Low, Trivial. Jira's highest/high/medium/lowest are aliases and do not occur on epics; probing 2000 epics returned only those six. There is no Medium.
  • progress — derived client-side from the epic's own stories, in buildStorySubtaskProgress's shape { total, done, inProgress }.
  • Column counts — derived: epics and summed story points per column, for the selected sprint and group.
  • Composer per-status counts — work items on board 1042, the figures from your own config screen.
  • Priority glyph and tint — placeholders for the app's real SVG marks (renderPriorityIcon); tints are the existing .task-priority-icon[data-priority] colours.
  • Facet counts — illustrative, scaled to 87 epics from the real distributions probed (priority split, 4 unassigned, 75% untracked). The facets and their vocabularies are real; the integers are placeholders.

Removed as invented, so no one builds against them: a days integer on stories (there is only updated); a numeric priority rank; a stale flag on epics (staleness belongs to the alerts panel, not the card); per-assignee avatar colours (the app renders assignee as plain text); a Medium priority bucket; and the sort options Priority and Last updated, which you did not ask for. Sorting is Assignee-then-status, Status, Assignee.
