## Proposed behavior and design

### 1. Immediate display; background write; confirmed ordering

Planning joins the **existing single-issue lifecycle** in `useEngPriorityTransitions` and `useEngStatusTransitions` (optimistic patch, per-key pending set, rollback, scope guard, no success refetch outside Board); do not build a parallel lifecycle. The token, overlay and lock machinery below layers onto it.

For a normal priority/status menu choice:

1. Capture the issue key, the full prior field value read from the loaded issue at submit time, target, Department/Sprint/surface identity and a mutation token. For priority capture the full value, not only its name, so rollback preserves IDs/icon metadata (today's fallback target carries empty prior values).
2. Atomically reserve that field/key before patching. Reject another action on the same key/field while it is pending or unconfirmed; never silently omit it. Different fields retain independent tokens and original values, while the shared queue still serializes network jobs by issue key. Reservation, confirmation and settlement use a **non-bumping** edit-state path (below). Mark only the reserved issue pending and patch its display through `applyLocalEngIssueField`. Reuse active arrays, Epic metadata and expanded subtasks; distinguish optimistic display from confirmed group-cache authority as specified below. Do not create a Planning-owned copy of Jira tasks.
3. Submit exactly that key through the existing shared queue: four concurrent jobs maximum, serialized for overlapping keys. Other issues remain editable. Closing or moving between menus must not redirect a response.
4. Until completion, display the new field but sort/filter that pending field using its captured prior value. Project the pending originals into **every** layer that reads the field before selection, not only `visibleTasks`/hierarchy: `engFilterScopeTasks`, `scopedTasks`, `baseFilteredTasks`, `selectionTasks` and the Status facet counts. Otherwise an optimistic closed status (default hidden `Killed`) prunes and persists the deselection of a selected Story that a rejection cannot restore (this already happens for Table status). Keep per-key/per-field snapshots so one completed edit can settle while another remains pending. Keep nonedited fields live.
5. On per-key `success`, or an `already_in_*` result that passes the staleness rule below, record the confirmed field through the edit-state observation mechanism and apply the returned value to that key. Then release its ordering snapshot and settle order locally: **Planning List children are re-sorted on a copy of each Product/Tech lane array with the same `sortTasksByPriority` the loader uses, so local order equals what a reload produces** (do not sort the merged lanes in the hierarchy builder, and do not change the shared comparator). Pending groups stay stationary because arrays are patched but not re-sorted until confirmation. The re-sort runs from the Planning surface only; Catch Up and Board keep their no-reorder behavior. Outer Epic/initiative order uses the pending-original projection (Task 6). Table retains its selected multicolumn criteria, blank placement and immutable-ID tiebreaker. A change must not activate an unselected sort criterion.
6. On a definitive rejection, restore the token's captured field **only where the issue still holds this token's optimistic value** (a newer remote read is not overwritten) and release its snapshot; no success reorder or whole-scope fetch. On an unconfirmed outcome, restore the prior display only as a provisional value, keep its pre-edit ordering/membership and a per-field/key unconfirmed lock, and show the existing inline result/error area as unconfirmed. Closing a menu must not erase the lock. Require explicit app Refresh acknowledgement before another edit of that field; never claim Jira rolled back or automatically replay the write. A queued job aborted before dispatch (scope change) restores its optimistic value; a dispatched job that meets a `401` follows the terminal-auth rule below.

Outcome classification must inspect each requested key, including HTTP-200 batch responses. Verify every code against the services before implementing; cover each in a table-driven test in both directions.

- **Confirmed:** exactly one matching result with `success`, or `already_in_*` that passes the staleness rule, and a usable authoritative value. Status may use `currentStatus` for already-in-status. Priority is confirmed by `targetPriority.id` equal to the requested id and takes its full value (icon, color, rank) from the options-catalog entry for that id. Do not require `targetPriority.name`: the service can return an empty name when catalog resolution fails, and `fromPriority`/`toPriority` are name strings only.
- **`already_in_*` staleness rule:** the result comes from an eventually consistent Jira search snapshot. Treat it as Confirmed only when this session has no earlier confirmed or unconfirmed write for the same key/field since the last committed read that carried raw evidence for it; otherwise classify it Unconfirmed (lock, Refresh). Test A→B (success) then B→A answered `already_in_A` from a stale snapshot.
- **Definitive rejection** (no write was applied): a queued job's pre-dispatch `AbortError`; HTTP 400 `invalid_json`, `issue_keys_required`, `invalid_issue_key`, `too_many_issues`, `target_status_required`, `target_priority_required`, `invalid_priority_id`; HTTP 403 `csrf_required`, `jira_oauth_required`; 503 `config_storage_unavailable`; per-key (HTTP 200) `transition_not_available`, `transitions_unavailable`, `invalid_transition`, `transition_forbidden`, `transition_conflict`, `jira_auth_error`, `priority_conflict`, `priority_forbidden`, `issue_not_found`. Validation at the base found these raised before a write or reported by Jira as a 4xx rejection. Reuse the vocabulary and dispatched/unknown tracking already in `useEngIssueFieldEdits.js` (`KNOWN_REJECTION_CODES`, `dispatched`, `write_outcome_unknown`) rather than adding a second one; the CSRF-token GET precedes the POST, so a thrown error alone is not proof of dispatch.
- **Unconfirmed:** per-key `transition_failed` (also returned by pre-write GET failures; the resulting false-positive lock is accepted and cleared by Refresh), `transition_timeout`, `priority_update_failed`, `priority_update_timeout`; HTTP 502 `jira_transition_failed` / `jira_priority_update_failed` (they also cover an unhandled worker exception after dispatched writes); generic post-dispatch transport/5xx failures; unknown codes; missing/duplicate/mismatched results; unusable success values. Never treat HTTP 200 or aggregate counts as authority. Settle each key independently.
- **Terminal auth:** any application API `401` triggers the existing terminal sanitized recovery. That includes `missing_oauth_scope`, which the routes return as `401 auth_required`, and a received 200 that the client converts to `AuthenticationRequiredError` because another request locked the app. Mutation tokens are **abandoned**: no rollback, no lock, no cache write, no replay.

**Unconfirmed lock and Refresh barrier.** Record the lock as `issueKey::field` for the workspace principal. It persists across scope visits (A→B→A keeps it) and is not bound to one visit. Normal reads (alerts, readiness, Sprint re-entry, cache hits) never clear it: they record the raw read value as the base while the display keeps the provisional prior value. Carry an explicit operator-Refresh request ID from the Refresh button through `loadMeasuredGroupTasks` / `loadGroupTasks` to `useEngSprintData.fetchTasks` and the final Product/Tech lane commits. `refreshActiveViewFromJira` also serves the long-absence listener and has early returns (EPM, strict Board, Board scope, unready Sprint catalog) that never load tasks, so split the entry point: only the Refresh button's loading branch issues an ID, and update the source pin in `tests/test_frontend_api_source_guards.js` without weakening its ordering assertion. That loader must preserve validated raw key/field evidence alongside its retained read token and acknowledge accepted current-scope commits before final token disposal; reconciled display arrays, aggregate outcome strings and `forceRefresh` alone are not raw authority. Automatic long-absence refresh, normal loads and Board refreshes never acquire explicit-operator provenance. Clear a lock only after a successful explicit Refresh started after settlement has committed a validated snapshot that (a) contains the key with raw evidence for the field, or (b) is a successful complete load of the lock's scope that omits the key (the issue left scope; no row remains to protect). Failed, aborted, superseded, other-scope, older or partial refreshes leave the lock intact with recoverable guidance. Sign-out or a principal change clears all locks. Do not clear a lock on the Refresh click or on a successful HTTP status. Unknown status/priority values must not be entered as confirmed observations. The acknowledging load must send `refresh=true` (the loader already does); the server clears its caches only when `succeeded > 0`, and search lag can still return a pre-write value, in which case the lock simply remains.

**Scope fencing.** All UI feedback (banners, menus, the inline result area) compares the captured scope token with the current scope, including Planning, and includes a monotonically increasing scope-visit generation so switching A → B → A cannot revive an old A feedback or menu callback. Abort queued jobs on scope changes (the existing abort controllers and `shouldStart` already do). **Value settlement is keyed by issue key and token, not by visit:** an already-dispatched job that finishes after the user left and returned patches, by key, the mounted arrays and every cached group snapshot of its origin Department/Sprint under the same principal/context. Success writes the confirmed value; definitive rejection restores the prior value only where the field still equals the token's optimistic value; unconfirmed settlement writes no value (the lock persists). A scope switch must never leave the origin scope showing a value that contradicts a settled write: a cache hit on return skips the reload, so a visit-fenced patch would leave it stale until Refresh. When a cached snapshot is restored while a token for it is still pending, re-apply that token's pending display overlay. Preserve terminal global `401` recovery; never unlock or replay locally. Declare `usePlanningIssueEdits` after the existing issue-edit/group refs and the available primitive context/Department/Sprint/view state (at the base the primitive inputs are declared by about line 797, `issueEditStateRef` at about 962, `selectedSprintInfo` at about 990 and `activeGroupTeamIds` at about 2415, all before the first consumer, the group-cache effect at about 2873), before cache, readiness, filter and hierarchy consumers. Use the **single shared scope-key function** the mutation hooks use (`mutationScopeKey` reads `strictBoardData`, declared later; do not create a second identity). Derive its surface from already-declared view inputs; do not read the later `statusTransitionSourceSurface` or later mutation/editor hook return values. Its transient reservations, held-editor keys, refresh barriers and render revision wrap the existing edit-state authority; it owns no copied task arrays. Later hooks receive its lifecycle callbacks.

**Edit-state authority.** Extend `createEngIssueEditState` reconciliation to status/priority and connect token reservation, dispatch, settlement and confirmation to it through a **non-bumping** path. `beginMutation`/`confirmMutation`/`markUnknown` increment `generation`, which invalidates in-flight aggregate reads and re-triggers `fetchDependencies`, i.e. a mutation-triggered read. Add a non-bumping reservation plus `observeConfirmed(key, field, value)` for Planning status/priority only; the existing editors keep their semantics. Status/priority must not use the `reconcileIssues` branch that records a raw read value as an observation. Record the raw read value as the **base** before any overlay is applied, so rejection ("restore captured prior") and overlay removal never overwrite a newer remote read. Keep a token-owned pending display overlay over incoming current-scope reads while queued/saving, separately from the original-value sort/filter projection. A read resolving before the write must not erase the optimistic field. After settlement, confirmed observations protect against older reads; rejection/unconfirmed settlement removes the desired-value overlay without recording it as confirmed. A genuinely newer validated explicit read remains authoritative. Reconcile flat/nested projections without manufacturing absent fields.

**Group caches** must contain authoritative values, not optimistic display. For status/priority, introduce a phase/token argument at `applyLocalEngIssueField` (existing other-field callers keep their current semantics): optimistic/provisional phases update current display but do not publish desired values into group caches. At group snapshot commit, strip token-owned pending display overlays back to their authoritative baseline, or decline caching that affected snapshot if it cannot be separated. A never-dispatched cancellation releases its token without leaving an optimistic cache value. Settlement of a job that outlives a scope switch follows the key-based rule above (`applyLocalEngIssueField` already patches every cached group by key). Returning to the original Department must never restore an unconfirmed desired value as authoritative and must never leave a settled value stale.

Prove queued cancellation, scope switch-away/return with success/rejection/unconfirmed outcome **including success arriving after return without a reload**, read settlement while queued/saving/after settlement, and cache restoration after the **last** `finishRead` prunes observations. Do not retain observations indefinitely as a workaround. Preserve other editable-field contracts and aggregate-read invalidation behavior.

**Invalidation.** No successful Planning mutation may invoke `onPrioritySuccessRefresh`, `onTransitionSuccessRefresh`, `loadMeasuredGroupTasks`, a task-list reload, review refresh or readiness reload. **Change the concrete invalidation seam:** `invalidateAlertsAfterEdit` falls back to `rearmCatchUpAlerts`, which increments `catchUpAlertRefreshNonce`, supplied as `useStoryReadiness.refreshRevision`; a Planning edit therefore refetches readiness immediately and blanks its snapshot. Planning must instead record lazy invalidation without advancing the nonce. A priority edit sets **no** marker (priority feeds no alert rule). A status edit sets a dirty marker that preserves the existing re-arm contract (it sets `catchUpAlertLoadRef`, `catchUpAlertForceRefreshRef` and `catchUpAlertVersionRef`, not the nonce). The marker has two consumers: explicit app Refresh already calls `rearmCatchUpAlerts` (so it clears the marker), and the **first Catch Up activation** after the marker was set calls the existing rearm path once; `useStoryReadiness` has no other view-activation path, so this effect is specified here. Catch Up/Board behavior is unchanged. Update the pinned guards (`tests/test_dashboard_alert_source_guards.js`: the `rearmCatchUpAlerts` body, exactly 4 call sites, the `invalidateAlertsAfterEdit` body and callback strings) and `tests/ui/eng_alert_loading_order.spec.js` ("Planning mutation re-arms deferred alerts for the next Catch Up entry", which currently waits for the whole-scope reload being removed). Retain server cache invalidation: invalidating a cache does not require downloading the list again. Parent subtasks already use the existing local patch/summary helpers.

**Readiness.** Add the same pending/confirmed read fence to `useStoryReadiness` department commits and its readiness-only Epic display. Removing the Planning rearm reload removes the only thing that refreshed a readiness-only Epic's status in Planning, so patch it locally: `applyStoryReadinessIssueField` accepts status and priority for Epic rows (it allows only summary/team/assignee today; the dashboard patches readiness for priority only). This lands in Task 2 with the invalidation split. Planning edits never call `loadEpic` (`alertCallsFor`/`alertCallsForEdit` return nothing outside Catch Up), so the retained-handle contract applies only to a Catch Up per-Epic response that lands after a Planning edit in the same session (a mode switch during the request): the response retains its read handle until `useEpicRefresh.recheckEpicAlerts` merges or discards it, and the consumer finalizes it in `finally`, including stale alert-version/epoch/scope, failures and missing merge callbacks. Loaded child arrays do not prove complete readiness membership/actionability: retain the last validated readiness requirements conservatively until the next permitted authoritative read, mark derived readiness dirty, and do not manufacture complete counts or hide readiness-only rows based on an optimistic edit.

### 2. One issue at a time; no Planning bulk status

Operator decision D2 (2026-10-08): Planning status changes are single-issue only.

- Every Story pill in List and Table changes the clicked Story regardless of checkbox selection, including no selection, a selection that includes the clicked Story, or one that excludes it. `IssueCard` passes `{ singleIssue: true }` and the explicit key from the Story pill, and a Planning submit without a key is refused (as Board already refuses it). All routes resolve the current user's OAuth Jira context and existing workspace/site boundary. Writes use signed-in-user Jira REST only; no Basic, service-token or Home write path. Basic/passive profiles retain their current edit gates.

| --- | --- | --- |
