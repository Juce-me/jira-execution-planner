## Proposed behavior and design

### 1. Immediate display; background write; confirmed ordering

Planning joins the **existing single-issue lifecycle** in `useEngPriorityTransitions` and `useEngStatusTransitions` (optimistic patch, per-key pending set, rollback, scope guard, no success refetch outside Board); do not build a parallel lifecycle. The token, overlay and lock machinery below layers onto it.

For a normal priority/status menu choice:

1. Capture the issue key, the full prior field value read from the loaded issue at submit time, target, Department/Sprint/surface identity and a mutation token. Story priority is `{ name }` only and Epic values are flat strings, so rollback restores that shape; today's fallback target carries empty prior values.
2. Atomically reserve that field/key in the single reservation registry before patching; the registry belongs to the edit-state (below). Reject another action on the same key/field from **any** surface (Planning, Catch Up, Board) while it is pending or locked. Today each hook's pending set is cleared on scope change, so a Planning-pending key could be edited from Catch Up. Different fields retain independent tokens and bases, while the shared queue still serializes network jobs by issue key. Mark only the reserved issue pending and patch its display through `applyLocalEngIssueField`. Reuse active arrays, Epic metadata and expanded subtasks; distinguish optimistic display from confirmed group-cache authority as specified below. Do not create a Planning-owned copy of Jira tasks.
3. Submit exactly that key through the existing shared queue: four concurrent jobs maximum, serialized for overlapping keys. Other issues remain editable. Closing or moving between menus must not redirect a response.
4. Until completion, display the new field but sort/filter that pending field using its captured prior value. **Project pending originals once, at the head of the Planning filter chain:** derive a Planning-surface filter-view array from `capacityTasks` in which each pending issue carries its original value, and evaluate on that view the facet counts (about `dashboard.jsx` 4009), `baseFilteredTasks` (about 4266), the `admits*` checks, the Accepted/To Do/Postponed/Awaiting toggles (about 4886–4918 and `planningSelectionActions.js` 109–130) and the selection pool; map back to the display (optimistic) objects by key at `visibleTasks` so cards render the new value. `engFilterScopeTasks` reads only search and team and is not a projection point. Projecting only some layers makes counts and `admits*` disagree, and a zero-count option is hidden, so the pending Story would leave the list at once. Capacity buckets and alerts keep reading the loaded arrays, as they already do for Table status. Catch Up filtering is unchanged. **Selection guarantee:** while a closed status is pending, and after its rejection, a selected Story's selection is untouched. After a *confirmed* closed status (default hidden `Killed`) the pool drops the Story exactly as a reload would and the selection effect prunes it; do not retain it. Keep per-key/per-field snapshots so one completed edit can settle while another remains pending. Keep nonedited fields live.
5. On per-key `success`, or an `already_in_*` result that passes the staleness rule, record the confirmed field through the edit-state and apply the returned value to that key. Then release its ordering snapshot and **settle List order**: re-sort the shown Product/Tech lane arrays (a copy of each, with `sortTasksByPriority`; Planning surface only; not the `loaded*` arrays, matching the `useEpicRefresh` precedent) on a view in which every *other* still-pending Story carries its original priority, then map back to the display objects. One confirmation therefore never moves another pending Story early, and a later rejection moves nothing. Equal-priority Stories keep their current relative order (stable sort); a reload orders ties by server order, so "equals a reload" is asserted for non-tied Stories only. A confirmation that lands while off the Planning surface (Catch Up shares the arrays and never reorders) or after a scope switch sets a **reorder-due** mark, and the same pure helper re-sorts the origin Department's cached snapshot at settlement; the mark is consumed on the next Planning entry or cache restore. The loader applies the pending overlay *after* its own sort (or exempts pending keys), so a Refresh while an edit is pending never moves the pending Story. Outer Epic/initiative order uses the pending-original projection (Task 6). Table retains its selected multicolumn criteria, blank placement and immutable-ID tiebreaker. A change must not activate an unselected sort criterion.
6. On a definitive rejection, settle the display to the issue's **base** (initialised to the captured prior and advanced by raw reads, see Edit-state authority) through an `expect` predicate: apply it only where the current value still equals this token's optimistic value, compared by normalized name (reference or id comparison never matches). The local-update helpers (`applyLocalIssueFieldUpdate`, `patchSnapshot`, `applyLocalSubtaskFieldUpdate`) are unconditional today and `strictBoard`/readiness `applyIssueField` take no predicate, so the predicate is new. Release the snapshot; no success reorder or whole-scope fetch. On an unconfirmed outcome, show the captured prior as a provisional value, keep its pre-edit ordering/membership and a per-field/key lock, and show the existing inline result/error area as unconfirmed. Closing a menu must not erase the lock. Require explicit app Refresh acknowledgement before another edit of that field; never claim Jira rolled back or automatically replay the write. A queued job aborted before dispatch restores its optimistic value, **unless** `readPendingAuthenticationRequired()` is true: an auth lock also aborts queued jobs, and that case is the terminal-auth rule below, not a restore.

Outcome classification must inspect each requested key, including HTTP-200 batch responses. Verify every code against the services before implementing; cover each in a table-driven test in both directions.

- **Confirmed:** exactly one matching result with `success`, or `already_in_*` that passes the staleness rule, and a usable authoritative value. Status may use `currentStatus` for already-in-status. Priority is confirmed by `targetPriority.id` equal to the requested id and takes its full value (icon, color, rank) from the options-catalog entry for that id. Do not require `targetPriority.name`: the service can return an empty name when catalog resolution fails, and `fromPriority`/`toPriority` are name strings only.
- **`already_in_*` staleness rule:** the result comes from an eventually consistent Jira search snapshot. Treat it as Confirmed only when this session has no earlier confirmed or unconfirmed write for the same key/field since the last committed read that carried **raw evidence** for it (the key/field present in the raw `data.issues` or `data.epics` of an accepted lane commit; not a cache hit and not a projected display array). Otherwise classify it Unconfirmed (lock, Refresh). Test A→B (success) then B→A answered `already_in_A` from a stale snapshot.
- **Definitive rejection** (no write was applied): a queued job's pre-dispatch `AbortError` (outside an auth lock); HTTP 400 `invalid_json`, `issue_keys_required`, `invalid_issue_key`, `too_many_issues`, `target_status_required`, `target_priority_required`, `invalid_priority_id`; HTTP 403 `csrf_required`, `jira_oauth_required`; 503 `config_storage_unavailable`; per-key (HTTP 200) `transition_not_available`, `transitions_unavailable`, `invalid_transition`, `transition_forbidden`, `transition_conflict`, `jira_auth_error`, `priority_conflict`, `priority_forbidden`, `issue_not_found`. Validation at the base found these raised before a write or reported by Jira as a 4xx rejection. **Any error thrown after the job starts is Unconfirmed unless it carries one of these exact HTTP status+code pairs:** the CSRF-token GET precedes the POST and nothing marks the send, and `jiraIssueApi.js` is not changed. The classifier is new: `KNOWN_REJECTION_CODES` in `useEngIssueFieldEdits.js` contains none of the transition or priority codes, so reuse only its `dispatched`/`write_outcome_unknown` vocabulary.
- **Unconfirmed:** per-key `transition_failed` (also returned by pre-write GET failures; the resulting false-positive lock is accepted and cleared by Refresh), `transition_timeout`, `priority_update_failed`, `priority_update_timeout`; HTTP 502 `jira_transition_failed` / `jira_priority_update_failed` (they also cover an unhandled worker exception after dispatched writes); generic post-dispatch transport/5xx failures; unknown codes; missing/duplicate/mismatched results; unusable success values. Never treat HTTP 200 or aggregate counts as authority. Settle each key independently.
- **Terminal auth:** any application API `401` triggers the existing terminal sanitized recovery. That includes `missing_oauth_scope`, which the routes return as `401 auth_required`, and a received 200 that the client converts to `AuthenticationRequiredError` because another request locked the app. Mutation tokens are **abandoned**: no rollback, no lock, no cache write, no replay. Abandonment freezes the pending-original projection until the navigation completes, so the selection effect cannot persist a pruned selection for an optimistic closed status. Recovery is a page navigation with a stored resume snapshot, after which arrays and caches are rebuilt from reads.

**Unconfirmed lock and Refresh barrier.** Record the lock as `issueKey::field` plus its origin Department/Sprint scope, for the workspace principal. Locks are in memory, so a reload or the terminal-auth navigation clears them; no client signal for a principal change exists short of that, and `AUTH_SESSION_REFRESH_EVENT` must not be used (it fires on every focus refresh). A lock persists across scope visits (A→B→A keeps it). Normal reads (alerts, readiness, Sprint re-entry, cache hits) never clear it: they advance the base while the display keeps the provisional prior value.
- **Release only by raw evidence from the lock's own origin scope, per issue kind, and only through an explicit operator Refresh of that scope.** A Story: the raw `data.issues` row of an accepted lane commit carries the key/field. An Epic: the raw `data.epics` entry (flat strings; `epicsInScope` has no priority). A Subtask is not in `data.issues`, and Refresh does not reload subtasks, so a Subtask lock releases only when its parent's subtask list is reloaded with raw evidence through the existing retry/expand path, never on Refresh. There is **no** "complete load omitted the key" rule: the task list is capped at 250 issues and the loader receives neither the cap nor a completeness flag, so absence proves nothing. A key outside scope keeps an inert lock until a Refresh of its scope sees it.
- Release is evidence-presence only and compares no values: afterwards the display adopts the read value, which under search lag can be the pre-write value while Jira holds the new one. This is an accepted residual risk; a value rule would deadlock genuinely failed writes.
- **Visible state.** When a menu opens for a locked key/field, the existing menu error area shows a concise "change not confirmed, Refresh to verify" message and the submit is refused (the duplicate-submit guard no longer returns silently). The pill gets no extra persistent text; Planning Table chrome allows none.
- **Refresh provenance.** Carry an explicit operator-Refresh request ID from the Refresh button through `loadMeasuredGroupTasks` / `loadGroupTasks` to `useEngSprintData.fetchTasks` and the final Product/Tech lane commits. `refreshActiveViewFromJira` also serves the long-absence listener and has early returns (EPM, strict Board, Board scope, unready Sprint catalog) that never load tasks, so split the entry point: only the Refresh button's loading branch issues an ID, and update the source pin in `tests/test_frontend_api_source_guards.js` without weakening its ordering assertion. Retain validated raw key/field evidence alongside the read token (as a property that leaves loader return values unchanged for other callers) and acknowledge only fields present in an accepted lane's raw result; reconciled display arrays, aggregate outcome strings and `forceRefresh` alone are not raw authority. Product succeeding while Tech fails acknowledges only the Product lane's keys. The acknowledging load needs a **new** current-attempt guard (latest request ID plus the captured scope and visit): the Refresh load passes no `shouldApplyResult` today and `activePerformanceLoadRef.cancel()` cancels only measurement. A consequence is that an older Refresh load is ignored; state this behavior change in the feature doc. Automatic long-absence refresh, normal loads and Board refreshes never acquire explicit-operator provenance. Do not clear a lock on the Refresh click or on a successful HTTP status. Unknown status/priority values must not be entered as confirmed observations. The acknowledging load sends `refresh=true` (the loader already does); the server clears its caches only when `succeeded > 0`, and search lag can still return a pre-write value.

## Residual risks

- Operator decision D2 removes the existing List bulk status action; users who relied on it lose it (documented). A confirmed multikey action can return later as its own plan.
- Row transforms can interact with horizontally pinned cells and docked chrome; actual browser geometry, a mid-animation ink check and screenshots are required.

Explicit Refresh remains the reconciliation path. Read-after-write limits: the routes clear server caches only when `succeeded > 0`, so an unconfirmed write leaves caches warm, and Jira search is eventually consistent. Lock release is evidence-presence only, so after release the display adopts the read value, which under search lag can be the pre-write value while Jira holds the new one.
