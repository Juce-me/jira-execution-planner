## Evaluation and confirmed decisions

The spreadsheet is a reference for compact comparison and review inputs, rather than a column-for-column specification. Its useful additions are a review estimate and a product-ranking input beside Jira facts. Repeating the selected Sprint, a single selected Team, or both textual and numeric versions of Jira priority consumes width without adding information. A custom review estimate must remain separate from Jira Story Points.

Confirmed by the user in this planning session:

- The switch belongs **only in Planning**, immediately beside **Open selected stories in Jira**, using `planning-action-button planning-icon-button`.
- While active, the table replaces Planning's shared Epic/Story list below the Planning panel. Catch Up keeps its current layout; this is a Planning layout, not another ENG mode.
- Custom column definitions and values are shared within the **workspace and sprint**.
- The first version includes new Jira **summary and Team** editing, plus **assignee** editing. Reuse the existing assignee and Story Points pipeline; do not defer summary/Team as an assumed scope reduction.
- The existing header owns Sprint and Teams. More than one Team in scope warrants a Team column; otherwise avoid repeated scope fields.
- Only the spreadsheet region may use the available browser width. Keep the header, Sprint/Teams controls, Planning capacity panel, and filters at their existing centered width in both layouts. Keep columns and cell padding compact; do not stretch a short table to fill unused width. Scroll horizontally when added columns exceed the available space.

Recommendation: implement a native table and the existing editors. React, the current UI controls, and existing persistence libraries cover this feature; no spreadsheet/grid dependency or formula engine is needed for the requested behavior.

### Custom values, totals, and sorting

- A column has a stable generated ID, label, row kind (`epic` or `story`), type (`number` or `text`), order, and aggregation (`sum` or `none`). Number columns sum automatically by default; the user can turn a ranking column's total off. Text columns have no numeric footer.
- Create columns through the visible **+ Add column** action: enter a name, choose Number or Text, then **Add column**. Reveal the appended column and focus its first editable cell; show a concise confirmation and the **Save review** reminder. Rename/remove and visibility/aggregation controls belong in **Columns**. The UI clearly says these definitions and saved values are shared for this Sprint. Renaming retains IDs/values. Removing archives the definition; stale writes to it fail. Changing the type of a populated column requires a new column rather than coercing existing values.
- Inputs are review data owned by this app. Show the distinction from Jira fields in column controls and editor accessible labels. Jira edits save through their existing explicit edit interaction; **Save review** sends only app review changes.
- A blank number is `null`, distinct from zero; empty inputs stay visually blank. Accept finite signed decimal values with up to three decimal places; use scaled decimal arithmetic for totals, not binary floating-point sums. Limit magnitude to `999999999.999`, labels to 80 characters, and text values to 500 characters. Reject invalid numbers without changing the saved value.
- Footer totals cover visible rows after filters, not selected Stories alone, and say **Visible total**. Custom Epic and Story values are independent: never aggregate both grains together or imply a custom Epic estimate equals its Story values. Show unsaved draft totals as such.
- Column-header click changes the primary sort; the compact Sort editor can add/reorder up to five criteria and choose direction. Numeric fields compare numerically; text fields compare naturally; empty values sort last in either direction. Use immutable Jira issue ID as the final stable tie-breaker. Removed/hidden columns cannot leave an unexplained active sort.
- Keep a row in place while its cell editor is active; apply changed-value sorting after commit/blur. Preserve keyboard focus and horizontal scroll when the order changes.

## Persistence and concurrency contract

The persisted review scope is **`workspace_id + sprint_id`**, derived from the request auth context and a validated Sprint. Department and selected Team sets are filters, not storage keys. The same issue/Sprint keeps its values after a Team or Department filter changes. Another Sprint has an independent definition/value set; no automatic copy-forward.

Proposed DB models:

- `WorkspaceSprintReview`: unique workspace/Sprint, schema version, schema revision, column definitions, shared row-kind column layouts (order/hidden), timestamps. No Jira issue summaries, people names, credentials, or copied task snapshots.
- `WorkspaceSprintReviewCell`: unique review/immutable Jira issue ID/column ID; typed value and cell revision. A stable ID survives key changes; current issue keys remain navigation information from Jira, not the canonical value key.

Cell saves compare per-cell revisions and the schema revision in one transaction. Disjoint cell edits may both succeed. A same-cell change, a renamed/archived schema revision, or a create race returns a scoped `409`; nothing in the failed batch commits. Serialize first-row creation with the unique constraint and a bounded retry. Do not solve concurrency with whole-dataset overwrites or append this payload to `/api/config`, `/api/groups-config`, Scenario drafts, or private view configuration.

**Authorization:** workspace sharing is not Jira issue permission. A values read returns only requested real issues readable through the current user's Jira context; a save verifies every affected real issue the same way. Never return all Sprint cells or trust issue IDs supplied by the browser. Use bounded batched Jira authorization reads with minimal fields, not one request per issue. These are separate from the existing task dataset load and must be counted explicitly. Column definitions are workspace/Sprint shared metadata. An absent or inaccessible issue receives the same unavailable result, with no saved cell contents.

Do not implement a new paging convention or reuse project-search `startAt` for issue search.

No new polling or SSE system. Read review data on first table activation and a new Sprint/visible issue set; reuse already-read cells for sorting and filtering. Fix: each heading is wrapped in `.planning-review-head` (flex, `space-between`) with the grip on the edge opposite the alignment edge (left for numeric, right for text, DOM order matching visual order); `.planning-review-input` is `100%` wide (see the correction below); `.planning-review-capacity .epic-stat-toggle` gets `margin: 0`. The 100px custom column floor is unchanged: a 90px trial widened the column when a maximum-size value made the footer total wider, which the existing stable-geometry test caught.

Verification: a new per-column audit test (both modes, grip side, grip/label vertical centring) failed against the old order (`Status` heading 13.2px off) and passes now; the same audit run in the real dashboard fixture, with real priority icons and status pills, shows every column within 1px (Priority icon 1.0px, from the icon artwork). Both Planning specs passed 57 cases on Chromium in three consecutive runs at six workers; the popup, geometry and alignment cases (21) passed headed in Firefox and WebKit. Popovers now take focus in a layout effect instead of the next animation frame, which removed an intermittent Escape-immediately-after-open failure under load.

Correction (user report from Firefox, same day): the first version of this fix let the input box extend 5px past the cell content (`calc(100% + 10px)`, `-5px` margins) so its text lined up with the heading. Measured in Firefox, the box then started at 2px while the grip started at 7px, so it poked past the grip and the label. The bleed is removed: the input box now equals the heading span (grip edge to label edge, 86px in a 100px column) and its text keeps the field's own 5px inset. The alignment audit now measures an input by its box and asserts `inputOvershoot < 1px`; it fails against the bleed in Firefox (`Effort` overshoot 5px) and passes in Chromium, Firefox and WebKit.

Observation, not changed: where a text column is followed by a numeric column their grips sit side by side (for example Priority then Story Points); revealing grips on header hover would remove that cluster but makes reordering less discoverable.

### Number precision, tooltips, headers and the layout-save fix (2026-10-01)

Number precision (user decision: at most one decimal, no `.000`): `validateReviewValue` and the backend `normalize_value` accept at most one decimal place (largest value 999,999,999.9); `parseReviewNumber` keeps reading three decimals so values stored earlier still total and sort exactly, and `formatReviewDisplay` shows them without trailing zeros (`12.000` -> `12`). The canonical stored form is unchanged (three decimals), so there is no schema change. K/M abbreviation was not used: the widest valid value (11 characters) fits the field without clipping, and abbreviating an editable value would lose precision. Supersedes the earlier "three decimal places" statements in this plan.

Status pill tooltip (user: remove redundant hover): `StatusPill` no longer defaults `title` to its own label; it adds a tooltip only when a caller passes `title`. The two EPM label chips that can clip (`epm-project-board-label-pill`, `epm-duplicates-project-label`) now pass their full text explicitly. The source guard in `tests/test_epm_view_source_guards.js` was updated to the new contract.

Layout save failure (user: "Save review" in the Sprint-change dialog glitched with "Review could not be saved"): root cause was a frontend/backend contract mismatch already in the committed code. The frontend posts its default hidden set (`components`, `project`, `capacity`, `projectTrack`) with every layout draft, but `apply_layouts` listed only `assignee`, `components`, `project`, `capacity` (plus custom and Epic `team`) as hideable, so any layout draft was rejected as invalid. The UI specs stub the save call and never reached the service. Fix: `projectTrack` is hideable. `tests/test_sprint_review.py::test_layout_accepts_the_default_hidden_columns_the_table_sends` reads the frontend's actual default list, failed first for both row kinds, and now passes. A running local server must be restarted to load it.

Headers: the Select heading is visually hidden (accessible name kept) and the totals row label is a Σ (accessible name Total), because a capitalised word does not fit the 46px sticky selection column and widening it would break the Key/Summary sticky offsets. Drag grips for non-custom columns now sit beside their own label (after it for text, before it for numeric) instead of at the cell edge, where they read as belonging to the next column's heading; custom columns keep the outer-edge grip so the heading spans the field. The alignment audit now judges grip side relative to its label and asserts the grip is within 12px of it.

Grip placement (user decision, after the commits above: "set the drag control for all columns on the right, either way it's confusing"): the per-column placement above is superseded. Every draggable column now carries `planning-review-movable` on its heading, body and totals cells: 14px of right padding forms a gutter holding the grip (`position: absolute` from the heading wrapper), so headings, values, totals and input boxes all share one content box and a grip can never sit under an input. A faint `::after` divider on each draggable heading marks its cell, because in wide text columns the grip otherwise sits next to the following heading. The custom column floor is 107px (was 100px) so its field keeps its 86px box; the compact-width cap in the UI test is 112px. The audit now asserts grip on the right of its label, inside the gutter, with inputs inside the content box.
