## Issue

#267: "inherit planning table view (and epic level custom values) from the current sprint to the future sprint. when during the planning a table was created in the active sprint, inherit it to the following future sprint. when table is modified in the future sprint, keep it as main for the current future sprint."

## Direction (operator, 2026-10-17 to 2026-10-19)

- Custom columns belong to the Department group and are available in every Sprint for that group; they are not Sprint-scoped.
- An Epic is a cross-Sprint entity, so a custom value belongs to the issue and is the same in every Sprint (one value per issue, per group).
- The view (column order and hidden columns) stays per Sprint, is shared across users of the group, and is preserved for earlier Sprints. A Sprint that has not saved a view inherits one; the first layout saved in it makes that Sprint's view its own. A user who opens a Sprint sees the view it inherits (the nearest earlier saved view, see View resolution), changes it, saves on top, and everyone sees the result.
- A small dismissible hint shows where an inherited view came from.
- Hide (this Sprint's view, separately for the Epic view and the Story view) and Archive (every Sprint) stay two separate verbs; Archive gets a clear warning.
- Column order is kept, including for columns added later.
- Stories are Sprint entities and Epics are cross-Sprint. A Story number column that sums is shown on Epic rows as the read-only sum of the Epic's Stories, marked with a superscript "S"; an Epic column is shown on every Story row as the parent Epic's value, read-only, marked with a superscript "E". Never the reverse. Both are automatic, visible by default, and by default the last column of the other view. The rollup exists only while the Story column's total ("Show total") is on (confirmed 2026-10-19). The marker sits before the name on right-aligned columns and after the name on left-aligned ones, with a hit area of at least 24px (2026-10-19), because a trailing marker on a right-aligned column would shift the label off the edge it shares with its values.
- Existing per-Sprint tables should not leave two permanent column sources; every configured Department group gets its own copy of the saved data, rolled out in a quiesced cutover.
- Sprints are ordered by numeric Sprint id, because ids only increase and Sprint names can be anything, not only quarters. Duplicating a group does not copy its review columns. Re-creating a group with a deleted group's id reattaches the old data; this was reaffirmed on 2026-10-19 with the real trigger (ids are creation-slot slugs, see Current State).

## Goals

- Columns and values added for a Department group appear in every Sprint for that group, and a value entered in any Sprint is the issue's value everywhere in that group.
- A Sprint with no saved view shows the nearest earlier Sprint's saved view; the first layout saved in it gives it its own view; earlier Sprints' views never change because of a later Sprint.
- A column added anywhere keeps a sensible position in every saved view.
- A Story number column rolls up into the Epic rows and an Epic column is inherited by its Stories, both read-only and without storing anything.
- No extra Jira requests, no catalog read, and a small, stated, bounded database cost.

## Non-Goals

- Copying columns or values between groups; duplicating a group does not copy its columns. Purging a group's review data when the group is deleted.
- Matching renamed, cloned or moved Epics by anything other than the immutable Jira issue id.
- Per-user views or per-user columns; any change to Jira-owned fields.
- Rewriting existing per-Sprint review rows in the application; a reset, choose-source or delete-view action for views.
- Cross-Sprint Epic totals (they would need Stories outside the table's scope); a Story overriding an inherited Epic value; storing any derived value.

## Anti-Goals

- Saving a view in one Sprint must never change another Sprint's saved view or the view an earlier Sprint displays.
- A read must never create or modify rows; a PATCH without changes must not create a row or take a lock; a cell-only, rename, archive or total save must never create a view row.
- Archive must never be reachable without a warning that it affects every Sprint for the group.
- Application code never copies or shares a column between groups; the one-time adoption copies legacy columns into each group as independent data, and a group re-created with a deleted group's id is the same group id.
- A draft built for one group must never be saved under another.
- A derived cell must never show a partial, mixed-vintage or stale value as if it were complete.

## Design

### What lives where

| Thing | Scope | Shared with | Stored in |
| --- | --- | --- | --- |
| Column definitions (label, type, aggregation, archived, default order, creation anchor) | Workspace + Department group | Every authenticated user | New group schema table |
| Cell values | Workspace + group + issue | Every authenticated user, subject to per-issue Jira authorization | New group cells table |
| Views (column `order`, `hidden`; per row kind) | Workspace + group + Sprint | Every authenticated user | New Sprint view table |
| Totals (`aggregation`) | Column property, so group-wide | Same as columns | Group schema table |
| Derived columns (Story sum on Epic rows, Epic value on Story rows) | Computed in the client from loaded cells | Not stored | Nothing |
| Hint dismissal | One browser | Nobody | Dashboard preference state |

Column ids are the lineage: a column keeps one immutable UUID, and a saved view refers to it by id. The group id is the storage key and is stable on rename.

### Storage

Three new tables, one Alembic revision after `20261001_0018_review_layouts.py` (verified head). Names are provisional until the `EXEC-*` plan; types follow the existing review models.

- **Group schema** (`workspace_group_review_schemas`): `id` Uuid primary key; `workspace_id` FK to `workspaces` with `ON DELETE CASCADE`; `group_id` `String(128)`; `schema_revision` (check `>= 0`); `columns` JSON; unique `(workspace_id, group_id)`.
- **Group cells** (`group_review_cells`): `id` Uuid primary key; `schema_id` FK to the group schema row with `ON DELETE CASCADE`; `issue_id`, `row_kind` (check `epic` or `story`), `column_id`, `value` (`String(500)`, nullable), `revision` (check `>= 1`); unique `(schema_id, issue_id, row_kind, column_id)`. The same cell shape as today, one value per issue.
- **Sprint view** (`group_sprint_review_views`): `id` Uuid primary key; `workspace_id` FK with `ON DELETE CASCADE`; `group_id` `String(128)`; `sprint_id` `String(128)`; `sprint_order` `String(128)` with `CHECK (length(sprint_order) = 128)` (the decimal id left-padded with zeros, so string order equals numeric order with no cast; one shared padding helper serves the route and the adoption script); `layouts` JSON; `view_revision` (check `>= 1`, so 0 always means "no row"); unique `(workspace_id, group_id, sprint_id)` and an index on `(workspace_id, group_id, sprint_order)`.

The existing `workspace_sprint_reviews` and `sprint_review_cells` stay in the database untouched and are no longer read by the application after cutover; they hold no user columns. Downgrade drops only the three new tables, and with them everything entered since cutover. The parity tests assert the foreign keys' `ON DELETE`, the checks, nullability and indexes, not only column names and unique constraints, and an offline PostgreSQL SQL render test (as in `tests/test_db_migrations.py`) asserts the `CREATE TABLE`, cascade, checks and index.

### View resolution (server only)

For group G and Sprint S, one lookup: `sprint_order <= :S ORDER BY sprint_order DESC LIMIT 1` over G's view rows. An equal match is S's own view (`inheritedFrom: null`); a lesser one is the nearest earlier view (`inheritedFrom: {sprintId, viewRevision}`); none means no view, and the response carries `layouts: {}` so the table model's default arrangement applies. It never writes.

- Ties cannot occur: the numeric-id regex forbids leading zeros and `(workspace_id, group_id, sprint_id)` is unique.
- A saved view is a row with at least one row kind. A row kind absent from `layouts` is absent, never stored as `{order:[],hidden:[]}`, because the table reads `hidden ?? DEFAULT_REVIEW_HIDDEN_COLUMNS` and empty arrays would unhide Component, Project, Capacity and Project Track. Inheritance is whole-row: a Sprint whose own row holds only one row kind shows the default arrangement for the other kind, not an inherited one, so any layout save freezes both kinds.
- Sprint ids are not checked against the catalog, so a group is capped at a fixed number of view rows (the `EXEC-*` plan pins it; recommended 500). The cap is enforced on the insert path only: under the schema lock, after the conflict checks and the column and cell validation, a `COUNT(*)` over the group's view rows decides, and a save is refused with `400 review_view_limit`, rolling the whole request back, when the count is at or above the cap; a `viewConflict` is decided first. The client copy is "This group has reached its limit of saved Sprint views." The risk is accepted in writing: any authenticated user can fill the cap with arbitrary numeric ids, a junk row with a low id is inherited by every unsaved real Sprint, and there is no delete-view action, so the plan carries an operator purge runbook.

**Decision (accepted 2026-10-18, inferred from the operator's answer on numeric ordering; a one-function change if reversed): an unsaved Sprint shows the nearest earlier saved view, not the latest saved view overall.** The latest-saved rule would change an earlier Sprint's displayed view: with Sprint A active and unsaved, a layout saved in Sprint B would make A suddenly show B's view, contradicting "previous views are preserved".

**Decision (confirmed 2026-10-18): order Sprints by numeric Sprint id**, with no catalog read. Ids only increase and Sprint names are not limited to quarters, so the rule needs no naming convention. Known limits, recorded and not fixed: a Sprint created out of chronological order, or a Sprint renamed or reused out of order, can inherit a later Sprint's view; the catalog's one-entry-per-name winner can change a quarter's id (future to active) and orphan its saved view, as today; a Board switch interleaves ids; an orphaned or deleted source makes the hint fall back to "an earlier Sprint"; there is no reset, choose-source or delete-view, so correcting a wrong inheritance means rearranging and saving, which then freezes that Sprint's view; and the hint can be dismissed. The hint makes the source visible.

### Column order

- A saved view stores the full order of built-in and custom columns, as today.
- `add` carries an optional `after` inside its `column` object (added to the strict key list): `null` means append, `'summary'` means directly after the pinned columns (what the boundary "+" and `insertColumnId` already use), or an id. A valid id is a same-kind built-in id or a same-kind group column id, archived ones included, including a column added earlier in the same request; anything else is rejected and the stored string is bounded. A missing `after` (legacy or adopted columns) reads as `null`.
- The client never sends a derived column's id. `addAfter` keeps meaning "the clicked column" (`null` is the corner popover, an id is that column's boundary popover), and the anchor to send is computed at submit by `nativeAnchorFor(order, afterId, derivedIds)`, a pure function extracted into `planningReviewTableModel.js` so node tests can cover it. A boundary "+" after a derived column maps to the nearest preceding same-kind native column id, else `'summary'`; the corner "+" (the only touch path, because the boundary "+" is hidden on `(hover: none)`) maps to the last native column of the viewed kind taken from the full `movableIds()` order, hidden columns included, so a new column lands ahead of any derived columns. The creating Sprint's layout uses that same sent anchor, not the clicked id, so the creating Sprint and every other Sprint place the column identically.
- Placement is computed by the client in `buildPlanningReviewColumns`, not stored. It runs on the unfiltered column list (as `layoutColumns` does) and filters for admission afterwards, so an anchor on an admission-gated built-in such as `project` or `teamsInScope` still resolves. Start from the view's saved `order` (empty for the default arrangement) plus any built-ins missing from it in their default sequence; fold the viewed row kind's own custom columns missing from that base, archived ones included so chains resolve, in creation order (the `order` field; the UI never emits `reorder`), each through `insertColumnId(base, id, after)`; an absent anchor lands at the end. Derived columns missing from the order are appended after that fold, in creation order. Hidden is unaffected, and a new column is visible unless the view lists it as hidden. A saved layout freezes derived ids into `order` at their current positions, which stays consistent because new native columns anchor to a native id; a layout saved while "Show total" is off drops that derived id, so its position is lost when the total is turned back on (accepted).
- Adding a column in the UI also saves a layout in the creating Sprint (existing behavior), so that Sprint gets its own view with the column at the chosen position. This matches the issue: a future Sprint that is edited becomes the main one. Other Sprints' saved views lack the column and place it by the fold. The group's default order among custom columns (`order`, `reorder`) is unchanged.
- **Decision (my call, confirm):** this is the author's reading of "keep the order of the columns".

### Story relations (derived columns)

Stories belong to Sprints and Epics span them, so the two kinds are related by two read-only display rules and nothing else. A derived column is computed in the client from cells that are already loaded; it adds no storage, no column kind, no endpoint and no read.

- **Value model.** `derivedValue(row, column, ctx)` returns `{scaled, complete}`, where `scaled` is a `bigint` or `null`, displayed through `formatReviewScaled`, and `ctx.isLoaded` is `id => review.isRowReadable({rowKind, issueId: id})`. A Story child's id uses the same expression as `issueRow` (children are raw tasks with no `issueId`), and `epicIssueId` uses the Epic row's id expression. `reviewValue` returns the formatted string for display; `planningReviewTotals` and `sortPlanningReviewRows` branch on the derived flag and read `.scaled`, so totals are blank when any contributing value is incomplete and incomplete values sort as empty. Derived sums never pass through `parseReviewNumber`, which rejects values above 999999999.999 and would sort a large sum as 0.
- **Up (Story to Epic).** A Story-kind number column with `aggregation: 'sum'` also appears in the Epic view. The coupling is deliberate (confirmed 2026-10-19): a column's total setting means it is summable, so turning "Show total" off removes the rollup in every Sprint's Epic view, and because number columns default to a sum, a rating-style Story column needs its total switched off. An Epic row shows the sum of that column over its `children` (the Sprint and the current filters, the same set that feeds "Sprint SP") read from `review.cells`. The cell is incomplete, and so blank, until every in-scope Story is loaded and not unavailable, and while a manual `force` refresh is loading, signalled by a flag set only for non-automatic `force` loads (the existing `loading` flag is set for every non-automatic load, so an incremental load would blank every derived cell); a refresh that fails partway restores the pre-refresh cells, or the derived cells stay blank until a load succeeds, so a mixed sum never shows as complete; it is also blank when no in-scope Story has a stored value, so adding a column does not flood Epic rows with 0; otherwise a blank Story value counts as 0. Story text columns and non-sum Story columns do not appear in the Epic view.
- **Down (Epic to Story).** Every Epic-kind column, number or text, also appears in the Story view. A Story row shows the parent Epic's value, found through `epicIssueId`, a new field set in `buildPlanningReviewRows` from `group.epic.id` (Story rows carry only `epicKey` today), read from `review.cells`. No other-mode rows are needed, so `dashboard.jsx` does not grow. The cell is blank until the Epic is loaded and not unavailable (the existing availability guard checks only a row's own id, and an automatic refresh keeps stale saved cells), and blank when the Epic has no issue id. It is repeated per Story and never summed.
- **Never reversed.** Nothing from the Epic is divided among Stories and no Story value is written into an Epic column. A derived cell is never editable and never written; `setCell` and the server already reject a cell whose column row kind differs from the cell's row kind.
- **Marker.** The header shows a superscript "S" on a Story column in the Epic view and "E" on an Epic column in the Story view, beside the heading button and not inside it (a focusable marker cannot live in a button). It sits before the name on right-aligned (numeric) columns and after the name on left-aligned ones, so the label keeps the alignment edge it shares with its values and totals (the `bodyDelta` and `totalDelta` audit stays under 1px), and its hit area is at least 24px. It follows the existing real-versus-docked header rule (the non-interactive copy gets `tabIndex -1` and `aria-hidden`), so there is one focusable marker and one readout instance, and a readout open across the dock flip is closed through the readout's existing `suppressed` prop. It appears on review columns only; the built-in parent-derived columns in the Story view (Epic, Capacity, Project Track) stay unmarked. The accessible name "<label>, Story property" or "<label>, Epic property" is carried into the `th` label, the grip, the menu trigger, the popover name and the heading button (which has no label today), and the Show hidden rows show the visible superscript as well. The readout says "Story property, summed from this Epic's Stories in this Sprint and the current filters" or "Epic property, inherited from the parent Epic". `EpicHeaderValueReadout` is shared: it opens only when truncated, opens on pointer-enter and focus, and sets its `aria-label` to its value, so every new behavior exists only under an always-on mode that defaults off. In that mode it is visible when a mouse hovers, or focus is visible, or it is pinned; a click toggles pinned, a document pointer-down outside clears it, and the truncation measurement does not close it. Touch pointers do not hover-open, so a tap pins it, a second tap closes it and an outside tap closes it, with no open-then-close from a hover and a click toggle stacking. The marker is a native `<button type="button">` named "Story property" or "Epic property" with the sentence as `aria-describedby`; existing readout users stay unchanged, pinned by `planning_review_table.spec.js`, `planning_capacity_editing.spec.js` and `eng_group_board_card.spec.js`; and a native `title` is never used. ### Read contract

- `GET /api/eng/sprints/<sprint_id>/review?groupId=<id>` accepts exactly one `groupId` and nothing else (a duplicate, whitespace-padded or extra argument is a 400; POST and PATCH keep rejecting any query string, so the args rule is per route) and returns `{schemaVersion, sprintId, groupId, schemaRevision, viewRevision, columns, layouts, inheritedFrom, capabilities}`. `schemaRevision` is the group's column revision; `viewRevision` is the Sprint's own view revision (0 when it has none). Reads do not consult the group catalog: an id with no rows returns the empty schema, and a deleted group's data still reads back by id, which is the reattach.
- `POST …/review/values/read` takes `groupId` in the body and returns the cells of the group's active columns for the requested issues, whichever Sprint is in the path; archived columns' cells are excluded, because group-wide accumulation would otherwise inflate reads (and 500 issues by 30 columns can already exceed the 10,485-cell response cap, which halves the batch on the client). `unavailableIssueIds` and the per-issue `authorize_issues` pass are unchanged, so access still comes from the signed-in user's Jira visibility.
- `groupId` is a string of 1 to 128 characters, equal to its stripped form, with no control characters; a missing or malformed value returns `400 invalid_review_request`. A group whose configured id is longer cannot use review columns (documented limit).

### Write contract

`PATCH …/review` accepts `groupId` (required), `baseSchemaRevision` (required, as today, and not compared for a layout-only request), `baseViewRevision` (optional, default 0, checked only with a layout action), `schemaChanges` and `cellChanges`; a query string is rejected.

- Error precedence: authentication and capability first (401, `503 review_storage_unavailable`), which means the route wrapper checks the capability before it parses the body, for PATCH and for the values read (which also passes the parsed body as an argument), and takes each route's allowed query names as a parameter so GET accepts `groupId` while the others accept none; then structural validation of the whole request through a stateless `validate_schema_changes` split out of `apply_schema` and `apply_layouts` (keys, types, id shapes, the `after` shape, and required `order` and `hidden` lists on layout actions), ahead of authorization so a malformed layout cannot spend the Jira budget, while state checks (duplicate id, column lookup, reorder set, layout-id membership) stay inside the transaction; then group membership; then Jira authorization (403/503); then the transaction.
- Group membership reads `current_shared_groups_config` in its own session and derives ids as `str(id or '').strip()`, matching exactly and case-sensitively; an id not found returns `400 review_group_unknown`. A missing group config row yields an empty catalog, so every group is unknown (fixtures need a `WorkspaceGroupConfig` row); a missing, `null` or empty `groups` is an empty catalog (every group unknown), and a truthy non-list `groups` or a non-dict entry returns `503 review_unavailable`; `InvalidSharedGroupConfig` is unreachable because the validator is not passed; a group deleted between the check and the write is benign.
- An empty request (no `schemaChanges` and no `cellChanges`) returns the 200 base keys with `cells: []`, creates no row and takes no lock.
- Every application writer, including layout-only saves, takes the group schema row first (insert-do-nothing, then `FOR UPDATE`); the adoption script is the one exception (table locks and plain inserts, see Existing per-Sprint tables). A request with a layout action then handles the Sprint's view row under that lock: select it; if absent, `INSERT` with `view_revision = 1` after the checks below; if present, require equality and bump. There is no insert-do-nothing and no second lock, so no insert race exists and a second first-save returns `viewConflict`. The lock serializes saves for one group across Sprints and users and is short because Jira authorization runs before the transaction.
- In-transaction order, as one list: (1) lock the schema row; (2) when a layout action is present, select the Sprint's view row; (3) evaluate conflicts as one predicate, `schemaConflict or viewConflict or cellConflicts`, at the first 409 site (a view row that is absent with `baseViewRevision != 0`, or present with a different revision, is a `viewConflict`); (4) apply the column actions and normalize the cells, whose 400s and the second 409 (a cell against an archived or missing column) come next; (5) on the insert path, apply the view cap (400); (6) write. A `review_view_limit` therefore never masks a 409.
- Column actions apply sequentially first. `schema_revision` is checked against `baseSchemaRevision` and bumped (once) if and only if the request has at least one non-layout action; a layout-only request checks only `baseViewRevision` and leaves `schema_revision` alone, so layout saves never conflict with column drafts. Layout actions validate against the post-action columns, archived included, so the normal Add column plus layout save in one request succeeds, and the relaxed `apply_layouts` allows custom ids of both row kinds.
- The server stores exactly the layout actions in the request, merged over the Sprint's own row if one exists, and copies nothing from another Sprint.
- Cell-only and column-only requests never create or touch a view row. Cell changes validate against the group's columns (existence, archived, row kind, type) and keep today's per-cell `baseRevision` semantics, touching neither revision. Because values are per issue, two users editing the same Epic's value from different Sprints conflict like two users in one Sprint do today.
- Both 409 raise sites always carry `schemaConflict`, `viewConflict` and `cellConflicts`, plus `columns` and `schemaRevision` as today; resolved layouts are not required on a 409, which has no consumer. Every 200 carries `schemaVersion`, `sprintId`, `groupId`, `columns`, `schemaRevision` and `cells`, and carries `layouts`, `viewRevision` and `inheritedFrom` (`null`) only when the request had a layout action, so a cell-only save needs no view resolution (a declared change: today `layouts` is always present). `sprintReviewApi.js` forwards `viewConflict`. The controller applies a 200's fields only from keys present: `layouts`, `viewRevision` and `inheritedFrom` only when present, and `columns` and `schemaRevision` as saved values only when the request carried a column action; otherwise it records them as `current*` and forces a refresh, so a fresh column's cells are read and the held layouts are not regressed by the `data.layouts || state.layouts` idiom. It treats either conflict flag as "the shared table changed, draft preserved".
- **Decision (my call):** carry the group as a query argument on GET and a body key on POST and PATCH, on the existing routes, so policies, CSRF and `X-Requested-With` guards stay where they are.

### Existing per-Sprint tables

The shipped table stores columns, layouts and values per `(workspace, Sprint)` with no group. Showing them next to group columns would leave two permanent column sources.

**Decision (confirmed 2026-10-18): a one-time adoption script copies the saved data into every configured Department group, run in a quiesced cutover, and the legacy tables are then retired from reading.** The target is always empty at that moment, which keeps the script simple.

Script conventions follow `scripts/promote_legacy_shared_admin_config.py`, under an importable name such as `scripts/adopt_legacy_sprint_reviews.py` with a way to list workspaces that hold legacy rows: required `--workspace-id`; dry run by default; `--apply` requires `--expected-sha256` with the `sha256:` prefix; a refusal raises `ValueError` (exit 1) and only a lock timeout returns 2; a physical-table preflight confirms every required table exists. It reads groups through `current_shared_groups_config` with a context carrying only `workspace_id`, never the bound validator in `jira_server.py` (importing it loads the repo `.env`), and applies the route's id rules itself (an id must equal its stripped form), aborting with a count on a malformed or over-128-character id or a non-numeric legacy Sprint id (none can exist). When legacy rows exist and no group is configured it refuses; when no legacy rows exist it reports that nothing needs adopting and exits 0; legacy rows with no columns, layouts or cells (an empty PATCH leaves one) are skipped and do not count as legacy data. It reuses `apply_schema`, `apply_layouts` and `MAX_ACTIVE_COLUMNS`.

- **Refusal, not no-op.** `--apply` refuses before any write if any group schema, cell or view row exists for the workspace, so a repeated run, a run after use of the new tables and a rollback-then-forward all refuse with zero writes. A group added later starts empty because nothing re-runs the script. All groups are written in one transaction.
- **Atomicity.** The transaction takes its locks first, with a 5-second `lock_timeout` and exit 2 on timeout: on PostgreSQL, `LOCK TABLE … IN EXCLUSIVE MODE` on the group schema table first and then the other two new tables (every new-app writer enters through the schema table, so locking it first avoids a deadlock with a writer that holds it while waiting for another), and `IN SHARE MODE` on both legacy tables, which needs UPDATE, DELETE or TRUNCATE privilege on them and INSERT on the new ones, with a dialect guard for SQLite like the precedent's fence. It then recomputes the digest, then checks emptiness, then writes with plain `INSERT`s that abort on any unique conflict (never insert-do-nothing). A concurrent first write by the new app either commits first, so the script refuses with zero writes, or waits for the script's locks and sees the adopted data; a lock wait past 5 seconds makes the script exit 2, a deadlock victim exits non-zero with zero writes, and the script never overwrites a live row. On SQLite the guard skips locks and SELECTs run outside a transaction, so a racing check-then-insert is stopped by the plain INSERT's unique key with an `IntegrityError`, which is tested.
- **Digest.** The canonical form (serialized like the precedent's `_fingerprint` and including the workspace id) is a rule-version constant, the sorted group ids, and the legacy rows ordered by numeric Sprint id and then id, each with its canonical-JSON columns and layouts, `schema_revision`, and its cell tuples `(sprint_id, issue_id, row_kind, column_id, value, revision)` sorted; the dry run prints it and `--apply` recomputes it inside the transaction.
- **Columns.** Legacy columns are processed in ascending numeric Sprint id, then list position, and grouped by `(row kind, casefolded stripped label, type)`; a row kind never merges across kinds. If the latest member of a key is archived the whole key is not adopted (counted in the report). Otherwise archived members are discarded with their cells (counted), and the adopted column takes the id and label of the earliest non-archived member and the `aggregation` of the latest non-archived member; cells and layouts of the other non-archived members are remapped to that id, while archived members' ids are dropped from layouts like any unadopted id. Each merged column is one `add` with its final aggregation, so a request holds at most 60 net adds under the 120-action limit. The cap ranks keys by their latest member's `(Sprint id, list position)` descending and keeps the first 30 active per row kind; the rest are not adopted and are listed by every member's column id and Sprint id, with their cells counted (it does not abort). Merged columns are added in the order in which their first non-archived member appears in the processing order. Same-key duplicates within one Sprint merge, the later list position winning a cell tie. Ids are unique per group schema, so the same id appears in several groups' schemas. A legacy column id can also repeat across Sprints under different keys (any user can send the same id for two Sprints); the script aborts with a count and the Sprint ids, because `apply_schema` rejects a duplicate id.
- **Cells.** Each legacy cell moves onto its merged column per issue with `revision` 1; the highest Sprint id wins a conflict and a `NULL` clear counts as a value, so a later clear wins. The report counts the dropped conflicting values and the cells dropped with archive-intent and cap-excluded keys. Adopted data can exceed the read response cap, which the client already handles by halving batches.
- **Views.** A view row is written only for a legacy layout that holds at least one row kind, with only the kinds present, column ids remapped and unadopted ids dropped, duplicates collapsed keeping the first occurrence, legacy layout ids are same-kind by construction and the script asserts it before the relaxed `apply_layouts` runs, and `view_revision` 1. Legacy layouts mostly hold one row kind, because the UI saves one kind per save; the script writes only what legacy has and does not fill the missing kind from an earlier view, so that kind shows the default arrangement in that Sprint. A legacy Sprint with empty layouts creates no row and still inherits. Beyond the view cap the script keeps the highest rows by `sprint_order` and lists the skipped Sprint ids. A new group schema row starts at `schema_revision` 1.
- **Derived columns after adoption.** Every adopted Story number column with a sum appears as a visible, last rollup column in every group's Epic view, and every adopted Epic column appears in every group's Story view; the report counts them and the runbook says so.
- **Hygiene.** The report prints counts and column or Sprint ids only, never labels, values or issue ids, including the per-merge id lists (every member's column id with its Sprint id) and insert counts per table and group; an `IntegrityError`, whose message echoes bound parameters, is caught and re-raised as a sanitized `ValueError`; inserts are chunked for SQLite and PostgreSQL parameter limits; test fixtures are synthetic; legacy rows are never modified or deleted.

**Cutover runbook** (precedent: migration `20260827_0008`, writers quiesced after a backup): back up the database; record the current `RUN_DB_MIGRATIONS` value and set it to `false`; stop every replica, so nothing serves; run Alembic as a one-off job; run the script dry run and then `--apply` with its digest, for every workspace that holds legacy rows, as one-off jobs from the new image (the Dockerfile gains a `COPY` for the script); restore `RUN_DB_MIGRATIONS`; start the new app. The image's entrypoint ends in a fixed `exec gunicorn` and ignores arguments, so the Alembic and script jobs need an entrypoint override (a command-only override still runs gunicorn), the database URL and connection-mode variables the migration job already uses, and a database identity with the privileges above. Open tabs must reload (an old bundle gets a 400 without `groupId`). Every workspace that holds legacy rows must have a configured group before the cutover (a workspace with legacy rows and no group, or no group config row, makes the script refuse, and the quiesced app cannot create one), so the operator checks that while the old app still serves. `--list` prints, per workspace, whether legacy rows exist and whether group rows exist, and the runbook ends with a check that every workspace with legacy rows is adopted before the app starts. The literal commands are `python -m alembic -c backend/db/alembic.ini upgrade head` and `python scripts/adopt_legacy_sprint_reviews.py --workspace-id <id>`, with `--apply --expected-sha256 <digest>` for the apply. The README and `INSTALL.md` deploy paragraphs carry the exception.

| Step that fails or is rolled back | State | Recovery |
| --- | --- | --- |
| Backup or Alembic upgrade | Nothing serves | Fix and re-run, or restore the backup |
| Dry run | Nothing written | Fix the input |
| `--apply` | The single transaction rolls back; legacy untouched | Re-run |
| Abort the release after the upgrade | The old image fails its startup preflight against the new head and cannot downgrade a revision it does not know | Run `alembic downgrade 20261001_0018` from the new image first, then restart the old image |
| After `--apply`, before the new app serves | Only adopted data exists | Clean redo from the new image: `alembic downgrade 20261001_0018`, `upgrade head`, re-run |
| After the new app served and users wrote | A re-run refuses (group rows exist) | Forward fix only; a downgrade loses the entries made since |

## Known limits and rollout risks

- Sprint id proxy and its recovery limits (View resolution); the unchecked-id view cap as an accepted insider risk with an operator purge runbook; the permanent per-group 240-column ceiling.
- A group re-created with a deleted group's id, including the default "New Group" slot, silently inherits the old group's columns, values and views (reattach, approved 2026-10-19); archiving the unwanted columns is the recovery.
- A column action by anyone interrupts dirty column drafts elsewhere in the group, and a layout change interrupts dirty layout drafts of the same Sprint; cell-only drafts are not interrupted.
- At cutover, adopted columns surface as derived columns in every group's Epic and Story views, and "highest Sprint id wins" collapses per-Sprint value history (the report counts dropped values).
- Archive affects every Sprint for everyone and cannot be restored; any layout save freezes a Sprint's inheritance for both kinds; a layout saved while "Show total" is off loses the derived column's position.
- Add column always carries a layout, so at the view cap in a Sprint with no view of its own no column can be added, and a cell draft in the same request rolls back with it; Discard is the only exit.
- The corner "+" pins a native column id, so in a Sprint whose view moved a native column to the front a new column can land second rather than last, and a boundary "+" after a mid-order derived column lands before it.
- Key-level cell loss at adoption (archive-intent and cap-excluded keys, counted in the report); whole-row inheritance after adoption (an adopted single-kind view makes later Sprints show the default arrangement for the other kind even when an earlier row held it); and a local-runner database that migrates with no adoption step (its legacy data stays unread until the script is run by hand).

### Acceptance criteria

1. Group isolation: a column added under group X appears for every Sprint of X and never for group Y; with identical column ids in both groups, archive, rename, a value and a revision change in X leave Y unchanged.
2. A value saved from Sprint C is read from Sprint A (one value per issue per group); concurrent edits of one value from two Sprints return a cell conflict by revision.
3. View resolution through the single `<=` lookup: own view, else the nearest earlier by numeric id (ids 9 and 10 and a 128-digit id), else none; a later Sprint's view never affects an earlier Sprint; a single-kind row does not inherit the other kind; at most one view row is loaded by the ORM with the cap's worth of views seeded (counted with a load listener, not a SQL count); a save at or above the cap constant (recommended 500) returns `400 review_view_limit`, with `viewConflict` decided first and the whole request rolled back; the `sprint_order` check rejects an unpadded writer.
4. View row creation: under the schema lock an absent row requires base 0 and is inserted at revision 1, a second first-save with base 0 returns `viewConflict`, a present row requires equality; a first layout save stores exactly the request's layout actions, returns `inheritedFrom: null`, leaves the source view unchanged, keeps an absent kind absent so default hidden columns still apply, and requires `order` and `hidden`.
